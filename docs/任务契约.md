## 0. 为什么需要这份文档（先说清它不是什么）

**它不是流程图。** 流程回答「数据怎么流过去」，本文件回答「**这个系统由哪几件事组成、每件的成败判据是什么**」。

三层必须分清，否则 harness 会装错东西：

| 层 | 定义 | 例子 | harness 里的位置 |
|---|---|---|---|
| **工具**（tool） | 一个**动作** | 拉热榜、拉话题帖、算 facts | 被任务调用 |
| **任务**（task） | 有名字 + 目标 + 产物 + **成败判据**的单元 | 热点追踪识别、素材获取 | **任务注册表的一项** |
| **流程**（flow） | 任务之间的编排 | 时钟 → 任务 → 任务 | 图的边 |

> ★ **时钟驱动的是「任务」，不是「脚本」。** 一个任务可能调多个工具（热点追踪 = 采集 + 感知），
> 也可能不调工具（校准只读轨迹）。此前把时钟画成「时钟 → 采集工具」是按数据流画的，
> **按任务画应该是「时钟 → 任务 →（任务内部调工具）」。**

## 1. 任务目录（九件）

从目标原文倒推，本系统由九件任务组成。**这是完整的任务清单，不是模块清单。**

| # | 任务 | 输入 → 产物 | 现状 |
|---|---|---|---|
| T1 | **采集巡检** | 通道 S1–S6 · U1 → 原始数据（三类目录） | ✅ 已建 |
| T2 | **热点追踪识别** | 热榜 / 帖子流 → 话题状态 + 迁移事件 | ✅ 已建 |
| T3 | **官方排期** | 官微公告 → 结构化排期日历 | ⚠️ 部分（31 条原文已攒，LLM 解析待充值） |
| T4 | **情报简报** | facts → 简报 + facts 报告 | ✅ 已建（决策层降级） |
| T5 | **素材获取** | 帖子 / 评论 → 4 类素材库（带溯源） | ⚠️ **部分**（2026-10-01：纯代码两类已实现，梗/二创角度需 LLM） |
| T6 | **创意生成** | 素材 + 热点 → 创意角度与运营动作 | ⬜ 空白 |
| T7 | **突发响应** | 异常事件 → 严重性 → 预案 + 处置清单 | ⬜ 空白 |
| T8 | **可视化展示** | 任务产物 → 看板 / 前端 | ⚠️ 部分（与 harness 无接线） |
| T9 | **校准** | 轨迹 → 时效指标 / 阈值 → 回灌 | ⚠️ 部分 |

**依赖值链**（不是直线）：

```
采集巡检 → 热点追踪识别 → ┬ 素材获取 ─┐
                          ├ 情报简报 ─┤
                          ├ 官方排期 ─┼→ 创意生成 → 可视化展示
                          └ 突发响应 ─┘
                                校准 ←（回灌 T2 / T7）
```

★ 断点明确：**创意生成依赖「素材 + 热点」，而素材获取是空白 → 创意生成必然空白**。
★ 突发响应独立于创意链（止损线，非增长线），可单独做。
★ **接前端接在 T8**：前端读的是**任务产物**，不是脚本 → 所以每个任务必须填 `artifact_contract`。

## 2. 契约 Schema（每任务必填 17 项）

| 分组 | 字段 | 语义 | 硬要求 |
|---|---|---|---|
| 身份 | `task_id` | 稳定标识（代码里用它） | 英文 snake_case |
| | `name` | 中文任务名 | — |
| | `goal` | 一句话目标（人话） | — |
| 接口 | `inputs` | facts 字段 / 数据文件 / 上游任务产物 | 明确到**文件名或字段名** |
| | `tools` | 调用哪些工具 + 单次预算 | 工具必须是注册表里的 |
| | `outputs` | 产物落在哪（文件 / 表 / 字段） | 明确到**路径与表名** |
| | `artifact_contract` | **给谁看 / 什么格式 / 什么粒度** | ★ 前端接口，必须有 |
| | `text_access` | **读哪些文本源 / 什么粒度 / 是否送 LLM / 读完回传什么** | ★ 见 §2.1，防「盲目」也防「失控」 |
| 判据 | `success` | 什么算成功 | ★ **必须可代码判定** |
| | `degrade` | 失败时产物变成什么 | 必须**如实标注**，不许假装 |
| 运行 | `schedule` | 周期 或 触发条件 | 二选一必须明确 |
| | `budget` | `max_tool_calls` / `max_net_calls` / `timeout` / `max_retries` / `token` | 不许为空；**网络与工具分开计**（见 §3 注） |
| | `idempotency_key` | 重跑不产生重复副作用的键 | ★ 重试的前提 |
| 安全 | `on_fail` | **按错误类型分派**：重试 / 降级 / 打回 / 中止 | 不许只有一种 |
| | `human` | 是否需要人确认（`interrupt` 点） | 高危操作必须 True |
| 关系 | `depends_on` | 上游任务 | 无则空数组 |
| | `status` | 现状（已建 / 部分 / 空白） | 与 §1 一致 |

### 2.1 为什么必须有 `text_access`（2026-10-01 用户追问）

> 用户质疑：「**原始文本不进 State，那怎么保证信息？追踪热点 / 情报 / 素材 / 创意增长
> 这四个还是要原文的，不然就是盲目的。**」

这条质疑成立，而且戳中一个**表述陷阱**：说「原文不进 State」很容易被误读成「系统不读文本」，
**那会做出一个盲目的系统**。本项目自己撞过这堵墙 —— `ferment_judge` 的旧判据（游戏归属字面匹配）
命中 **0/10**，改用**读语义**后 **5/10** 可发酵（[架构设计 §1.2](./Agent-v2-架构设计.md)）。

**所以四个任务都要读文本，区别只在「读多少」与「谁读」**：

| 阶段 | 读多少 | 谁读 | 回传什么 |
|---|---|---|---|
| 发现 | 不读 | 代码 | 数字（变化率） |
| 判断 | **短文本**（标题 / 摘要 ~90 字） | 代码 + LLM | 结论（分数/标签），**带 source id** |
| 加工 | **长文本**（Thread 全文） | LLM（工具调用内部） | 产物落文件，State 只留 id |

准确表述是：**原文不做图的长期记忆；需要时按 id 检索、作为那一次调用的临时输入，用完只留结论。**

`text_access` 就是把这件事**写成可校验的声明**：

```python
"text_access": {
    "sources": ["discovery_posts.summary", "discovery_comments.content（Thread 束）"],
    "granularity": "full",        # none | short | full
    "via_llm": True,              # 是否送模型
    "returns": ["material_id", "type", "topic_key", "count"],   # ★ 只回传结论与 id
}
```

**校验规则（`validate()` 强制，有测试）**：

1. `granularity ∈ (none, short, full)`；`none` 不许有 `sources`，`short/full` **必须**有 `sources`
2. `via_llm=True` 必须有 `returns` —— **不许把原文回传**
3. `returns` 里不许出现原文类字段名（`raw_text/content/summary/…`）
4. ★ **工具含 LLM 类（`llm_classify`）却 `via_llm=False` → 判非法**：
   声称做语义判断却不声明读文本，**就是要做成盲目的系统**

### 四条写契约的纪律

1. **`success` 必须可代码判定**。写「产出质量好」是无效契约；写「`assert_traceable` 全通过」才有效。
2. **`on_fail` 必须按错误类型分派**。网络抖动该重试，数据脏该降级，参数错该打回，预算不足才中止——**不是二选一**。
3. **`degrade` 不是失败**。降级要产出「部分结果 + 显式标注原因」，比整任务失败好。
4. **不知道的值写 `需拍板`**，不许拍脑袋填。

## 3. 契约 ① 热点追踪识别 `hotspot_track`

```yaml
task_id: hotspot_track
name: 热点追踪识别
goal: 从 TapTap 平台热榜与话题帖子流中识别值得关注的社区热点，
      持续追踪其生命周期（冒头→升温→爆发→退潮→沉寂），并在状态迁移时产生事件。

inputs:
  - data/raw/taptap/hot_hashtags.csv          # S4 全站话题热榜
  - data/raw/taptap/discovery_posts.csv       # S5/S6 帖子流（含 hashtag_id）
  - data/outputs/agent/platform_insight.json # 平台事件 facts（可选维度）
  # 无上游任务（本任务是链头，只依赖 T1 采集巡检）

tools:
  - crawl_taptap_discovery --source hot-hashtags --limit 10    # 1 次/轮
  - crawl_taptap_discovery --hashtag-ids <ids> --comment-limit 20  # 深采，≤5 话题/轮
  - platform_insight.py      # 生成平台 facts（必跑 stage）
  - topic_tracker.py --sample  # 记录采样 + 判状态迁移
  - events.py --run            # 迁移 → 事件 → 分发
  - features.py --run          # F1–F7 特征落盘（先算不判）

outputs:
  - data/state/topic_tracker.sqlite3 → topic_state（当前状态）
                                            → topic_series（时间序列）
  - data/state/events.sqlite3        → topic_event（迁移事件，幂等）
  - data/state/post_snapshots.sqlite3 → F2/F3 速率原料
  - data/raw/taptap/features/features.jsonl  # 特征快照（append-only）
  - 11情报Agent/reports/scheduler_status_latest.md

artifact_contract:
  给谁看: 运营侧（看板/前端）
  格式: site 直读 JSON —— 话题名 / 当前状态 / 峰值 / 首见时间 / 最近迁移
  粒度: 每话题一行；状态迁移另出事件流
  ★ 前端素材页/看板的话题列表就读这里

success:
  - 采样写入成功：topic_series 本轮新增 ≥1 行
  - 被追踪话题的序列 sample_count ≥ 2（否则无法判迁移 → 记 insufficient_data）
  - 迁移事件幂等：同一 event_id 不重复入库
  ★ 关键：「本轮没有热点/没有迁移」也算成功 —— 不得把「无迁移」当失败

degrade:
  - 热榜拉取失败 → 本轮跳过采样，记 stale；不产生迁移（**不猜测**）
  - 无话题命中 → 输出「本轮 0 话题」而非报错

schedule: 周期 15min（探测）；深采 = 事件触发 + 同话题冷却 60min
# ★ 文本读取声明：本链只读标题（短标识）；判「值不值得做」的语义判断在 ferment_judge
text_access:
  sources: [hot_hashtags.title, discovery_posts.title]
  granularity: short          # 追踪判变化率；不看全文
  via_llm: false
  returns: [topic_key, title, state, peak_metric, series_delta]
  # ★ 语义判断的交接点（不是缺口！）
  ferment_handoff: 语义判断由**深采决策**消费 —— scheduler.decide_drill 读
                   outputs/ferment_judge.json 的 ferment_score/verdict 决定挖哪些话题
                   （日志里「冒头但可发酵度 act（60）」就是它）。
                   发现高频便宜、判断低频贵 —— 刻意如此，不是没接上

# ★ budget 分两级（实现后精化）：真正要控的是**网络调用**（反爬）与**token**（成本）；
#   本地脚本调用次数的意义是"防跑飞"，所以上限给得宽。
budget: {max_tool_calls: 8, max_net_calls: 2, timeout: 600, max_retries: 2, token: 0}
idempotency_key: hash(topic_key + to_state + occurred_at)   # ✅ 已实现（events.py）

on_fail:
  网络类(URLError/502)   → retry ≤2（退避 2s/4s）
  空数据(0 条)           → degrade（记 stale，不猜测）
  解析/schema 不符       → 打回（不进图，记轨迹）
  反爬(WAF 挑战页)       → 中止本轮 + 拉长间隔（已实测 1 req/s 安全）

human: false
depends_on: [collect_patrol]
status: 已建
```

**实测状态**：调度器已跑 64 轮（约 20min/轮）· `topic_series` 14 话题多时间点 · F1 ok 13/22 · 事件数 0（尚未判出真迁移，属正常）

## 4. 契约 ② 素材获取 `material_extract`

```yaml
task_id: material_extract
name: 素材获取
goal: 从已采集的帖子与评论中抽取 4 类素材（原帖引用 / 热评金句 / 梗 / 二创角度），
      每条素材带可验证的溯源；够不上溯源门槛的一律丢弃。

inputs:
  - data/raw/taptap/discovery_posts.csv
  - data/raw/taptap/discovery_comments.csv
  - 上游 T2 产出的 topic_key / topic_title   # 素材归属话题，两系统据此对齐
  - Thread 结构（moment_id + 评论束）        # 见 素材层设计 §3.5：存 Thread，不存孤立评论

tools:
  - 抽取器（纯代码）      → 原帖引用 ✅ / 金句选取 ✅       成本 ≈ 0
  - llm_classify（LLM）  → 金句分类仲裁 ⚠️ / 梗（两轴分类 + 跨社区发现）/ 二创角度
  - pii_hash.py           → 横切：素材带作者名，但绝不入库
  - assert_traceable()    → 准入闸门（代码层强制，见素材层设计 §2.3）

outputs:
  - data/raw/taptap/materials/materials.jsonl   # 4 类统一样本（含 provenance）
  - Thread 库                                    # 检索与生成的基本单元

artifact_contract:
  给谁看: 运营侧（前端「素材页」）
  格式: 素材卡片 JSON —— material_id / type / text / topic_key / thread_id /
        provenance（moment_id + 可打开的 TapTap url）/ metrics
  粒度: 一条素材一卡；四类可筛选
  ★ 这就是前端素材页的数据源，不需要额外推送层

success:
  - ① 溯源 100%：每条素材 assert_traceable 通过（moment_id 必带 + url 以
    https://www.taptap.cn/moment/ 开头）；**不通过的丢弃并计数**
  - ② 四类各自可判定：
      原帖引用 = 纯代码必成
      热评金句 = 选取纯代码；分类需 LLM 仲裁
      梗       = 需 LLM 两轴分类 + 跨社区发现
      二创角度 = 必须 LLM
  - ③ PII：作者名可展示但绝不入库（硬约束，CI 有 guard）

degrade:
  ★ 分层降级（本任务最容易做错的地方）：
  - LLM 可用      → 4 类全出
  - LLM 不可用    → **只出「原帖引用」+「金句选取」两类**，
                    并显式标注「梗 / 二创角度未生成，原因：LLM 不可用」
  ★ 纪律：部分产出 + 显式标注 > 整任务失败。不得因 LLM 不可用而让任务整体失败。

# ★ 文本读取声明：这一类**必须读全文**（判梗要看评论原文与语境）
text_access:
  sources: [discovery_posts.summary, "discovery_comments.content（Thread 束）"]
  granularity: full
  via_llm: true
  returns: [material_id, type, topic_key, count]
  note: 原文经 Thread 检索后作为**那一次调用的 prompt**，用完即弃；产物落 materials.jsonl
  source_id_required: true    # 用完即弃 → 结论必须带 id，否则不可回放

schedule: 需拍板（周期 跟随采集 / 事件触发 话题升温时抽该话题 —— 二者可并存）
budget: {max_calls: 需拍板, timeout: 300s, max_retries: 2, token: 需拍板（LLM 两类）}
idempotency_key: hash(moment_id + comment_id + type)   # 同素材不重复入库

on_fail:
  LLM 类失败（402/超时）  → degrade（出可出的类，标注缺哪些）
  溯源失败（缺 moment_id / url 不合法）→ **丢弃该素材并计数**（不是打回）
  数据缺字段（CSV 列缺失）→ 打回（不进图，记轨迹）
  LLM 成本超限            → 中止该子类，其余照常

human: 可选（PII 抽检）
depends_on: [hotspot_track]
status: ⚠️ **部分**（2026-10-01）—— 纯代码两类已实现并落盘：
        96 条素材（原帖引用 47 / 金句候选 49）+ 149 个 Thread，溯源达标率 1.0；
        `meme` / `remix_angle` 需 LLM，**显式标注缺失**（分层降级，任务仍判 ok）
        实现：`11情报Agent/materials.py`（27 测试）· 已注册为 harness 真 tool `material_extract_code`
```

**待定项（需拍板，不许我拍脑袋填）**：

1. **`schedule`**：周期（跟随采集）还是事件触发（话题进入升温/爆发时抽该话题）？还是两者并存？
2. **`budget.token`**：LLM 两类素材的 token / 费用上限——因为不知道成本，先定上限还是先测成本再定？
3. **金句「分类需仲裁」**（素材层设计 §4.2）是否要设人工确认点（即 `human: true`）？
4. **溯源丢弃率的告警阈值**：丢多少条算任务不健康？（建议：>20% 触发告警）

### 实现中发现的三件事（都写进了代码注释与测试）

1. **`budget` 必须分两级**：`max_net_calls`（反爬配额，真正要控）与 `max_tool_calls`（防跑飞）。
   混成一个数会导致"为了省网络调用而不敢跑本地校验"这种荒唐取舍。
2. ★ **Windows 上不要用 `os.kill(pid, 0)` 探活** —— 那会**真的杀掉**目标进程
   （`TerminateProcess`）。单例锁改用 OS 文件锁，进程一死自动释放。
   且锁区固定在**字节 0**、持有者信息写在偏移 1 之后 —— 因为**读被锁区间会直接 PermissionError**。
3. **`@dataclass` + `importlib` 加载**：模块必须先注册进 `sys.modules`，否则
   `sys.modules.get(cls.__module__)` 为 None 会报错（项目其他测试的模块没用 dataclass，此前没踩到）。

> **为什么先写这两份契约**：`hotspot_track` 验证「已建任务能否装进 harness」，
> `material_extract` 验证「空白任务能否被契约描述清楚」——**两种都过，harness 的 schema 才算立住。**

> ✅ **已接线（2026-10-01 同日完成）**：调度器探测链**从 5 步收成 1 步**
> —— `agent_graph.py --run --thread probe-<15min 桶>`。
> 也就是说：**时钟驱动任务，不再自己拼脚本**；任务内部的流转交给图（LangGraph），
> 每步的可靠性交给 harness。详见 [热点追踪设计 §7.3](./热点追踪设计.md)。
>

> `interrupt ↔ 契约 human 字段` · `条件边/重试环 ↔ 契约 on_fail` · `thread_id ↔ 幂等键`。
