### 2.1 ★ 源抽象：为什么「先 TapTap 后 B站」这个分工有架构价值

既然要「先做一个源、后加一个源」，那**加第二个源的成本**就是架构质量的直接体现。

```
┌─────────────────────────────────────────────────────┐
│  Agent 层（只认统一模型，不认具体平台）               │
│   话题信号 · Thread · 变化率 —— 不含任何平台特有字段  │
└────────────────────┬────────────────────────────────┘
                     │
┌────────────────────┴────────────────────────────────┐
│  SourceAdapter 接口（每个源一个实现）                 │
└──┬──────────────────┬──────────────────┬────────────┘
   ↓                  ↓                  ↓
 TapTap             B站              未来源
 ✅ 已有 S1–S6+U1    ⚠️ 已有爬虫       ⬜ 只留接口位
 先做深              做好 TapTap 再接  加源 = 加一个类
```

**统一输出模型**（解决 §0.2 的「形态统一」问题）：

```python
TopicSignal:
    source: str          # "taptap" | "bilibili" | ...
    source_id: str       # 源内 id（topic_key / bvid / ...）
    title: str
    heat_norm: float     # 0–1，**源内归一**（同源可比）
    heat_raw: dict       # ★ 原始指标，**必须保留**
    captured_at: str
```

**为什么 `heat_raw` 必须保留**：B站的「投币」和 TapTap 的「点赞」不是一回事，
**抹平了就再也看不出平台特性**（比如 B站三连重、TapTap 轻点赞）。
归一化是为了**排序**，不是为了**替代原始值**。

#### ★ 跨源比较的口径：不比绝对值，只比相对位置与变化率

| ❌ 不要做 | ✅ 应该做 |
|---|---|
| 「B站 500 万播放 = TapTap 多少浏览？」 | 「它在 B站排第 3，**6 小时涨了 4 倍**」 |

**理由**：第一问是**无解**的（两个平台的播放/浏览计价逻辑、曝光机制完全不同），
硬换算只会把差异抹成噪声。而**「源内排名 + 变化率」是天然跨源可比的** ——
每个平台自己就是自己的基准线。

> 这个口径还有额外好处：**它和 `topic_tracker` 判状态用的是同一套思路**（判变化率不判绝对值）。
> **同一套方法论用两次** —— 是架构一致性，不是重复。

#### 为后续子 Agent / MCP 铺的路

| 用户提到的 | 本设计如何支撑 |
|---|---|
| **工具链** | `fetch_topics` / `fetch_threads` 天然是 tool 形状（有输入、有输出、可独立测试） |
| **子 Agent** | 每个源可升格为一个子 Agent（自己管采集节奏、自己的失败重试） |
| **Skill** | 加源的操作流程可打包成 Skill（改哪些文件、怎么验） |
| **MCP** | `SourceAdapter` 是 MCP server 的现成边界（一个 adapter = 一个 server 的 tool 集） |
| **Memory** | 每源的健康状态/最后采集时间 = 需要跨天记住的东西，与 `topic_tracker` 同库 |

> **一句话**：**源抽象不是为了好看，是为了让「加第二个源」变成「加一个类」而不是「改一遍 Agent」。**
> 用户说的「分工明确就好设计」，本质就是这个。

### 0.2 形态统一：不同源的数据归一到什么模型

| | |
|---|---|
| 问题 | TapTap 有 `moment_id` + 评论；B站是视频 + 弹幕；微博是博文 + 转发链；媒体是文章 |

## 3. 补充二：横向问题（贯穿四问，最容易被漏）

### H1 跨源对齐：同一个热点在不同源怎么认出是同一个

| | |
|---|---|
| 问题 | 「三角洲行动二周年」（TapTap 话题）vs「三角洲二周年」（B站标题）vs 微博话题标签 —— 是不是同一个热点？ |
| 为什么是定义性难点 | **认不出是一个，「全网」就只是「几个互不相干的池子」** —— 那不算全网追踪 |
| 现状 | ❌ 没做。`topic_tracker` 只在 **TapTap 内部**做字面归一（全半角/标点/话题标签） |
| 技术名 | cross-source entity resolution / event linking |
| 可用手段 | 别名库（`games/*.json`，**当前取不到词，要先修**）· 时间窗对齐 · 语义相似（需 LLM） |

> **如果只能补一个问题，就是这个。** 它直接决定"全网"是不是真做到。

### H2 验收指标：怎么知道追得好不好

| | |
|---|---|
| 三个指标 | **覆盖率**（发生的热点了，我们抓到多少）· **时效**（平均滞后多久）· **准确率**（判为热点的，多少是真热点） |
| 为什么必须有 | 没有这三个，「追踪做得怎么样」**永远说不清**，也无法改进 |
| 现状 | ❌ 完全没定义 |
| 难点 | 覆盖率要**知道分母**（全网到底发生了多少热点）—— 这本身就要先有"全网" |

**可操作的起步**：先做**时效**（最好测）。

**实测核对（2026-09-30）**：`topic_tracker` 的 `topic_state` 表**已有**两个时间戳字段
（`first_seen_at` / `state_changed_at`），机制上可算 —— **但当前 14 个话题的差值全是 0**，
因为只有 1 次采样（`first_seen_at == state_changed_at`）。

> ⚠️ **所以「现在就能算」这个说法要收窄**：**字段已具备、公式已明确，
> 但要等有 ≥2 次采样后才产生有意义的数字。**
> 换句话说：**时效指标本身不阻塞，阻塞它的是「采样频率」—— 与 H3 是同一个问题。**

### H3 成本与频率：多久采一次、采多少

| | |
|---|---|
| 冲突 | **及时性 ↑ 成本 ↑**：30 分钟一次 vs 6 小时一次，请求量差 12 倍 |
| 现状 | ❌ 没定（当前手动跑，等于频率 = 0） |
| 已设计 | 分层频率（心跳 30–60min / 深采 6h / 全量对齐每天 1–2 次）—— 但未实现 |
| 约束 | 反爬/限流、单机算力、无服务器（个人项目） |

## 5. 关键澄清：「提前预判」要拆成三类

用户问「能不能提前预判热点的产生」——**这个问题本身需要澄清**，
否则会承诺做不到的事（被追问「你怎么预测突发舆情」就答不上来）。

| | **① 有排期的热点** | **② 有前兆的热点** | **③ 突发热点** |
|---|---|---|---|
| 例子 | 版本更新 · 联动定档 · 周年庆 · 赛事 | 讨论苗头 · 外部话题外溢 | 事故 · 争议 · 竞品动作 |
| 时间特性 | **已知** | **已发生、未爆发** | **无前兆** |
| 该做什么 | **日历管理**（不是预测） | **早期信号检测** | **快速响应**（不是预判） |
| 技术栈 | 结构化排期库 | 高频采样 + 阈值 | 异常检测 + 预案 |
| 现状 | ❌ 需建排期库 | ⚠️ 状态机已有，缺高频采样 | ⚠️ `anomaly_lite` 有一半 |

**三条实际后果**：

1. **「预判」的准确范围 = ① + ②** —— ③ 只能做响应速度，不能做预测。
   **对外表述必须这么讲**（与 RAG/RLHF 的命名诚实性同源）。
2. **三类的技术栈完全不同**，不能混在一个方案里做。
3. **个人项目最该先做 ①** —— 最简单且立刻可用：知道 10 月 15 日更新，就能提前备素材。

## 5.1 三类的具体实现方案（用户 2026-09-30 补充）

### ① 排期 → 日历管理（含抓取公告）

> 用户：「排期确实是排期。排期的话，**日历管理**。
> 我觉得日历管理包括**抓取公告**啊之类的这种东西。
> 这些可以**交给职业监测**，或者说有工具啊、脚本工具，**给 agent 用**。」

**设计要点：抓公告是一个 tool，由 Agent 决定何时抓、抓什么。**（符合「真 tool」判据）

```
日历管理 = 排期库 + 公告抓取 tool + 提前提醒

排期库（结构化）
  ├ 来源：官方公告页抓取 + 人工补录
  ├ 字段：game / event_type / title / scheduled_at / confidence / source_url
  └ 用途：提前 N 天提醒「10/15 版本更新 → 该备素材了」

公告抓取 tool
  ├ 输入：game_profile（games/*.json）
  ├ 输出：候选排期事件（带原文链接）
  └ 降级：抓不到就只用人工库，不静默为空
```

**为什么它是三类预判里最该先做的**：
- **立刻可用**：知道排期就能提前准备，价值即刻兑现
- 它是**其他两类的基础**——有排期才能区分「这次爆是排期内的预期内，还是意外的」

> ⚠️ **2026-09-30 修正我自己的一个错误判断**：初版我写「① 不依赖 LLM（纯抓取 + 结构化）」。
> 用户指出：「**每个游戏的公告文字排版不一样**，用脚本提取可能不行，
> 这个地方可能就需要大模型输出 JSON 格式」——**用户是对的**。
>
> 准确的分工是：**「抓取」不依赖 LLM，但「解析」需要**。
> 各游戏公告排版千差万别，给每个站写正则是脆弱且不可维护的。

#### 实现记录（`11情报Agent/announcements.py`，51 测试）

**✅ 已实现**，端到端验证通过（含 LLM 挂掉时的降级路径）。

**四段链路，每段可独立降级**：

```
① 抓取 → 存原文（不做解析）        ← 不需要 LLM
② 解析 → LLM 输出 JSON            ← 需要 LLM
③ 校验 → schema 校验 + 失败重试     ← 防御
④ 入排期库 → 汇总「未来 N 天要发生什么」
```

**★ 核心是 JSON 可靠性（用户明确点出的问题：「保持不能报错」）**

LLM 输出的 JSON 典型失败模式：裹代码块 / 带前后解说 / 字段缺失 / 类型错 / 截断。

**四层防御**：

| 层 | 做法 |
|---|---|
| ① 请求侧 | `response_format={"type":"json_object"}` |
| ② 提取侧 | **宽容提取**：直接 loads → 剥 ```` ```json ```` → 取首个 `{` 到末个 `}` |
| ③ 校验侧 | 纯标准库手写 schema 校验，**返回具体错在哪**（否则重试没法让模型改对） |
| ④ 重试侧 | 校验失败 → **把错误信息喂回去**重试一次 → 仍失败标 `parse_failed` |

**★ 最重要的一条纪律：解析失败也不丢原文。**
`raw_text` 永远保留，`parse_status` 如实标注（`ok` / `failed` / `skipped` / `needs_ocr`）。
好处：换了模型或 prompt 之后可以**事后补解析**；人工也能直接看原文。

**实测（LLM 402 余额不足时）**：`parse_status=failed`，`degraded_reason=LLM 调用失败`，
**但原文完整入库（155 字）** —— 降级路径验证通过。

**关于「公告是图片」（用户提的第三点）**：

| 选项 | 判断 |
|---|---|
| OCR | ❌ **不做**。中文游戏术语 OCR 易错，**错了比没有更糟** |
| 找文字版替代源 | ✅ 优先（官网 / 平台官方账号） |
| 只存链接 + 标记 | ✅ **降级方案**：记 `needs_ocr=True`，人工可点开看，不假装解析成功 |

**其他设计要点**：

- **`evidence` 字段**：要求 LLM 从原文**逐字摘录**支持该事件的句子 → **可核对，不是模型编的**
- **`scheduled_at` 可为 null**：原文没写时间就填 null，**不许编造**
- **人工录入兜底**（`--manual-file`）：官网抓取要按站点适配，人工录入**立刻可用**
- 公告库落在 `data/raw/taptap/announcements/`（含原文，属**原始域**，已 gitignore）

**待办**：官网抓取源尚未接入（需要先确定可达的站点与提取方式）。
现在可用的是**人工录入 + 完整解析链路**。

#### ★★ 更好的公告源：TapTap 官方账号（2026-09-30 实测发现）

**背景**：用户指出「公众号公告常是图片，脚本不好解析」。对。
但紧接着发现了一条**更优的路径** —— 用户给出了鸣潮官方账号的 URL，实测后确认：

| | **TapTap 官方账号** ✅ | 微信公众号 ❌ |
|---|---|---|
| 内容形式 | **纯文字** | 常是图片 |
| 可程序化获取 | ✅ 有 `feed/v7/by-user` 接口 | ❌ 需登录态、无开放接口 |
| 官方身份标记 | ✅ `moment.is_official: true` | 无 |
| 公告正文字段 | ✅ `moment.topic.summary` | 需 OCR |

**实测证据（鸣潮，user_id=429475503）**：

```
moment.is_official = true
moment.author.user.name = "鸣潮"
moment.topic.title   = "《鸣潮》3.7版本PV | 镜锁妄世，心照红尘"
moment.topic.summary = "...《鸣潮》3.7版本「镜锁妄世，心照红尘」将于9月30日开启！..."
```

**含版本号 + 日期 = 正是排期信息**，而且是文字，不用 OCR。

**两个副产品**：

1. **反查官方账号的方法**（已验证）：扫社区流 `feed/v7/by-group`，
   捞 `is_official=true` 的帖子的 `author.user.id`。
   鸣潮用此法成功捞出 `429475503` —— 与人工确认的一致。
   ⚠️ 但**明日方舟扫 120 帖未命中**（其官方帖不一定出现在默认社区流里），
   这时需要人工从浏览器抓一次 `by-user` 请求。所以 `games/*.json` 里
   `official_account.user_id` **是可配的**，不靠自动发现。

### ③ 突发热点 → 快速响应（用户说想不到，这里给方案）

> 用户：「突发快速响应，快速响应的话，这个怎么做呢？**我确实一时间想不到比较好。**」

**核心认知：快速响应的瓶颈通常不在「发现」，而在「决定做什么」。**

突发事件来了，运营懵的往往不是"这事发生了"，而是"**我该干什么**"——
**那 15–30 分钟才是真正的损失**。

| | 发现（技术活） | 响应（组织活） |
|---|---|---|
| 靠什么 | 高频采样 + 异常检测 | **预案库 + 自动路由** |
| 能压缩到 | 30 分钟 ~ 1 小时 | **但发现快 ≠ 响应快** |
| 现状 | `anomaly_lite` 有一半 | ❌ 完全没有 |

**完整链路**：

```
突发发生
   ↓
① 高频采样发现异常（30min 粒度）+ anomaly_lite 判偏离
   ↓
② 快速评估严重性 ← 这一步复用已有资产（见下表）
   ↓
③ 匹配预案（争议 / 事故 / 竞品 / 塌房 …）
   ↓
④ 路由到责任人 + 拉起处置清单
```

**② 评估严重性复用四个现成的东西**（这是意外的收获）：

| 判断维度 | 复用哪个 | 已有输出 |
|---|---|---|
| 扩散多快 | `topic_tracker` 变化率 | 状态迁移 |
| 多少人在说 | `anomaly_lite` 近 4 窗检验 | delta / p 值 |
| **谁在说**（重度玩家？） | `risk_insight` | `high_hours_share_pp` |
| **像不像上次那个事** | **素材层的相似检索**（RAG） | 需批 2 |

> **最后一条是意外发现**：**「和历史事件比对」正好是 RAG 检索该干的活** ——
> 「这个场面像不像我们三个月前处理过的那个小事/大事」，
> 检索历史事件 + 当时的处置 → 给出参考。**素材层的向量检索在这里又派上用场。**

⚠️ **诚实边界（必须写清）**：真实的处置预案是**企业内部的流程资产**，
个人项目**拿不到**。所以可交付的是：

| 能做 | 不能做 |

## 5.2 采样策略：从「及时」的定义推导频率（2026-09-30 用户要求给理由）

> 用户的质疑：
> 「30分钟一次，一个小时两个小时 —— 其实这个设计来看并不太好。
> **这个及时有多及时呢？这都是个问题。**
> 你追踪一个小时够的指标，和两个小时这个有效指标，**为什么要这么设置？**
> 你为什么要采用这样子，是**有个理由的**，是**多方对比下来的**，
> 是有限制考虑、有成本考虑，或者说方案里面挑的最好，**各种约束下面它是最好的**。」

**说得对。原来那三个数字是我拍的，没给推导。下面补上。**

### Step 1 「及时」必须是可测量的定义

| 概念 | 定义 |
|---|---|
| 及时（不可测） | ❌ "热点出现后尽快知道"—— 多快算快？ |
| **及时（可测）** | ✅ **采样间隔 ≤ 热点特征时间 ÷ 2**（采样定理：要看见变化过程，采样频率须 ≥ 2× 信号频率） |

所以真正要测的是**热点特征时间**（讨论从一个话题出现到达峰需要多久）。

### Step 2 实测特征时间（用真实数据）

**方法**：取平台发现流的 74 条评论，计算「评论出现在帖子发布后多久」。

**结果（2026-09-30 实测）**：

| 指标 | 值 |
|---|---|
| **< 1 小时** | **29 条（39%）** |
| 1–6 小时 | 13 条（18%） |
| 6–24 小时 | 25 条（34%） |
| 1–3 天 | 7 条（9%） |
| p25 / 中位数 / p75 | **24 分钟** / 2.6 小时 / 16.2 小时 |

> **关键结论：讨论的爆发是「小时级」而非「天级」—— 四成评论在头一小时内就发生了。**

⚠️ **样本的诚实说明**：74 条、且是 top-N 评论（非全量），有偏。
但它给出的量级判断是可靠的（**小时级**这个结论不会因为偏差而变成天级）。
**要精确校准，需要 `topic_tracker` 跑几天的多采样数据。**

### Step 3 约束分析（关键是分清哪些是**真**约束）

| 约束 | 方向 | 数值/估计 | 是真约束？ |
|---|---|---|---|
| **信号特征时间** | 下界（不能太慢） | 24min ~ 2.6h | ✅ **是** |
| **反爬 / 限流** | 上界（不能太快） | 未知，需实测 | ✅ **是** |
| 请求成本 | — | 探测仅 1 请求/次 → 15min 也才 96 次/天 | ❌ **不是** |
| 算力 | — | 单次探测 = 读 JSON + 写 14 行，秒级 | ❌ **不是** |
| 存储 | — | 约 1300 行/天 | ❌ **不是** |

> **★ 这是本次推导最重要的发现：成本、算力、存储都不是约束。**
> 我把它们当成约束来"省"，是错的。**探测一次只要 1 个请求——
> 为省 48 个请求/天而牺牲及时性，是错误的取舍。**
>
> **真正的约束只有两个：信号特征时间（下界）与反爬（上界）。**
> 而**深采层才需要省**（每话题十余个请求），所以自适应该用在深采，不是探测。

### Step 4 结论

```
特征时间（p25）24min  ÷  2  =  12min   ← 理论下界
特征时间（中位）2.6h  ÷  2  =  1.3h    ← 宽松下界

所以合理区间：12min ~ 30min
   · 30min = 刚好卡在「能看见」的边界
   · 15min = 有余量的选择  ← 起步值
   · 12min 以下没有收益（信号本身没那么快变）
上界由反爬决定，需实测。
```

**定案**：**探测层起步 15 分钟**，跑几天观察：
1. 是否触发限流（决定上界）
2. 实际变化率分布（决定下界是否可放宽）

**不是拍的，是推的**；且留了校准路径。

### 采样策略表（两级分离）

| 对象 | 触发条件 | 探测频率 | 深采 |
|---|---|---|---|
| **热榜列表（全景）** | 定时 | **固定 15min** | 不深采 |
| 冒头话题 | 新进榜 或 可发酵度 act | 15min | 轻量（只标题） |
| **升温 / 爆发** | 状态迁移 | 15min | **全量 + 高频** |
| 退潮话题 | 状态迁移 | 6h | 停 |
| 沉寂话题 | 72h 无变化 | 归档 | 停 |

**为什么探测层频率固定、不随热度变**：

> ⚠️ **如果按「当前热度」决定频率，会漏掉冷启动** ——
> 话题现在不热 → 低频采 → 看不见它升温 → 等看见时已错过窗口。
> **而早期信号检测的全部意义，恰恰是在它还冷的时候看见它变热。**
> 这是观察者悖论：**要靠采样判断热度，但频率又依赖热度判断。**

**自适应该用什么判据？—— 用「可发酵度」，不是「当前热度」**：

| 判据 | 会不会漏冷启动 | 可用性 |
|---|---|---|
| 当前热度 | ❌ 会（悖论） | — |
| **可发酵度**（`ferment_judge`） | ✅ **不会** —— 它判的是「有没有讨论动机」，不是「现在热不热」 | ✅ 已有 |

**所以：冷话题只要可发酵度高，照样进高频通道。** 这既实现了用户想要的"差异化"，
又避开了悖论。

**★ 最重要的实现决策：调度器自己收集校准自己的数据**

### 7.1 事件流实现记录（`11情报Agent/events.py`，32 测试）—— 触发链接通

**补的断点**：之前 `topic_tracker` 判出状态迁移后**只改了当前状态字段**——
「何时从什么变成了什么」这段历史没人记，更没人触发下游。这是验收项 C1「触发链未接通」。

**链路**：

    topic_state（当前状态）
      ↓ emit_transitions()   扫出新迁移，生成事件（幂等去重）
    topic_event（事件表，Memory —— 迁移历史不可重建）
      ↓ dispatch_pending()   分发给订阅者（各自独立失败隔离）
    stdout（兜底）· 事件流报告 · 未来的推送

**两条硬纪律**：

| 纪律 | 实现 |
|---|---|
| **幂等** | `event_id = hash(topic_key + to_state + occurred_at)`，**三个输入全来自上游**（迁移时刻用上游的 `state_changed_at`，不掺扫描时刻）→ 重跑不会重复触发 |
| **失败隔离** | 每个订阅者独立 try/except；分发后**不论成败都标记**（否则失败的永远卡在队列被反复重发） |

**分发门槛**（沿用交付形态设计 §3.2）：只有**爆发/升温**主动分发；
冒头/退潮/沉寂**只记录不打扰**。

**已接入调度器**：探测链从 3 步变 **4 步**
（拉热榜 → facts → 采样判迁移 → **触发链：迁移→事件→分发**）。

**端到端验证**（构造「升温→爆发」迁移）：
第 1 次运行产生 1 事件、分发 1 次（stdout 打出 🔴）；
第 2 次运行 **0 新增 0 分发** —— 幂等成立。

**订阅者可插拔**：`default_subscribers()` 现在只有 stdout + 事件流报告；
**推送（企微/飞书）接入时在这里加一项即可，本模块不用改** ——
这是「触发链」与「交付层」的解耦点。

**当前真实事件数：0** —— 状态机还没判出过真迁移（首日全冒头，`prev_state=null` 不算迁移）。
采样积累后这里会自动开始记录。

**用法**：

    python 11情报Agent/events.py --run      # 扫迁移 + 分发（调度器每轮自动调）
    python 11情报Agent/events.py --status   # 事件流状态

### 7.3 巡检图实现记录（`11情报Agent/agent_graph.py`，13 测试）—— ③ 控制层动工

**这是「agent harness + LangGraph 框架」两个词的合流点。** 二者不是两件事，是同一件事的两面：

| | 管什么 |
|---|---|
| **LangGraph** | **怎么流转**：节点 / 条件边 / 重试环 / checkpointer / interrupt |
| **harness**（§见任务契约） | **每一步怎么靠谱地跑**：参数校验 / 预算 / 幂等 / 产出契约判定 / 失败分派 / 轨迹 |

**图的节点体 = harness 的一步**。对应关系（一一对应，不是类比）：

| LangGraph 机制 | harness 里的对应物 |
|---|---|
| `State`（TypedDict） | facts（锁数纪律：原始文本禁入 State） |
| `checkpointer` | 轨迹（每步 attempt/耗时/成败/产物，可回放） |
| `interrupt` | 契约的 `human` 字段（高危闸门） |
| 条件边 + 重试环 | 契约的 `on_fail`（retry/degrade/reject/abort） |
| `thread_id` | 契约的 `idempotency_key`（同窗口不重跑） |

**★ 2026-10-01 升级：图已**契约驱动** —— 节点由 `契约["tools"]` 生成，同一张图能跑任何任务。**
（原来节点写死为 crawl/sense/act，只服务热点追踪；现在 `hotspot_track` 生成

质检闸门也随之改为**复用首工具的产出契约**（不再写死行数）。

**图结构（可核对）**：

```
START → tick → crawl → qc ─┬→ sense ─┬→ gate → act → finish → END
                     ↑     ├→ crawl  ←┘（重试环，有界）      ↑
                     └─────┘  └→ mark_degraded ─────────────┘
```

- `qc → crawl` 是**有界重试环**（上限 2 轮），超限走 `mark_degraded` 继续 —— 对应设计里

  这是锁数纪律在**框架层**的落地（不靠提示词约束）。

`llm_classify` 未实现 → 其 `unavailable_class="llm"` → 走契约 `llm: degrade`
→ **任务判 ok、只标注缺哪两类**，而不是整任务失败。此前未实现工具一律 `abort`，会把「无 key」
误判成任务失败 —— 这不符合契约，已修（并加测试：契约没声明 llm 策略时兜底 `abort`，不擅自降级）。

### 7.3.1 无窗口运行（并入 `harness.py` **执行层**）—— 2026-10-01 用户反馈「时钟脚本时不时弹出来」

**根因**：计划任务用 `python.exe`（**控制台子系统**）→ Windows 为它分配控制台 → **每 5 分钟弹一次窗**，
而其中 3/4 的唤起被 `probe_log` 节流空跑。

**★ 关键：两半必须同时改，只改一半会更糟**

| 改动 | 作用 | 只做这一半会怎样 |
|---|---|---|
| 任务改跑 `pythonw.exe`（GUI 子系统） | 自身不分配控制台 → 不弹窗 | **更糟**：pythonw 无控制台可继承，它 spawn 的每个子进程都会被**新建控制台** → 一轮探测 6 个子进程 = 6 次弹窗 |
| 子进程加 `CREATE_NO_WINDOW` | 子进程不新建窗口 | 自身仍弹窗（治标不到本） |
| 入口补标准流兜底 | pythonw 下 `sys.stdout` 为 **None**，任何 `print()` 抛 `AttributeError` | 调度器**每轮静默崩**（崩溃信息也没地方打印） |

**实现（★ 2026-10-01 归位：这块属于执行层，所以并进 harness，不做平行模块）**

用户原话：「**这种应该放进 agent harness 里面**」—— 说对了。「怎么起进程」就是执行层的职责，
而执行层 = harness；平台适配不该是被三处 import 的平行模块。

顺带发现并消除了一处**真实重复**：`scheduler.run_step` 与 `harness.run_tool_call`
**各写了一份子进程调用**（编码注入、超时、降级）。现收敛为 **harness 的单一出口**：

| 归属 | 内容 |
|---|---|
| `harness.exec_command()` | **执行层唯一子进程出口**：编码注入 + `CREATE_NO_WINDOW` + 超时（结构化失败，不抛）+ 失败分类 |
| `harness.no_window_kwargs()` | 给 subprocess 展开的 `creationflags`（非 Windows 返回空 dict） |
| `harness.ensure_std_streams()` | 标准流缺失时接到 `state/console.log`（有控制台时**不动**）；超限自动轮转 `.1` |
| `scheduler.run_step()` | 退化为**薄适配层**：只负责报告降级，不再自己 `subprocess.run` |

**架构不变量（有测试防止再分裂）**：调度器源码里**不许**出现 `subprocess.run(` 与 `PYTHONIOENCODING`。

**实测验证**（不是推断）：用 `Start-Process -WindowStyle Hidden` 起 `pythonw.exe` 跑调度器 ——
该场景下 `sys.stdout` 确实是 `None`；补兜底后输出落到 `state/console.log`，退出码 **0**、`[done] ok=True`。

**★ 止血方案：进程可以自己隐藏控制台（`suppress_console()`，不需改系统设置）**

命令安全策略一度禁止 `schtasks.exe`（改不了任务），所以补了一条不依赖系统设置的路径：
`python.exe` 启动时那个控制台**在计划任务场景下只属于本进程**，进程可以自己 `ShowWindow(SW_HIDE)` 藏掉。

⚠️ **安全前提（否则会隐掉用户的终端）**：必须先判「控制台是否为本进程所有」——
`GetConsoleProcessList` 只有自己才算独占。从终端/IDE 启动时是继承来的共享控制台 → **一律不动**。
（实测：本环境派生进程无控制台 → `suppress_console()` 返回 `False`，什么都没动 ✅）

⚠️ **诚实边界**：从进程启动到执行到该函数之间仍会**短暂闪现**（约 0.1–0.3s）。
   要**彻底**不闪，仍须让任务改跑 `pythonw.exe`。**pythonw 是根治，自隐是止血，两条不冲突。**

**✅ 2026-10-01 已重新注册（沙箱解除后由 agent 完成）**：

    powershell -ExecutionPolicy Bypass -File scripts/register_scheduler_task.ps1

任务 `ArkIntelScheduler` 的 `<Command>` 已从 `python.exe` 改为 **`pythonw.exe`**（可用
`schtasks /query /tn ArkIntelScheduler /xml` 核对），并通过**手动触发**做了端到端验证：
无控制台启动 → 输出落 `state/console.log` → 探测链跑图（`graph_run ok=True 步数 5`）→ 探测日志新增 `ok=1`。
