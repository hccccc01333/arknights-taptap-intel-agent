# TapTap 全网热点情报 Agent：重构实施方案

更新：2026-10-07。根据用户确认的目标图片及本轮代码、数据库、接口核查制定。

## 目标与边界

目标是「全网热点追踪：构建 AI 自动化情报与素材系统，通过热点识别产出与 TapTap 相关的实际增长创意」。旧目录名已经作废，不以单游戏舆情平台作为产品目标。

用户已授权重构核心及必要时全部重构。已有未提交修改、数据和采集配置保留；文件删除仍需列明文件并获得批准，逐个执行。

Agent 的业务任务是持续发现、补采、理解、跟踪、判断关联、整理素材并产出运营创意。日报和周报是这项工作的交付形式。创意的实际发布、授权获取与真实增长验证需要与具体业务资源对接，不能由模型声称已经完成。

## 已核查的基线

本轮核查时，外部热点快照生成于 10 月 7 日，L1 注册库及 L2 清洗库的最新观察截至 10 月 6 日，L3 活跃趋势事件采用的最新观察截至 10 月 4 日，社区报告生成于 10 月 5 日。采集文件更新、入库、趋势分析和报告生成没有表现为同一条同步的数据链。

L2 库有 5,899 条记录，L3 有 182 个活跃事件；这些数量不能证明热点识别有效。当前 L4 `intelligence_analysis` 表没有分析记录，但另一路 JSON 存有增长创意，说明必须核查两条产出路径，不能把其中一条的状态当作整个系统状态。

前端最新入口使用 `FieldStudio`。研究、策划和员工行动体验主要在前端及本地存储完成，读取已有 API 快照不会触发新的模型研究。现有巡检图负责有界重试和脚本执行；它提供运行基础，但不等于已完成业务研究 Agent。

这些是当前运行态的核查结果，后续运行可能变化。水位来自现存数据，不能单独推断某个任务从未运行，也不能证明全网覆盖。

## 重构原则

1. 先交付一条可验收的业务链，再扩展平台和交互。
2. 采集器按实际采集成功率复用；框架和代码量不作为保留依据。
3. Agent 调用工具查证内容、追踪事件并决定下一步。确定性的去重、计数、时间计算和约束检查仍由代码执行。
4. 原文通过证据工具提供给模型；事件标识、来源、快照时间、引用和计算指标持久保存，保证能复查。
5. 失败必须可见。规则候选、模型判断、人工修订和缺失数据分别记录，模型不可用不能冒充研究成功。
6. 保留已有数据，采用新增结构和显式切换，避免以运行新链为由覆写旧结果。

## 唯一业务主链

### 一、采集与证据

先接通实际可获取的 B 站、微博、游戏媒体和 TapTap 数据，逐渠道核查请求成功、原文可用、发布时间、重复率和样本偏差。平台名称不是覆盖证明；不可用的平台明确说明。

统一保存原始平台、原始内容标识、原文链接、标题、正文或可读摘录、发布时间、观察时间及互动快照。搜索命中只是发现线索，不能当作新增独立讨论量。官方身份来自来源结构信息，不能因正文出现「官方」就升级证据层级。

### 二、业务研究 Agent

输入是业务目标、候选线索、当前事件档案和工具结果。Agent 可以读取趋势与来源健康、搜索补充材料、读取原文与评论、对比旧快照、提出关联判断及生成创意。

每轮保存所用模型、提示版本、工具调用、证据标识、决策和结束原因。按轮设置请求、时间和模型预算。证据不足时补采；工具失败时结束为待补充；达到预算时保留进度。重新运行可接续已有档案。

调度器负责何时唤醒和避免重入，业务 Agent 负责查什么及值不值得继续。工具完成不自动等于业务目标完成。

### 三、热点发现与事件跟踪

按真实事件组织内容，以主体、动作、时间和上下文判定是否同一件事。事件使用稳定标识；「明日方舟」「联动」等词只是实体或主题，不直接等同于一个事件。

候选发现结合新内容、历史基线、互动快照变化与跨渠道线索。模型参与阅读原文、命名事件、区分诉求和判断关联；不让模型编造讨论量、增长率或传播链。

新进榜、新搜索结果及回帖量变化分别解释。没有足够历史快照时，状态为数据不足；不能画出推测的增长曲线。热点升温、持续、降温及再活跃都需要保存变化依据。

### 四、TapTap 关联与增长创意

关联判断必须说明：触及哪些用户、用户有什么诉求、TapTap 能提供什么价值、站内有哪些实际承接方式。覆盖直接游戏话题，也允许有证据支持的玩家文化与可迁移玩法候选；不因游戏词命中就判定值得行动。

先查明可用资源和时效，再生成创意。每条交付至少包括热点依据、目标人群、承接位置、用户动作、执行步骤、文案或素材提案、素材来源、授权状态、交付时间、风险和验证办法。

建议指标依据真实业务目标。没有历史基线时不编增长承诺。没有适配的创意时明确说明原因，而不是凑固定条数。

### 五、情报与素材交付

日报说明新增事件、已有事件变化、值得行动的机会、待补采线索及数据缺口。周报对比本期与上期的已保存观察，说明事件演变和判断变化；没有历史数据时先积累，不拼接快照冒充周趋势。

重要结论引用具体证据，并区分事实、推断与未知。素材先完成来源收集与可用性核查；涉及作品使用条件时保留授权状态，不把下载链接当作可用授权。

首版界面围绕候选热点、事件详情、增长创意和运行状态组织。现有研究空间及工作台保留，待主链可靠后决定如何连接。

## 实施顺序及验收

第一阶段：接通真实采集到标准证据、增量处理和事件档案。用同一内容重复采集、内容更新和渠道失败三个场景验证，证明不重复制造内容、不丢观察变化、不隐藏失败。

第二阶段：接入 Agent 的补采和查证决策。用真实原文评估误合并、漏发现和关联误判，形成有版本的标注样本及回归用例。测试框架通过不代替业务效果验收；没有标注基线时不报准确率。

第三阶段：交付可复查的增长创意与素材清单。按证据、TapTap 承接能力、时间窗口和资源约束逐条验收；先跑通一条真实候选到完整交付，再扩大规模。

第四阶段：自动运行、持续事件跟踪、日报周报及失败恢复。保存历史后验证跨日变化；用模型不可用、平台失败和中途重启验证不会生成假成功或覆盖已有研究。

## 本轮已实现的范围

新增 `runtime/pipeline_health.py`，只读检查六类现存输入和产物，区分缺失、过期、空库、损坏、未知时间和未来时间戳。默认 60 分钟为未校准的检查阈值，CLI 可调整。这个阈值不是热点判定规则。

新增登录保护的 `/api/pipeline-health` 接口，现有社区报告和 Universe 接口同时携带状态。经典报告页及 React 实时模式提示滞后输入；点击刷新不会改变实际数据水位。

本轮补丁只是接手后的诊断基础。核心 Agent 业务重构、数据主链接通、热点语义识别和自动创意交付仍属于待实施阶段，不能标作已经完成。
