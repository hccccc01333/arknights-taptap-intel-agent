>
> **方向**：本项目改为 **Agent 项目**。

> **目标**：**服务游戏社区，完成全网热点追踪 —— 构建 AI 自动化情报与素材系统，通过热点识别产出与 TapTap 相关的实际增长创意。**

>
> | | 游戏厂商视角（❌ 不是本项目的） | **社区平台视角（✅ 本项目的）** |
> |---|---|---|

> | 创意 = | 游戏内活动 / 商业化 | **社区侧运营动作：建什么话题、引导什么讨论、做什么活动** |

>
> 目标拆解为三层，与架构一一对应：
>
> | 层 | 目标短语 | 架构含义 |
> |---|---|---|

## 0.5 为什么需要 Agent：不可替代性在哪（2026-09-29 论证）

> 用户质疑：「我们这个项目设计 Agent 的意义是什么？这是决定如何设计 Agent 的前提。」
> 这是最该先回答的问题——**答不上来，v2 就只是用 LangGraph 重写一遍 cron**。

### 最尖锐的质疑

> **输入固定、处理固定、输出固定 —— 那用 crontab + Python 脚本不就完了？Agent 是不是纯装饰？**

按 v1 现状，**这个质疑是对的**：每天同一批数据、跑同样 6 个模块、出模板简报。用 cron 完全够。必须先找到**流水线做不到、而 Agent 能做**的事，否则整个 v2 没有正当性。

### 答案：在「相关性不确定」的下钻链上做选择性投入

项目的数据面有一条**天然下钻链**：

```
S4 话题热榜（10 个） → S6 话题下帖子（每话题 8-10 帖） → S3 帖子评论（每帖 1 次调用）
```

这条链的三个特性，合起来恰好是流水线解决不了的：

| 特性 | 实测证据 | 为什么流水线不行 |
|---|---|---|
| **① 相关性非字面** | 「星布谷地联动宇树科技」「游戏十年纪录片理想的存档上线」「妮姬新生庆典送 185 抽」——**从话题名字面看不出是什么游戏** | 别名库匹配 **0/6 命中**（§1.1 损失表第 4 条）。这是规则应对不了非字面映射的**直接证据** |
| **② 下钻有真实成本** | 全量下钻 ≈ 129 次调用；只深挖 2 个话题 ≈ 51 次（**2.5×**） | 要么全挖（浪费）要么不挖（漏）——流水线只能二选一，没有中间态 |
| **③ 控制流依赖运行时内容** | 看到 S4 之前不知道该挖哪个；看了 S6 才知道要不要继续挖 S3 | **流水线的控制流是写死的，而这条链的控制流要读到上一层才能决定**——这是唯一一个「非 Agent 不可」的点 |

**③ 是核心**：前两条（省调用、提高召回）优化一下也许能凑合，但**「下一步做什么取决于上一步看到了什么」**这件事，本质是运行时的条件分支，无法预先编码。这就是 Agent 不可替代的地方。

### 由此得到的 Agent 定位

> **Agent 不是「跑分析的人」，是「决定把有限的下钻预算花在哪的人」。**

对应到能力要求（也解释了 v1 为什么不算 Agent）：

| 能力 | v1 现状 | v2 需要 |
|---|---|---|
| 语义相关性判断 | 别名库规则（0/6） | **交给 LLM**——非字面映射正是它的强项 |
| 选择性下钻 | 无（要么全要么不） | Agent 决定挖哪 2 个话题 |
| 循环追查 | 0 轮 | 挖完 S6 再判断是否继续挖 S3（§6 议题 1） |

⚠ **这也顺带回答了 §6 议题 9**（平台事件要不要触发 deep_dive）：**要，而且判断权应该给 LLM**——因为规则已经用 0/6 证明它做不到语义匹配。只不过在拍板前仍需先排除「这批数据本就与两款游戏无关」的可能（见 §1.1）。

### 一句话

**如果项目的产出固定、路径固定，那确实不需要 Agent。**
**本项目的不可替代性，在于那条「下一层值不值得挖，要看了这一层才知道」的下钻链——而这恰好是我们 S4/S5/S6/U1 四个通道刚铺出来的能力。** 换句话说：**先有了下钻链，Agent 才有意义；v1 的意义不足，是因为链刚铺好、还没接上。**

用户提出「V4.1-Flash 性能大于 V4-Pro」。**查证后：方向对，但不完全；而且真正的结论不是换模型，是换维度。**

| Automation-Bench | 54.8 | 43.2 | Flash |
| Codeforces (rating) | 3471 | 3348 | Flash |

**② 但 V4-Pro 在「知识密集型」上仍领先，而这部分恰好是创意生成要用的**：

| Benchmark | V4.1-Flash | V4-Pro | 赢家 |
|---|---|---|---|
| SimpleQA-Verified（事实召回） | 42.3 | **55.2** | Pro |

**④ 真正的分层维度是 thinking 的开关与档位**（V4.1-Flash 默认开 thinking，且思维链 token 按 output 计费）：

| 任务 | 配置 | 理由 |

## 1. 系统分层（四层）

```
① 数据层      游戏档案 games/*.json · TapTap 评论接口 · 对照渠道
              社区五通道（2026-09-28 抓包验证）：
                S1 group/v1/recommend            全平台社区地图（关注/帖子量/活跃/官方声量，from 翻页）
                S2 feed/v7/by-group              单游戏社区帖子流（正文+互动数+内嵌热评，group_id+from）
                S3 moment-comment/v1/by-moment   帖子评论流（moment_id）
                S4 hashtag/v2/hot-hashtags       全站话题热榜（事件话题，如「星布谷地联动宇树科技」）
                S5 discover-categories/v2/feed-list  发现页跨游戏内容流（帖子+来源游戏+next_page）
                S6 feed/v7/by-hashtag            话题下帖子流（hashtag_id 翻页）——S4→S6 深挖链路
                                                 （2026-09-29 补：热榜只能看到话题名，
                                                   真正读玩家情绪要下钻到话题下的帖子+评论）
                U1 feed/v7/by-user               用户社区足迹（user_id 翻页，limit 上限 10）
                                                 ——「用户流动」数据源：一个人在哪些游戏发过帖、按时间序
② 管线层      采集(--game/--data-dir/--source) → 清洗 → LLM标注(两段式) → 分析实验室
              （两个游戏共用同一套代码；原始数据含 PII 不入 Git）
              数据面按**归属**分三类目录，避免口径串味：
                02数据_<game>/            单游戏评分区（reviews）
                02数据_<game>/community/  单游戏社区（S1/S2/S3）
                02数据_platform/          平台级发现流（S4/S5/S6，不归属单一游戏）
③ Agent 层    LangGraph 两段式控制面（见 §2）——v2 核心
④ 支撑层      工具箱 / 跨日记忆 / 执行轨迹 / DeepSeek(可选)
```

**定位校准（用户决策）**：项目面向**游戏社区公司**（TapTap 即是）——数据面不只评分区评论（S2 的评分评论），而是 **S1–S6 + U1** 全量社区数据：平台地图、话题热榜、社区帖子流、用户足迹。Agent 感知范围对应扩展为平台级巡检（S4 话题热榜 → 事件检测 → S6 话题下钻 / S5 深挖）与用户级流动（U1）。

关键原则：**Agent 不重写管线，而是坐在管线之上**——管线脚本降级为 Agent 可调用的幂等工具；LLM 全程拿不到原始数字，只能引用 facts 与工具返回（锁数纪律从 v1 延续）。

## 1.1 已完成部分在四层架构中的位置（截至 2026-09-29）

> ⚠️ **2026-10-01 更新**：本文其余部分仍是 09-29 快照，但 ③ 控制层**已动工** ——
> **第一段「数据运维编排」的巡检图已实现并真跑通过**（LangGraph，8 节点 + 有界重试环 +
> checkpointer 跨进程恢复 + interrupt 人工点），且**调度器探测链已从 5 步收成 1 步**（时钟驱动任务，
> 不再自己拼脚本）。详见 [热点追踪设计 §7.3](./热点追踪设计.md) 与 [任务契约](./任务契约.md)。
> 因此「③ 只加了一处消费侧接线、控制逻辑一行未改」这句**已过期**；
> 但仍**没有**模型驱动的工具选择循环，所以尚不构成行业语义的「Agent harness」。

**一句话定位：已完成的工作落在 ①数据层、②管线层（= v2 的 tool 层）和 ④支撑层；③ Agent 控制层只加了一处「消费侧接线」，控制逻辑一行未改。**

换个更直白的说法：**我们做厚的是「Agent 手里的工具」和「工具喂给它的 facts」，不是「Agent 本身」**。

也就是说，现状是「**感知面已经铺到平台级与用户级，控制面还是 v1 固定流水线**」。v2 的 LangGraph 化不是补功能，而是**替换控制层**——下面这些模块届时原样变成图里的工具与 facts 来源。

关于 ③ 的精确口径（避免两种误读）：`daily_agent.py` 确实被改过，但 `git diff --stat` 是 **83 行新增 / 0 行删除**——纯增量。新增的是 `load_platform()`（读平台 facts）与简报里的一段渲染，既有决策规则、路由、显著性判定**一行没动**。
所以准确表述是：**碰了控制层的消费侧 wiring，没碰控制逻辑**（没有自主循环、没有记忆、没有 interrupt）。

```

                     已消费下方全部 facts，但**它是 v2 要替换的对象，不是 v2 的一部分**
        ▲ 只读 facts、只调工具（锁数纪律：LLM 看不见原始数字）
```

### ② 里的两类东西：**真 tool** vs **pipeline stage**（2026-09-29 纠正）

> ⚠ 本节是对上一版「tool 层里的两种东西」的**自我纠正**。上一版把两者并列叫 tool，是**归类错误**。
> 用户质疑：「Agent 调 tool 拿到加工过的数据，严格说返回的是一个模块的数据」——**这个质疑成立**。

**tool 的判据只有一个：Agent 是否拥有「要不要调、调几次、传什么参」的决策权。** 按此实测：

| 类别 | 成员 | 实测调用关系 | 判定 |
|---|---|---|---|
| **采集类** | `crawl_taptap_reviews / community / discovery / user` | **Agent 从未调用**——人工跑 CLI，Agent 只读 CSV | ❌ v1 里还不是 tool（v2 计划包成 tool） |
| **感知类（被调的）** | `risk_insight` / `anomaly_lite` | `perceive()` 里 `run_tool()` subprocess 调用，但**无条件必跑**（仅 `skip_anomaly` 一个开关） | ⚠ 是 **pipeline stage**，不是 tool——Agent 没有「跑不跑」的决策权 |
| **感知类（只读的）** | `platform_insight` / `user_flow` / `community_insight` / `cross_game_compare` | **连调用都没有**，只 `load_*()` 读 JSON 产物 | ❌ 就是**独立模块的输出**，Agent 读文件而已 |

**结论：v1 里一个真正的 tool 都没有。** 感知类产出的不是「tool 的返回值」，而是**一个模块的输出 / state 的一个字段**——正是用户所指出的那样。v2 的价值之一就是把采集类真正包成 tool，把必跑的感知类显式建模为 stage。

后者是本项目最值得讲的一条设计：**facts 是 LLM 与数据之间唯一的界面**。LLM 全程拿不到原始数字，只能引用 facts——锁数纪律靠这个界面落地，而不是靠提示词约束。

### ★「原始文本不进 State」到底是什么意思（2026-10-01 用户追问）

> 用户质疑：「原始文本不进 State，那怎么保证信息？追踪热点 / 情报 / 素材 / 创意增长
> **这些都是需要文本的**。摆脱了原始文本，我们怎么做这些呢？这个问题你考虑过了没有？」

**先纠正一个隐含前提：这条纪律不是「系统不碰文本」，而是「State 里不放原文」。**
原文当然要用——它只是**必须落盘 + 靠 id 寻址**，而不是被搬进图的 State。

**三层分离**（这是纪律的另一半，此前只写在代码注释里，未成文）：

| 层 | 放什么 | 在哪 | 是否进 State |
|---|---|---|---|
| **原文层** | 帖 / 评全文、Thread（帖 + 评论束） | `02数据_platform/*.csv`、`materials.jsonl` | ❌ 不进 |
| **facts 层** | 数字、判定量、**短标识**（标题 ~13 字） | 各 `outputs/*.json`；State 只搬判定量 | ✅ 进 |
| **产物层** | 引文 / 素材卡片 / 简报（**必须带溯源**） | `materials.jsonl`、`reports/*.md` | ❌ 不进 |

**你点名的四件事，逐个对照**（四个都要读，区别在读多少）：

> ⚠️ **2026-10-01 二次修正（用户追问「这四个还是要原文的，不然就是盲目的」）**：
> 上一版本表把「追踪热点」写成「不需要原文」，**这是错的**。准确说法见下方「文本在哪被读」。
> 结论先行：**四个任务都要读文本** —— 区别只在**读多少**与**谁读**，不在读不读。
> **只看数字必然是盲目的**，本项目自己撞过这堵墙：`ferment_judge` 的旧判据（游戏归属字面匹配）
> 命中 **0/10**，改用语义判断后 **5/10** 可发酵 —— 见 §1.2。

| 任务 | 读文本吗 | 说明 |
|---|---|---|
| **追踪热点** | ★ **要**（读标题） | **发现**靠数字（变化率），**判断靠读**——「这热点值不值得做」需读标题（`ferment_judge`） |
| **情报简报** | ★ **要**（读摘要） | 纯数字简报不可读；要说明"发生了什么"就必须读摘要，引例还要带原文引用 |
| **素材获取** | ★★ **要**（读 Thread 全文） | 判"梗 / 段子"必须读评论原文与语境（素材层 §4.3） |
| **创意生成** | ★ **要**（读素材） | 不懂这个梗，就写不出能用的创意角度 |

### 文本在哪被读（这才是纪律的正解）

**问题从来不是「要不要文本」，而是「在哪读、读多少、读完回传什么」。**

| 阶段 | 读多少 | 谁读 | 回传什么 |
|---|---|---|---|
| **发现** | 不读 | 代码 | 数字（变化率/斜率） |
| **判断** | **短文本**（标题 / 摘要 ~90 字） | 代码 + **LLM** | 结论（`ferment_score` / 相关性），**带 source id** |
| **加工** | **长文本**（Thread 全文） | **LLM**（工具调用内部） | 产物（素材卡片 / 创意角度）落文件，State 只留 id |

所以「原文不进 State」的**准确表述**应该是：

> **原文不做图的长期记忆；需要时按 id 检索、作为那一次调用的临时输入，用完只留结论（且结论必须带 id 可回查）。**

这正好落在素材层 §3.5.6 的**非问答式 RAG** 上：
**retrieve = 按话题取 Thread**，取到的文本进 prompt、用完即弃，**不进 State**。

★ **由此推出一条硬要求**：既然文本"用完即弃"，那么**结论必须带 source id**，
否则事后无法回放"当时 LLM 究竟看到了什么"——轨迹就失去可复查性。
这条与「轨迹回放」是同一件事的两面。

> **机制一句话：引用而非搬运（reference, not copy）。**
> 原文只落一次、有稳定 id；任何引用都带 source pointer。
> 这正是素材层设计 §3.5.6 说的**非问答式 RAG**：query 是热点信号、corpus 是 Thread 池、
> **检索单元是 Thread（保住语境）**，而不是把全库文本塞进上下文。

**信息不丢靠四条，不靠把文本塞进 State**：

1. **落盘唯一性**：原文只落一次，id 稳定（`moment_id` / `comment_id`）
2. **可寻址**：fact / 素材 / 引文都带 source pointer（溯源链实测 **100% 可关联**，素材层设计 §2.1）
3. **准入闸门**：素材「没有溯源就不算素材」（`assert_traceable` 代码层强制）
4. **存 Thread 不存孤立评论**：保住评论所处语境，否则「损失的语境，还能叫素材吗」

⚠️ **诚实边界（必须写清，否则这条纪律会被当成万能钥匙）**：

- State 守卫（`agent_graph.assert_state_clean`）是**体积闸门，不是语义闸门**：
  它挡的是「字段名像原文」+「字符串 >300 字符」。而**帖 summary 平均 90.4 字 —— 它能过闸**。
- **真正把文本挤出 State 的是「契约」，不是这条守卫**：契约规定每个任务的 `outputs` 必须落在
  指定文件 / 表，所以节点只能把 `material_id` 之类放进 State，文本自然进了文件。
- **已知缺口**：若某任务确实要把原文送进 LLM（梗识别 / 二创角度），必须在**工具调用内部**使用、
  只把结论（如 `is_meme: true`）写回 State —— **这条目前只有纪律，没有代码强制**。
  对策（待做）：给契约加 `text_access` 字段，声明「本任务读哪些文本源、是否送 LLM」，由 harness 审计。

### 那感知类为什么存在？——它揽了两件不同的活

感知类不是 tool，但它**必须存在**，因为它承接的是 **LLM 干不了的活**：

| 它做的事 | 性质 | 该不该它做 | 理由 |
|---|---|---|---|
| 算负向率、分层占比、显著性 p 值 | **计算** | ✅ 必须代码做 | LLM 算不准、不可复现、且会把 3000 条原文塞爆上下文 |
| `event_signals`：规则判定「这是不是个事件」 | **判断** | ❌ **揽过头了** | 判断本该是 Agent 的活；用规则做（决策 #8）的代价就是 §1.1 那张损失表的第 2、4 条——阈值损失与 0/6 命中 |

一句话：**感知类存在的意义是「把 LLM 不擅长的精确计算拿走」，但它顺手把「注意力分配」也拿走了，而后者恰恰是 Agent 的核心职责。** 这就是 v2 要动手的地方。

⚠ 措辞修正：是「**LLM** 与数据之间」，不是「Agent 与数据之间」。`act()` 阶段（纯代码，无 LLM）会**绕过 facts 直接读** `risk_insight.json` 取 `top_samples`——这是有意为之（见下面「有损压缩」第 4 条），但意味着 facts 不是整个系统的唯一入口，只是 LLM 的唯一入口。

**「facts 源」到底干了什么——拿 `platform_insight` 举个实例**：

```
输入  02数据_platform/ 三个 CSV：hot_hashtags 10 条 / discovery_posts 118 条 / discovery_comments 74 条
输出  outputs/platform_insight.json：
        inputs         {hot_hashtags:10, posts:118, loaded_comments:74}   ← 数，已经算好
        hot_board      [10 条，按 page_view 排序]
        event_signals  [6 条，规则判定，如 kind=hot_topic / score=23539 / evidence="热榜第 7 名 / 浏览 23539"]
        event_rules    {hot_board_pv:10000, topic_dig_interaction:500, ...}  ← 阈值公开可查
```

也就是说：**它把几千行原始文本，压缩成几十个可追溯的数字**，并且每个数字旁边都带着 `evidence`（出处）和 `event_rules`（判定阈值）——这就是「锁数」能被验证的原因。

下游怎么接：`daily_agent.perceive()` 把它挂到 `facts["platform"]`；而 `llm_decision()` 里发给 LLM 的就一行：

```python
{"role": "user", "content": json.dumps(facts, ensure_ascii=False)}
```

**LLM 收到的全部东西就是这个 JSON**，它没有任何通道去读左边的 CSV。提示词里那句「数字一律引用 facts，不得编造」只是二次声明——真正的约束是架构性的：**不给它看，它就没法编**。

### facts 是有损压缩：中间到底丢了什么（2026-09-29 实测）

几千行压成几十个数字，损失是必然的。**必须知道丢在哪，否则会把 facts 的盲区当成事实**。四层，越往下越严重：

| # | 损失类型 | 实测证据 | 后果 | 是否已补偿 |
|---|---|---|---|---|
| 1 | **截断损失** | `hot_board` 10 条 / `games_top` 10 条 / `interaction_top` 10 条 | 第 11 名之后的长尾**全部消失**，小众但尖锐的话题进不了 facts | ❌ 未补偿（Top-N 是硬截） |
| 2 | **阈值损失** | `event_rules`：`hot_board_pv` / `topic_dig_interaction` / `hot_board_top_n` | 阈值以下的事**即使真实存在也不算事件** | ⚠ 阈值写在 JSON 里可自查，但弱信号仍丢 |
| 3 | **语义损失** | facts 里**没有一条玩家原话**，`evidence` 也只是数字摘要（如「热榜第 7 名 / 浏览 23539」） | LLM 只看得到「6 个话题名 + 数字」，**看不到任何真实发言**；平台侧目前只有**热度**，没有**情绪** | ⚠ 部分补偿（见第 4 条） |
| 4 | **关联断裂（最严重）** | `matched_games` **0/6 命中**——6 条 `event_signals`、10 条 `hot_board`、4 条 `topic_dig`，**没有一条匹配到已建档游戏**（明日方舟 / 鸣潮） | 平台感知对我们的跟踪游戏**零命中**：数据在往 facts 里流，但对决策**零贡献**，整条链在空转 | ❌ **未补偿，且此前未发现** |

第 4 条值得单独说：这正是 §6 待定议题 9（「平台事件要不要触发 deep_dive」）一直悬着的**现实原因**——**它从来没被触发过，因为从来没命中过**。在拍板那个议题之前，得先回答一个更前置的问题：**是建档游戏的别名库太窄，还是这批数据确实与两款游戏无关？**（热榜上是原神 / 崩铁 / 三角洲 / 妮姬等，确实不含方舟与鸣潮，倾向于后者，但需扩样验证。）

> **🔄 2026-09-29 重新解读（客户 = 社区平台方之后）**
>
> **0/6 命中很可能不是 bug，而是我们把问题问错了。**
>
> 命中判据当时写的是「这个话题属于不属于我们建档的那两款游戏」。但客户是**社区平台**——
> 对 TapTap 来说，「卡厄思梦境换帅」「三角洲行动二周年」「星布谷地联动宇树科技」
> **哪怕一款都不属于我们建档的游戏，玩家照样会在社区里讨论它**，照样值得平台建话题、做活动、引导 UGC。
>
> 也就是说：**「未命中建档游戏」≠「与社区无关」。** 那条判据测的是「游戏归属」，而平台真正需要的是「**社区可发酵度**」——这两件事不是一回事。
>
> 判据应当改写为：
>
> | | 旧判据（测错了） | 新判据（平台视角） |
> |---|---|---|
> | 问法 | 这个话题属于我建档的游戏吗？ | **这个话题能不能在本社区发酵、值不值得建话题？** |

> | 失败模式 | 长尾游戏、非字面话题名全部漏掉 | 需要阈值与示例来校准 |
>
> 这也顺带把 §0.5①（相关性非字面 → 该交给 LLM）和 §0.5（Agent 不可替代性）落到了实处：**相关性判断本来就该是 Agent 的活，之前用规则做，测的还是错的东西。**

**已有的补偿机制**（v1 就在跑，别当成新设计）：`act()` 在 deep_dive 路径上直接读 `risk_insight.json` 的 `top_samples`，把**真实评论原文**（`text_excerpt`，含标点与换行）补回简报——实测每层 3 条（`high_risk_samples` + `disguised_samples` 共 6 条）。
注意它的边界：**只进简报给人看，不进 LLM**。所以「原文回查」这条路当前是**单向的、人工的**——LLM 发现疑点后，没有工具能自己去翻原始评论。这正是 v2 要补的能力（§6 议题 1 的 dig 循环上限，前提是先有可回查的工具）。

### 这个位置带来三条边界（避免误读）

1. **已完成部分不构成「Agent 能力」**。没有自主循环、没有跨日记忆、没有 interrupt 人工确认点——按 §0 第 2 条的自评标准，控制面仍是 workflow。已做的是**把感知面做厚**，不是把控制面做成 Agent。
2. **已完成部分是可直接迁移的资产**。采集脚本本来就是幂等 CLI（参数白名单已收口），v2 化时包一层 tool 即可，无需重写；感知模块统一输出 facts JSON，正好就是 v2「LLM 只见 facts」的输入契约。**这也是先做感知、后做控制面的理由**——先定死输入契约，控制层重构时不用回头改数据。
3. **`daily_agent.py` 是待替换物，不是成果**。它现在承担简报合并职责，v2 落地后会被两段式图接管。评审时不要把它的存在当成「Agent 已经能编排」。

## 1.2 判据改写落地：`ferment_judge.py`（2026-09-29 首个新定位模块）

§1.1 里「0/6 命中可能是问错了问题」这个判断，已经写成代码并**用真实数据验证**了。

**旧判据** `matched_games`：话题名 → 别名库字面匹配 → 问「属于我建档的游戏吗」
**新判据** `ferment_score`：LLM 语义判断 → 问「能在 TapTap 社区发酵吗、值得建话题吗」

### 实测验证（10 个热榜话题，无 key 走规则兜底）

| | 结果 |
|---|---|
| 旧判据（游戏归属）命中 | **0 / 10** |
| 新判据认为可发酵（act + watch） | **5 / 10** |

> **这条对照直接印证：未命中建档游戏 ≠ 与社区无关。** 那 10 个话题一款都不属于我们建档的游戏，但按平台视角有一半值得建话题或观察。

### 同时暴露了规则兜底的盲区（所以要上 LLM）

「米哈游反舞弊通报」pv 仅 2524、互动 0、标题不含关键词 → 规则给 **0 分 / 忽略**。
但它是**争议性话题**，玩家一定会吵，社区可发酵度其实很高。

> **热度 ≠ 可发酵度。** 规则只能测热度，测不了「有没有讨论动机」——这正是 LLM 该干的活，也把 §0.5 的论证落成了可运行的代码。

该案例已写成单测 `test_known_blindspot_controversial_topic_scores_low` 锁死，避免以后有人把代理分当结论用。

**降级纪律**：无 API key 时仍可跑通产出结构，但 `degraded=True` 且报告顶部红字标注「代理分不等于可发酵度，不可作为结论使用」。**测试 109 全绿（+10）。**

## 1.3 「追踪」落地：`topic_tracker.py` 话题生命周期状态机（2026-09-29）

项目目标原文是「**热点是需要追踪的**」。此前所有模块都是**单次快照**——它们能回答「今天有什么热」，回答不了「这个事**在升温还是退潮**」。这是目标与实现之间最实的一个缺口，本节把它补上。

### 为什么不选另外两条路

| 方案 | 为什么没选 |
|---|---|
| 把昨天报告丢给 LLM 让它对比 | 数字不可复算、不可回溯；违反「facts 锁数」不变量 |
| 存两份 JSON 做 diff | 只能比两点，判不了「退潮」；且话题改标题就失忆 |

选的是**状态机 + SQLite 时序库**：判据是**变化率**，状态跨天持久，每次采样 append-only 可回放。

### 状态定义（判变化率，不判绝对值）

```
冒头 ──1.5×──> 升温 ──3.0×──> 爆发
  ↑                              │
  └────────── 0.6× ──────────────┘
              ↓
           退潮 ──72h 无采样──> 沉寂
```

| 常量 | 值 | 含义 |
|---|---|---|
| `RISING_SLOPE_RATIO` | 1.5 | 相对上次采样涨幅 ≥1.5× → 升温 |
| `BURST_SLOPE_RATIO` | 3.0 | ≥3.0× → 爆发 |
| `FADE_SLOPE_RATIO` | 0.6 | ≤0.6× → 退潮 |
| `SLEEP_AFTER_HOURS` | 72 | 72h 无新采样 → 归档为沉寂 |
| `MIN_SAMPLES_FOR_TREND` | 2 | 少于 2 次采样不做趋势判断（首日全部「冒头」属正常） |

> **判变化率是这一层的核心判断**：热度榜上所有话题绝对值都高，「浏览 6583」本身不含任何行动信息；只有「比上次涨了 6 倍」才说明现在接还来得及。绝对值高但持平的话题，状态机**不改状态**（已有单测锁死）。

### 表结构（`11情报Agent/state/topic_tracker.sqlite3`，运行时库、不入 git）

- `topic_state`：每个话题一行当前态（topic_key / title / hashtag_id / **metric_kind** / first_seen_at / last_seen_at / state / last_metric / peak_metric / sample_count / prev_state / state_changed_at）
- `topic_series`：append-only 采样序列（topic_key / sampled_at / metric / metric_kind / source）
- `meta`：`SCHEMA_VERSION`，便于以后改表

### 话题身份：`metric_kind` 必须算进 key（★ 实测踩坑）

第一版 `topic_key = hid:{hashtag_id}` 或 `tit:{归一标题}`。用一个话题三天的真实数据模拟时暴露了严重失真：

```
三角洲行动二周年： [6270, 38, 6583, 39, 6583, 39]
                   └浏览 ┘└互动┘ └浏览 ┘└互动┘ ...
```

浏览量（6270）和互动量（38）写进了**同一个 key**。状态机把「换了个指标」误读成「跌到 0.6% → 退潮」，下次又误读成「涨 173 倍 → 爆发」。**第 2 天产生 9 个迁移记录，几乎全是噪声。**

修复：`topic_key(title, hashtag_id, metric_kind)` 追加 `|{metric_kind}`，两个指标各走各的序列。修复后同一天**只剩 1 个真实迁移**（米哈游反舞弊通报浏览量涨 6× → 爆发）。

> 自我批评：代码注释里当时写着「两个指标不能混算同一条曲线」，但实现没做到——**注释对、实现错**。已加两条回归测试锁死（`test_metric_kind_part_of_identity` / `test_metric_switch_does_not_fake_a_crash`）。

### 与主链的接线方式：只读、不参与决策

`daily_agent.py` 新增 `load_topic_state()`，只读状态库（**写入由 `topic_tracker.py` 独立负责**）：

- 采样时机与频率归调度层管。若让简报生成顺手写状态，等于把「全天监测」绑架在「每天一跑」上——这正是要避免的耦合。
- facts 新增 `topic_trend` 维度（可选，缺失显式降级），简报新增「话题趋势（跨天追踪）」段落。
- 它是**信息维度不是决策项**：`rule_decision` 完全不看它（已有单测 `test_topic_trend_does_not_change_decision` 锁死）。

### 降级与未校准声明（两条硬纪律）

1. 状态库缺失 / 损坏 → 简报写明「不可用：原因」，**绝不静默变成「无趋势」**。
2. 简报「边界」段固定声明：状态阈值（1.5×/3.0×/0.6×）**未经真实运营反馈校准**，不得当可信参数使用。

### 当前实测状态

首日采样 14 个话题，状态全为「冒头」——符合设计（迁移需 ≥2 次采样）。跨天记忆、持久化、斜率判定、归档均已用模拟数据验证。**测试 149 全绿（topic_tracker 30 + daily_agent 集成 10）。**

### 待办（明确未做）

- 阈值校准需要真实运营反馈（现在全是拍的）
- 话题**语义**归一（「三角洲行动二周年」vs「三角洲 2 周年」现在靠字面归一，同义不同形仍会分裂）——接口已留，等 LLM 余额
- 采样调度器（心跳频率、事件驱动触发）尚未实现
- 素材层、创意生成层：项目目标另两个缺口，尚未动工

## 2. Agent 控制范围：两段式 + 人工域

### 第一段：数据运维编排（每日巡检）

| 步骤 | 行为 | 失败处理 |
|------|------|----------|
| 新鲜度检查 | 距上次采集 >24h 或档案变更 → 需采集 | — |
| 采集工具 | subprocess 爬虫；参数白名单：`--game` / `--data-dir` / `--max-records` | 记录降级 |
| **质检闸门** | 条数 / app_id 归属 / 空文本率 | 失败自动重爬 1 次，再败标记降级继续 |
| 清洗工具 | 质检通过才执行 | 记录降级 |
| **标注闸门（人工确认点）** | 算增量条数与额度账；余额不足（当前 402）自动跳过并记录 | 充值后待批执行 |
| 异动分析工具 | anomaly_lite（零依赖），每游戏一次 | 记录降级 |
| 产物刷新工具 | 看板重建 + 跨游戏对比报告 | 记录降级 |

### 第二段：情报分析

感知（读巡检 facts）→ 分析（有无值得深挖的事，结合跨日记忆去重）→ 深挖（评论查询/主题下钻/趋势，循环上限待定）→ 简报（当日简报 + 巡检摘要合并）。

### 边界外（人工域）

标注额度充值与批准 · 游戏档案增删 · 架构变更。

### 三条不变量

数字只来自代码（facts/工具返回）· 每步幂等可重跑 · 全程轨迹落盘可回放。

## 3. 标注三层架构（成本优化，讨论中）

动机：DeepSeek 402 余额不足；全量 LLM 标注扩样后成本上升。

```
全量评论
 ├─ ① 规则层（词库/句式库，纯标准库）→ 显性情绪 + 模式化反讽，预计短路 60-70%
 ├─ ② BERT 情绪层 → 剩余样本打分；p≥0.9 采用 / 0.6-0.9 采用+抽查 / <0.6 或与星级冲突 → 上送
 └─ ③ LLM 仲裁层（RAG 在此：反讽例句库 few-shot 检索）→ 疑难样本 5-15%
```

**技术修正记录**（讨论结论）：
- 反讽是 BERT 弱项（字面与意图分裂），BERT 只覆盖显性情绪与模式化反讽；
- RAG 放 LLM 仲裁层而非 BERT 层（BERT 无检索输入通道）；
- 通用情绪模型不识游戏黑话 → 需用 LLM 标注历史做领域微调。

**种子资源**：154 条修辞伪装标注（reason 字段）= 词库 v1 种子；方舟 3000 条 LLM 标注 = BERT 微调集 + 金标验收集。

**效率杠杆**：置信度路由 · 文本 hash 去重（带词库/模型版本号的缓存键）· 增量处理 · LLM 攒批错峰 · 反馈闭环（仲裁确认的新案例 → 句子库 → 规则覆盖面扩大 → LLM 调用递减）。

**验收口径**：规则+BERT 组合 vs LLM 金标的一致率（接 model_eval proxy 口径）。

## 4.5 用户级数据与 PII 边界（用户 2026-09-29 拍板）

「锁定用户看流动」一旦做，就必然碰到隐私红线。定死三层：

| 域 | 位置 | 允许内容 | 是否入库 |
|----|------|----------|----------|
| 原始域 | `02数据/reviews.csv`、`02数据_*` / `02数据_platform`（已 gitignore） | 明文用户标识、昵称、原文 | ❌ 不入库 |
| 分析域 | `02数据/processed/reviews_clean.csv`、`11情报Agent/outputs/` | **只有**加盐哈希 + 聚合分布 | ✅ 入库 |
| 产出域 | `reports/`、看板 | 只有聚合（流向矩阵 / 占比 / 分布） | ✅ 入库 |

**⚠️ 2026-09-29 事故复盘（这条边界曾经失守）：**

`.gitignore` 原先写的 `02数据_*/`（**带下划线**）与实际目录 `02数据/`（**无下划线**）不匹配，
规则静默落空 —— 含明文 `user_name` / `user_id` / `avatar_url` 的 3000 行 `reviews.csv`
与 `processed/reviews_clean.csv` 自 `85fc148`（2026-07-27）起在公开仓库暴露约两个月。

已修正：
- `reviews.csv` 移出版本库（本地保留，U1 采集必需明文 `user_id` 作接口入参）
- `reviews_clean.csv` 删除三列明文，保留 `user_id_hash`，仍入库（CI 的 `anomaly_lite` 依赖）
- `.gitignore` 改为**显式路径**，不再依赖目录名巧合
- CI 新增 PII guard：扫描 `git ls-files` 中所有 CSV 的表头

**教训（写进纪律）：gitignore 规则必须用显式路径，且必须用 `git check-ignore -v` 验证命中。**
目录名少一个下划线，就能让边界失效两个月而无人察觉。

三条硬约束：
1. **哈希必须加盐**。原实现 `sha256(uid)[:16]` 无盐——TapTap 用户标识是 9 位数字（空间 ~10⁹），
   彩虹表秒级反推，那不叫脱敏。已改为 `HMAC-SHA256(salt, uid)`，盐在 `01爬虫/.env`（不入库）。
   ⚠ 换盐 = 历史哈希全废，需重算。
2. **只出聚合，不出个体**。报告里不允许出现单个哈希，也不允许出现「某人的轨迹」。
   `user_flow.assert_aggregate_only()` 在写文件前扫渲染文本，命中 16 位十六进制串直接抛错。
3. **明文标识只用于运行时关联**。因为哈希不可逆，没有明文就查不了 `by-user` 流；
   所以明文只在原始域存在，分析时现算哈希做关联，不落任何产出文件。

产出文案也回避字段名：CI 有 PII 字段扫描（`user_name|avatar_url|device_raw|user_id`），
`user_flow` 的 privacy 块已改用「identifier / 明文标识」表述，避免描述文字误触发。

| # | 契约项 | 内容 | 现状 |
|---|---|---|---|
| 1 | 任务定义 | 输入 facts 哪些字段 / 输出落哪 / 什么算成功 | ⬜ 空白（无显式契约） |

**核实依据**：`daily_agent.run_tool()` 失败直接抛（无重试、不记成功）；`scheduler.run_step()`
失败记录降级（有降级纪律、无重试）；`agent_run.log` 仅异常堆栈。

**同一层里用户未提、但必须一并定的三条**（agent 补充，待用户确认）：

13. **幂等键**——**重试的前提是幂等**。要答"错误了打不打回"，必须先答"重试安全吗"。
    现状：`events.py` 有 `event_id` 幂等、`features.py` 有 `UNIQUE(run_id, moment_id)`、
    `ops_push` 有 `UNIQUE(topic_key, state)`——**点上有，整体无统一幂等键约定**。
14. **并发 / 重入**——见第 10 条：内化时钟后 tick 可能重叠，需单例锁（或"上一轮未结束则本轮跳过"）。
15. **成本预算**——不只是调用**次数**，还有 **token / 费用**上限。本项目已有 402 余额事故，
    标注闸门里有额度账，但**没有把"每轮/每日成本上限"作为硬约束**。

### 7.2 平台通道已验证的接口与坑

| 通道 | 接口 | 坑 |
|------|------|----|
| S4 | `hashtag/v2/hot-hashtags?from=&limit=` | `from` 翻页无效（第 2 页回同一批）；`comment_count` 多数回填 0，热度看 `page_view`；个别条目无话题实体 id（用 `t:<标题>` 兜底去重） |
| S5 | `discover-categories/v2/feed-list?category_id=0` | 只能用 `next_page`（带 session_id）翻页；推荐流重叠率高，靠「连续 N 页无新增」停 |
| S6 | `feed/v7/by-hashtag?hashtag_id=&from=&limit=&sort=` | 每话题约 8–10 帖即到底 |
| 通用 | Referer 含中文话题名 | 必须 `quote()`，否则 urllib3 抛 `UnicodeEncodeError: latin-1` |
| 通用 | 评论正文 | 发现流是 Slate 富文本 `contents.json`，且作者名在 `author.name`（非 `author.user.name`）；解析器已双形态兼容 |
| U1 | `feed/v7/by-user?user_id=&from=&limit=` | **limit 上限 10**（20/30 → HTTP 400）；`from` 翻页有效；`data.total` 是总量；试过的 `moment/v1/by-user`、`user/v1/moments`、`user/v1/games` 全 404；`user/v1/detail` 参数名是 **`id`** 不是 `user_id` |
| U1 | 取样 | 必须分层（`--sample stratified`）：按投入时长取 top 会让低投入组全变成「接近阈值的重度玩家」，C 口径直接失效 |
| U1 | 加权 | 分层把两组拉成 1:1，但池子里真实比例不是（鸣潮实测 665 高 / 2344 低）。**「整体流出率」必须按池比例加权**；直接算样本会高估重度玩家影响（实测 50.0% vs 加权 25.0% 的差距量级）|
