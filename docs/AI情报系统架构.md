# AI 自动化情报与素材系统 · 架构设计

> 2026-10-05 定稿　｜　取代旧 L1-L6 管线分层模型
> 目标：**全网热点追踪 → 情报 + 素材 → TapTap 增长创意**

---

## 0. 旧架构为什么废

旧架构是**数据流水线**：L1 爬→L2 洗→L3 聚→L4 报→L5 记→L6 执行。
问题：每一层都是规则和阈值，**没有任何一步"读懂"内容**。
产出是 `arknights / 上线 / 开服` 这种实体碎片——正确的废话。

新架构是 **AI Agent 系统**：LLM 是大脑，直接读原始数据做判断；
爬虫和算法是 Agent 的手和眼（工具），不是独立的"层"。

| 知乎热榜 | 问答讨论 | social | ❌ 需登录态 |
| 抖音话题 | 泛用户传播 | content | ❌ 风控严重 |

**采集原则**：
- 所有通道按 S1 游戏标签自动匹配到游戏（1246 个游戏社区的名字做标签库）
- 新帖发现靠**反复轮询 + 发布窗口过滤**（by-group 无时间序参数）
- 帖子的计数快照每轮必写（增速 = 两次快照之差 = 爆火检测）
- 评论**只在需要时抓**（LLM 点名 / 计数飙升触发了才下钻）

### 2.2 数据查询工具（LLM 的眼睛，免费）

| 工具 | 作用 |
|---|---|
| `list_threads()` | 帖子目录（标题/摘要/计数/增速），LLM 挑选深挖对象 |
| `read_comments()` | 读已抓回的评论（按赞/按时间排序） |
| `list_hotspots()` | 外部热搜条目（百度/微博/B站，含趋势率） |
| `get_game_info()` | 游戏社区信息（关注/帖子量/近期活跃/官方声量） |
| `get_event_timeline()` | 事件的跨平台传播时间线 |

### 2.3 事件分析工具（有算法有 LLM）

| 工具 | 做什么 | 谁来判断 |
|---|---|---|
| `detect_burst()` | 发帖速率异常检测（以采集时刻为锚点） | 规则（z-score/MAD） |
| `cluster_topics()` | 相似帖子聚成事件候选 | bge embedding + LLM 精判 |
| `resolve_events()` | 跨平台事件合并（同一件事 → 一个 Event） | bge 召回 + LLM 判定 |
| `judge_relevance()` | 外部热点和 TapTap 游戏的相关性三档 | LLM（related/adjacent/irrelevant） |
| `extract_semantics()` | 从帖子/评论中抽 Entity + Relationship + Event | LLM（★ GraphRAG 的地基） |
| `track_lifecycle()` | 事件生命周期（EMERGING→RISING→PEAK→DECLINING→DORMANT） | 规则（基于速率曲线） |

### 2.4 创意生成工具（产出层）

| 工具 | 产出 |
|---|---|
| `generate_creative()` | 针对具体热点生成创意（位置/步骤/文案/素材/风险/KPI） |
| `extract_materials()` | 从帖子/评论中提取可用素材（金句/截图/视频/梗） |
| `suggest_timing()` | 建议投放时机（基于生命周期 + 创意提前期） |
| `check_feasibility()` | 可行性校验（团队资源/预算/提前期） |

## 4. 关键设计决定（今天全部讨论过）

### 4.1 热度度量：发帖速率，不是评论数
- 以采集时刻为锚点：最近 1h/6h/24h 各发了多少帖
- 社区级用 `topic_count` 做差（但它是**批量刷新**的，只能测小时级持续增长）
- 评论增速是**单帖爆火**的信号（B 类），不是**事件爆发**的信号（A 类）

### 4.2 热榜是存量榜：只报 forming 档
- 词上榜时讨论量已过峰值
- 只报：刚进榜 / 热度在涨 / 排名在升（forming 档）
- peaking/fading 的**不报**（那是过去时）

### 4.3 分析单元 = Thread（帖子+评论）
- 评论没有独立生命，语境完全属于帖子
- 帖子是观点载体，采集和完整性监测的基本单元
- 事件是热点单元——一堆帖子在讲同一件事
- 聚类输入是 thread（标题+正文+高赞评论采样），不是零散内容

### 4.4 LLM 必须接触原始数据
- 词表实体/相似度阈值/图算法——全是规则，产出的"事件"是伪语义
- LLM 逐帖抽 Entity + Relationship → 存图 → GraphRAG 建社区 → LLM 在图上做全局推理
- 免费模型的限制：结构化输出≤8 条/次；需要置信度输出 + 降级路径

### 4.5 外部热点不要等站内数据
- 鸣潮的热点即使 TapTap 站内还没讨论，也完全可以出创意（甚至更有价值：先发）
- 站内数据是**事后验证**（热点传导到社区了吗）和**效果度量**（创意发了社区有反应吗）
- 不是创意生成的**前置条件**

## 5. 运行模式

### 5.1 自动模式（定时任务）
```
每 10 分钟：S2/S5 首页轮询（新帖发现 + 计数快照）—— 轻量
每 30 分钟：S3 评论增量（只抓计数增长了的帖）—— 中量
每 2 小时：S1 社区地图 + S4 热榜 + 事件合并 + 形成中报告 —— 中量
每天一次：全量分析（LLM 逐帖抽取 + 事件图 + 报告 + 创意）—— 重量
```

### 5.2 交互模式（用户问）
```
用户："今天有什么热点？"
  → Agent 调 list_threads 看目录
  → Agent 调 list_hotspots 看外部信号
  → Agent 调 deepen_threads 深挖感兴趣的
  → Agent 调 read_comments 读评论
  → Agent 输出：情报（事件/态度/风险）+ 创意（可执行动作）
```

## 8. 诚实边界

- **topic_count 有缓存延迟**（大社区几小时刷一次）→ 只能测小时级增长
- **推荐流有马太效应**（热帖反复出现、冷帖被推走）→ 采集样本有偏
- **百度热搜是搜索意图**，不是讨论热度（用户搜了不代表在讨论）
- **微博趋势指数**是非公开接口 → 用自己跨轮算的变化率代替
- **免费模型的结构化输出**有条数上限（8 条/次）和可靠性问题 → 需置信度 + 降级路径
- **贴吧/知乎**需登录态，暂未接入

## V2 · Agent 自主控制（设计记录，未实施）

> 2026-10-05 用户定调：V1 是"人配参数、Agent 执行"，V2 是 **Agent 自己控制时间和参数**。
> Agent 不只是分析数据，还决定**怎么采数据、花多少预算、盯哪些社区**。

### 核心：Agent 接管三类决策

**① 采集节奏（什么时候抓、抓多深）**

| 场景 | V1（人配） | V2（Agent 自定） |
|---|---|---|
| 平时 | 固定 10 分钟一轮 | Agent 根据近期活跃度调：活跃期 5min、安静期 30min |
| 检测到爆发 | 人改参数 | Agent 自动升频到 1-2min，持续 30-60min 后自动回落 |
| 冷门社区 | 和热门一样频率 | Agent 降低频率或暂停，节省预算给活跃社区 |
| 深夜（03:00） | 和白天一样 | Agent 知道这个时段发帖少，自动降频 |

**② 采集参数（窗口、预算、阈值）**

| 参数 | V1 | V2 |
|---|---|---|
| 新帖窗口（fresh_hours） | 前端配 48h，写死 | Agent 根据当前活跃度动态调：爆发期缩到 24h、安静期放到 168h |
| 评论预算（max_comment_calls） | 前端配 150 | Agent 分配：按"增长最快的帖优先"，预算给到最有价值的地方 |
| 评论页数上限 | 固定 10 页 | Agent 按帖热度分级：<300 条抓全、>1000 条抓热评+最新 |
| 点赞阈值 | 前端配 50 | Agent 根据社区基线动态调：大社区阈值高、小社区阈值低 |
| 形成中涨幅门槛 | 固定 8% | Agent 按社区基线的标准差动态调 |

**③ 覆盖范围（盯哪些社区/哪些游戏）**

| 决策 | V1 | V2 |
|---|---|---|
| 盯哪些游戏 | 手动 --app-ids 传入 | Agent 根据 S1 索引的近期活跃度自动选：recent_topic_count 飙升的社区自动加入监测 |
| 何时新增/移除 | 人改 | Agent：连续 N 轮无增长 → 降级；突然有增长 → 升级 |
| 跨游戏联动事件 | 人发现 | Agent 发现"多个游戏社区同时出现同一话题" → 自动建跨游戏事件 |

### 实现路径

```
V1（已完成）
  人配 crawl_config.json → 爬虫读取 → 固定参数跑

V2（过渡）
  Agent 每轮跑完后输出一份"采集建议"（JSON）：
    {"adjust": {"fresh_hours": 24, "max_comment_calls": 200},
     "reason": "检测到3个帖增速异常，需要更频繁的评论追踪"}
  下一轮爬虫自动读取并应用

V3（终态）
  Agent 直接控制采集调度：
    - 自己决定下一轮什么时候跑、跑哪些源、花多少预算
    - 自己决定要不要深挖某个帖、要不要追某个话题
    - 人只看产出（情报/创意），不管过程
```

### 约束（不能让 Agent 飞了）

- **请求总量有硬上限**：不管 Agent 怎么调，TapTap 的 WAF 是真实存在的（实测 >150 秒冷却），所以总请求量/小时有天花板
- **预算有硬上限**：评论接口调用/轮 有上限，Agent 只能在这个范围内分配
- **重大操作要人工确认**：新增一个游戏社区的持续监测、大范围改采集策略——这些至少要通知人

---

### V2 需要新建的模块

| 模块 | 做什么 |
|---|---|
| `strategy.py` | Agent 的采集策略引擎：输入当前状态（快照/增速/生命周期），输出下一轮的采集参数 |
| `feedback.py` | 策略效果回溯：上一轮 Agent 调的参数，抓到了什么？有没有漏？下一个周期怎么调？ |
| `budget.py` | 请求预算分配器：按社区活跃度/事件优先级/渠道重要性加权分配 |

---

> **V2 的本质：Agent 从"分析者"升级为"调度者"——它不只告诉你发生了什么，还自己决定下一步看哪里、看多仔细。**
