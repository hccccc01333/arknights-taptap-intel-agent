# 热点检测架构设计（LLM + GraphRAG）

> 状态：**设计决策已拍板，尚未实施**（2026-10-04 讨论产出）
> 决策人：项目负责人　｜　实施优先级：L1/L2 数据链路完成之后

---

## 0. 一句话

**LLM 是"形成热点判断"的主体，GraphRAG 负责理清帖子之间的关系，L1/L2 提供干净连续的原始语料。**

不做"先规则算出结果、再让 LLM 配文案"——那是本末倒置，等于让 LLM 去解释一个它没参与的判断过程。

---

## 1. 为什么推翻原路线

原链路 L1-L3 是**规则流水账**：

```
词表抽实体 → 相似度算分 → 阈值切分 → 图算法聚类
   ↑              ↑
 信息在这里被压成 ID，后面全是数字运算，没有任何一步"读懂"内容
```

**后果**（都是实际发生的）：

- 帖子标题明写着「【明日方舟】谬因实战测评：断层第一」，聚出来的事件名却叫 `arknights`
- 评论在说"这个卡池太阴了"，特征里只有 `supports=7`
- 两个人说同一件事，用词不同就聚不到一起
- 图算法的输入根本不是语义，是我们用规则造的**伪语义**——算法没错，地基错了

**结论：这个项目必然需要语义。LLM 必须接触原始数据。**

---

## 2. 目标形态

```
使用者的一个问题（"今天有什么热点"）        ← 一种形式
   或  定时自动触发                          ← 本质一样
        │
        ▼
┌───────────────────────────────────────────┐
│ LLM（提示词 + 各个帖子的原文）             │  ← 系统的心脏
│ 直接形成"热点"这个判断                     │
└───────────────────────────────────────────┘
        ▲                            ▲
   各个帖子的关系              事实数据（计数/时间）
        │
┌───────┴────────────────────────────┐
│ GraphRAG（图上做关系/事件发现）      │  ← 输入就是 LLM 抽的语义
└───────┬────────────────────────────┘
        │
   L2 清洗 → L1 数据获取
```

**关键**：LLM 一次不能只看到零散片段，它要能看到**结构**（哪些帖子在说同一件事、涉及哪些实体、彼此什么关系）——这正是 GraphRAG 的意义：**先建索引，再让 LLM 在索引上做全局推理**。

---

## 3. 分工

| 层 | 职责 | 变化 |
|---|---|---|
| **L1** | 数据获取（爬虫） | **不动**。爬虫不需要语义 |
| **L2** | 清洗 + **LLM 逐帖提取**（实体/话题/态度/涉及玩家） | 规则清洗保留；LLM 抽取**并入此处**，落库存档保证可复现 |
| **L3** | GraphRAG：帖子关系建模 + 社区/事件发现 | 图算法逻辑基本能用，**输入从词表 ID 换成 LLM 抽的中文语义** |
| **L4** | **LLM 形成热点判断 + 回答使用者** | 心脏。速率检测放时间维度：**先算发帖速率曲线，再在"速率异常的簇"上检测热点** |

---

## 4. LLM 抽什么（喂给 GraphRAG 的原料）

每个帖子的原文交给 LLM，产出：

- **实体**：中文（游戏名、干员名、活动名、道具…）—— 修正当前中英混用问题
- **话题/主题**：这篇在讲什么
- **态度**：正面/负面/中性、吐槽/测评/求助
- **关系**：与其他帖子的关联（讲同一件事 / 引用 / 反对 / 补充）

**速率数据不是 LLM 产出的**——评论数、发布时间、增速永远由规则算，LLM 只引用（锁数纪律，见 §7）。

---

## 5. 热点信号的分类（已商榷确认）

| 类型 | 信号 | 定位 |
|---|---|---|
| **A 话题爆发** | 一组相似帖子的**发布速率**飙升 | **主线**：热点的形成过程 |
| **B 单帖爆火** | 单帖评论/点赞暴涨 | 热点的**具体载体**（事件里的"热门帖"） |
| **C 站外热度** | B站/抖音/微博等站外热度先行 | **发现雷达**：站外涨了站内还没动静 = 早期信号 |
| C' 站内热榜 | TapTap 热榜 | **辅助**：只做展示 + 给 A 播种新话题 |
| **D 口碑舆情** | 低分评测集中出现、评分骤降 | **验证信号**：验证 A 的发现（同向=真热点；D 单独异动=产品问题不是话题问题） |
| **E 官方动作** | 公告/官方动态 | **归因字段**：不是事件类别（官方窗口内也会有自发热点）。记录"这期间官方有无动作"，用于事后复盘 |

**C 的重要认知**：对 TapTap 而言，**站内热榜只是回声（平台推荐结果，二手信号），站外信号才是雷达（一手信号）**。玩家可能还没来 TapTap 发帖，已经在 B 站吵起来了。

## 6. 速率检测（A 的算法）

原则：**先按时间分桶 → 桶内按内容相似度聚类 → 看哪个簇在变大**。

这样"事件"天然带着"我什么时候开始变大的"属性，热度不用另算。

- **站内热点**（单游戏社区内）：给运营用——"方舟社区在聊什么"
- **跨站热点**（全平台）：给公司用——"什么题材火，该立项"。跨站判定天然依赖话题标签而非玩家，所以要 LLM

**前提**：判定"两个帖子是不是在讲同一件事"。做法=**词表粗筛 + LLM 判同组**（数据量小，粗筛命中率够，LLM 只在有歧义处出手）。

---

## 7. 三个必须认下的代价

**代价1：成本与延迟——必须分层，不能全量过 LLM**

| 内容 | 走不走 LLM |
|---|---|
| 计数类（评论数/点赞数/增速） | ❌ 永远不走，规则算 |
| 新帖（未进过库的） | ✅ 抽实体+关系（增量，量可控） |
| 爆火帖的评论（事件确认后深挖） | ✅ |
| 已确认"同一件事"的老帖 | ❌ 不重复处理 |

**代价2：可复现性**——同输入两次可能给不同答案。复用现有 `input_hash` + `analysis_cache` 设计：**同一帖子只标一次，结果落库，后续重跑完全可复现**。

**代价3：免费模型的能力边界**——现有是 OpenRouter 免费模型路由。LLM 判"是不是同一件事"准确率可能只有六七成。
→ 必须**输出置信度**，低于阈值宁可不合并也不误合并；
→ 必须有**降级路径**：LLM 挂了/低置信度时退回词表方案，**但保留结果并标注"这条是规则判的"**。

**不能因为上了 LLM 就假装没有降级路径。**

---

## 8. 锁数纪律（不变）

LLM 拿不到原始数字，只能引用 facts（评论数、发布时间、增速），避免编数字。这条从 L4 `ModelRouter` 延续下来。

## 9. 实施前的验证（建议先做）

用库里现有 320 条帖子原文，跑一次：

1. LLM 逐帖提取 → 建图
2. 把图结构 + 关键帖原文给 LLM → 让它说"今天有什么热点"

**只看输出质量**，不做前端。用真实数据说话，再决定是否动地基。
