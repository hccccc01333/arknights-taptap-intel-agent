# 创意生成与闭环设计 —— 从素材到「实际增长创意」

> 状态：**设计稿，待拍板后动工**。写于 2026-09-30。
> 决策人：HZZ；agent 只做实现、验证与边界汇报。
> 上游：[素材层设计](./素材层设计.md)（素材怎么抽） · [交付形态设计](./交付形态设计.md)（谁在用）
> 定位：项目目标原文「**通过热点识别产出与 TapTap 相关的实际增长创意**」——
> 这是整条链的**最后一环**，也是 LLM 唯一做它真正擅长的事（**创造**）的地方。

---

## 1. 为什么这一环必须靠提示词工程

项目里其他环节大多是**计算**（facts 锁数）或**判断**（可发酵度、三概念分类）。
**二创角度是唯一的「创造」**，而没有确定性判据 —— 所以：

| | 其他环节 | **二创角度** |
|---|---|---|
| 依靠 | 代码算 / 规则判 | **提示词 + 上下文** |
| 可核对性 | 数字可回查 | ❌ **不可核对**（所以必须标注「这是建议」） |
| 质量靠什么 | 逻辑正确 | **提示词设计质量** |

用户说的很准：

> 「二创角度其实是属于创造性的内容了。那意味着我们的脚本
> **只能通过写提示词，然后结合帖子上下文**。这其实还是提示词的规划。」

**所以这一环的工程质量 = 提示词工程质量。** 没有别的抓手。

## 2. 提示词设计：五个必答问题（用户列的）

用户提出，要让大模型给出二创角度，**必须先让它知道五件事**：

> 「你首先是不是要——**原先这个素材是什么样子？原先这个素材在哪儿？原先什么意思？
> 我们能用在哪些方面？他是为什么用这个东西？**」

这五个问题**恰好映射到素材 Schema 的字段**（说明 Schema 设计是对的）：

| 用户的问题 | 提示词槽位 | 字段来源 | 谁产生 |
|---|---|---|---|
| **是什么样子** | 素材原文 | `text` | 代码（抽取） |
| **在哪儿** | 来源社区 + 帖子标题 + 可点链接 | `provenance.url` / `app_title` / `topic_title` | 代码 |
| **什么意思** | 语义解释 | ← **需要 LLM 补**（梗解释 / 金句含义） | **LLM** |
| **能用在哪些方面** | 适用场景 | `usable_for` | LLM（仲裁层产出） |
| **为什么用** | 它的作用（共情 / 吐槽 / 玩梗 / 反讽） | `selection_reason` + 梗的两轴分类 | 代码 + LLM |

**两个字段是这一环的硬前置**：
- `什么意思` —— 如果素材是梗，**必须先解释它**（这正是 §4.3 里「梗解释」那一步的价值）
- `能用在哪些方面` —— 决定它能往哪个方向做二创

> ⚠️ **所以「梗解释」不是一个可选步骤**。没有它，二创提示词里就缺了
> 「什么意思」和「能用在哪些方面」两块 —— LLM 只能瞎猜，产出必然空泛。

## 3. 提示词模板（结构示意）

```text
【角色】你是 TapTap 社区的内容运营策划，擅长把玩家自发的表达
        转化为社区可执行的内容动作。

【本次选题】
  话题：{topic_title}（当前状态：{state}，热度变化：{slope}×）
  社区：{app_title}

【可用素材】（共 {n} 条，全部来自真实帖子，链接可点）

  素材 1（{type}）
    · 原样：{text}
    · 来源：{url}（{app_title} · 帖子「{post_title}」）
    · 什么意思：{semantic_explanation}      ← 梗需要解释，金句是字面
    · 用在哪些方面：{usable_for}
    · 为什么用：{why}（{axis_note}）          ← 梗的两轴分类写在这
    · 上下文：{thread_context}                ← 非自足素材必带（§3.5）

  素材 2 …（同上）

【任务】
  基于以上素材，产出 {k} 个**可执行的社区内容动作**。
  每条必须包含：
    ① angle   —— 二创角度（一句话说明做什么内容）
    ② example —— **一个具体的示例**（能直接照着做的文案/活动描述）
    ③ based_on —— 依据哪几条素材（必须引用上面的编号）
    ④ grounding_score —— 0~1，这个角度与素材的关联强度（**自评**）
    ⑤ reason  —— 为什么这个角度在本社区可行

【约束】
  · 每个角度必须能追到上面某条素材，**不许凭空生成**
  · 示例文案要像玩家写的，不要像广告
  · grounding_score < 0.6 的不要输出（宁缺毋滥）
```

**设计要点**：

| 要点 | 为什么 |
|---|---|
| 每条素材带**可点链接** | 呼应「先确保人工能找到素材怎么来的」——**生成的创意也要能回溯** |
| `什么意思` / `用在哪些方面` 单独列 | 用户明确要求（§2） |
| `上下文` 按 `self_contained` 条件带上 | 自足素材省 token（§3.5） |
| 要求 **`example` 具体示例** | 用户明确要求：「最好还能给出例子来」 |
| 要求 **`grounding_score`** | 用户明确要求：「通过大模型自己输出一个相似度的字段」 |
| **`based_on` 必须引用编号** | 代码可校验，防止凭空（见 §5） |

## 4. 自我迭代：相似度字段怎么变成改进信号

用户提出：

> 「因为一旦给出了那种它的二创例子的话，然后通过大模型自己输出一个相似度的一个字段，
> 对吧？我们**本质上来说就可以制作一个自我迭代的一个系统**」

**机制**：`grounding_score` 是 LLM 对「我这个角度到底有没有真的基于素材」的自我评估。

```
生成 → 自评 grounding_score
         ↓
   ┌─────┴─────┐
 < 0.6          ≥ 0.6
   ↓              ↓
 丢弃       进候选 → 员工筛（§6）
    ↑              ↓
    └── 若员工也否，反馈回提示词（负例）
```

**这个环对应 G4 图的 `self_critique` → `revise` 节点**
（见 [Agent框架落地设计 §2.6](./Agent框架落地设计.md)）。

⚠️ **纪律**：`grounding_score` 是 **LLM 自评，不是事实**。
- 必须标注 `self_reported: true`
- **代码要独立校验 `based_on`**：引用的 `material_id` 必须真实存在（这是硬校验，不靠 LLM 自觉）
- 不得把 grounding_score 当作「质量分」对外展示

> **两个信号要分开**：`grounding_score`（自评，与素材的关联）≠ 质量（要人判断）。
> 自评只能用来做**粗筛**，不能用来做**结论**。

## 5. 人类反馈闭环（用户提出的 RLHF 部分）

用户提出：

> 「如果有些社区公司用这个 agent 系统的话，它就可以进行判断，
> 然后还可以基于员工，结合上下文，结合二创，
> 这里就有一个**基于人类强化学习的 RLHF**。通过人类的反馈标注来——
> **其实也不算标注吧，就是我们给他，然后他看看其中哪些好，哪些不好。**」

用户自己也说了「**其实也不算标注**」——这个自我修正是对的。要精确区分：

### 5.1 做什么 vs 不做什么（命名诚实性）

| | 做不做 | 说明 |
|---|---|---|
| 收集**成对偏好数据**（A 好 / B 差） | ✅ **做** | 员工点「这个好 / 这个不行」 |
| 用偏好数据**更新样例库** | ✅ **做** | 好的进正例、差的进负例 → 下次进 prompt |
| 训练 reward model | ❌ 不做 | 个人项目无数据量、无算力 |
| PPO / DPO 微调模型 | ❌ 不做 | 同上 |
| 把整套叫「RLHF」 | ❌ **不要** | 见下 |

> **对外表述**：这是「**人类反馈驱动的样例库迭代**」（in-context 的自我改进），
> **不是 RLHF 训练**。
>
> 理由与 §4.0 的 RAG 命名同源：说 RLHF 而被问「reward model 怎么训的、
> 偏好数据多少条、KL 惩罚系数多少」会答不上来。
> **准确的说法不减分**：「我收集了偏好数据并用于迭代提示词样例库，
> 这批数据同时也是将来做 RLHF 的数据基础。」——**这句话既诚实又显示了前瞻。**

### 5.2 闭环怎么转

```
G4 生成 N 个二创角度
      ↓
推给内容增长角色（交付形态设计 §2.2）
      ↓
员工逐条选：✅采纳 / ❌否定（可附一句理由）
      ↓
写入 preference 表
   {material_ids, angle, example, grounding_score, human_verdict, reason, actor_role}
      ↓
定期（如每周）归集：
   · 采纳的 → 样例库**正例**（下次 prompt 里的「像这样的」）
   · 否定的 → 样例库**负例**（「不要这样的」）
      ↓
下一轮生成质量提升 ←──── 闭环
```

### 5.3 与样例库的统一（一个重要的架构收敛）

**这里有一个漂亮的收敛**：§4.0 的样例库（用于**判断**「是不是梗」）
和本节的样例库（用于**生成**二创角度）**是同一套基础设施的两种用法**：

| 用途 | 样例的组成 | 谁产出 |
|---|---|---|
| **判断**（仲裁层 §4.0） | 已确认的「是梗 / 不是梗」样例 + 边界负例 | 人工种子（批 0）+ 员工反馈 |
| **生成**（本节） | 采纳过的二创角度（正例）+ 被否的（负例） | 员工反馈 |

**同一张 `examples` 表，`purpose` 字段区分用途。**
好处：偏好数据一次收集，两处都能用；且**冷启动只用做一次**（批 0 的种子）。

### 5.4 诚实边界：这一环在个人项目里跑不起来

必须写清楚，否则价值主张会被问崩：

| 环节 | 个人项目能否真跑 |
|---|---|
| 生成二创角度 | ✅ 能（有 LLM 就能） |
| `grounding_score` 自评 | ✅ 能 |
| **员工采纳/否定的反馈** | ❌ **不能** —— 没有真实员工 |
| **偏好数据积累** | ❌ 不能（没数据量） |
| 样例库迭代 | ⚠️ **机制可做，但只能自造反馈验证** |

**所以**：
- 可交付的是**机制**（表结构、反馈接口、样例库更新逻辑）
- 加上**用小规模自造/自评反馈做的机制验证**
- **不能声称「系统通过 RLHF 自我进化了」**——那是没有数据的

> **对外准确表述**：
> 「我实现了一套**人类反馈驱动的样例库迭代机制**，并用模拟反馈验证了闭环可运转；
> 真实的偏好数据需要平台方接入后才能积累。」
> —— 这句话说明了设计能力，也划清了边界。
