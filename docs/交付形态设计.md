## 0. 为什么要先写这份文档

上一轮讨论中，用户问「用什么框架，LangChain 还是 LangGraph，员工怎么用」。
我的回答是：**框架选型是这四件事里最不紧急的一件**。

理由是一个顺序问题：

| 顺序 | 要定的事 | 为什么排这个位置 |
|---|---|---|
| 1 | **交付形态**（本文） | 决定系统是「批处理」还是「事件驱动」——这是架构地基 |
| 2 | **事实源分层** | 决定会不会走上「同一指标算三遍、数字对不上」的老路 |
| 3 | **闭环回写** | 没有它，阈值永远拍脑袋，系统学不会变准 |
| 4 | **框架选型** | 前三件定了，这个答案是**自然推论**，不是选择题 |

> **一句话**：先想清楚「员工早上看到什么」，再想「用什么图调度它」。
> 顺序反了，就会写出一套技术上漂亮、但没人看得见的系统。

## 1. 诚实的起点：现在是什么，缺什么

### 1.1 现状

| | 状态 |
|---|---|
| **算得对** | ✅ facts 锁数 · 显式降级 · 话题状态机 · 149 测试 · 跨天记忆 |
| **进不到员工手里** | ❌ 输出是本地 `.md` 文件，无推送、无权限、无看板、无历史检索、无订阅 |

现在这套系统的真实使用者**只有一个人**：跑脚本的开发者本人。
它每天生成一份 `reports/daily_intel_latest.md`，然后等人去读。

**这不是「给员工用的系统」，这是「一个人的日报工具」。**

### 1.2 缺的三层（按「不做什么就白搭」排序）

| | 层 | 内容 | 不做的后果 |
|---|---|---|---|
| ① | **接入层** | 推送渠道、定时投递、按角色分流 | 员工根本看不到产出 —— 换什么框架都不改变这一点 |
| ② | **协作层** | 「这条我要跟进」、状态回写、去重 | 同一条热点被推 7 天，员工开始无视推送 |
| ③ | **闭环层** | 建议是否被采纳、采纳后数据回传 | 状态阈值永远是拍的，系统学不会变准 |

> **关键认知**：框架（LangGraph）解决的是 ① **之前**的「谁决定下一步」，
> 不是这三层中的任何一层。**把框架当选型题做，是问错了问题。**

## 2. 三类使用者：他们分别要什么

同一个事实源，切三种视角。**这是「按角色分流」的本质**——
不是算三遍，是同一份 facts 渲染三次。

### 2.1 角色画像

| | ① 社区运营 | ② 内容增长 | ③ 产品发行 |
|---|---|---|---|
| **KPI** | 社区活跃：发帖量、评论量、话题参与 | 内容产出量、互动率、UGC 带动 | 留存、投放效率、卖点认知 |
| **关心什么热点** | 现在社区里**正在吵什么** | 什么话题**能做成内容** | 什么趋势**影响产品决策** |
| **时间粒度** | 分钟级（热点有保质期） | 天级 | 周级 |
| **决策动作** | 开话题 / 加精选位 / 引导讨论 | 挑选题 / 产出创意初稿 | 投放节奏 / 卖点调整依据 |

### 2.2 每类角色看到什么、做什么

**① 社区运营**

- **触发**：企微/飞书群机器人推送（事件驱动，命中即推）
- **看到**：爆发话题 + 争议点 + 高投入负向样本（玩家真在乎什么）
- **动作**：决定要不要开话题 / 加精选位
- **时效要求**：**最高**。热点 6 小时后推给运营已经晚了

**② 内容增长**

- **触发**：素材简报订阅（每日定时，如 10:00）
- **看到**：热点 + 素材包（原帖 / 热评 / 梗 / 二创角度 / 截图位）
- **动作**：挑选题、产出增长创意初稿（**这是 LLM 真正的主场**）
- **时效要求**：中。允许一天延迟，但素材要能用

**③ 产品发行**

- **触发**：日报 + 周报（定时）
- **看到**：跨游戏对比 + 玩家流动方向 + 长周期趋势
- **动作**：投放节奏 / 卖点调整依据
- **时效要求**：低。要的是**信号稳定性**，不是速度

### 2.3 为什么「谁来用」决定架构

三条推论，直接落到架构上：

1. **三类角色共用底座** → 底座必须输出**结构化事实**，不是一句自然语言结论。
   否则三个视角会各自去调 LLM 生成，数字必然对不上（违反 facts 锁数不变量）。

2. **三种视角 = 同一份 facts 的三次渲染** → 模板不同，数字同一个。
   **不能各算一遍**。这是「渲染层」与「计算层」必须分开的原因。

3. **运营要「现在就推」（事件驱动）+ 产品要「每天一份」（定时）** →
   两种触发方式都要。这正是 LangGraph 的 `checkpoint` + `interrupt`
   能真正省事的地方 —— **也是它唯一值得上的理由**。见 §6。

## 3. 接入层设计（缺 ①）

> **2026-09-30 用户拍板：渠道不预选，做成可插拔，让使用者自己配。**
>
> 用户原话：「企微、飞书、微信都可以吧。推送渠道，都建都可以啊，
> **你主要是让使用者选嘛**，对不对。」
>
> **这个判断是对的，而且理由不止"灵活"**：
> 个人项目拿不到真实企业的渠道凭据，**任何一个具体渠道都只能自测**；
> 但做成可插拔之后，**"支持 N 种渠道"本身是可交付的能力**，
> 而"我们公司用企微"是使用者自己的事 —— **把不可控的部分交给使用者，把可控的部分做扎实。**

### 3.1 渠道做成可插拔（取代原「渠道选型」小节）

**接口设计**（一个方法，最小契约）：

```python
class Notifier(Protocol):
    name: str                    # "wecom" | "feishu" | "wechat" | "email" | "stdout"
    def send(self, title: str, body: str, *, dry_run: bool = False) -> dict:
        """返回 {ok, channel, message_id, error}——不抛异常，失败也要可降级。"""
```

**实现清单**：

| 渠道 | 实现方式 | 凭据来源 | 备注 |
|---|---|---|---|
| **企微** | 群机器人 webhook | `.env` 的 `WECOM_WEBHOOK_URL` | 支持 markdown |
| **飞书** | 群机器人 webhook | `FEISHU_WEBHOOK_URL` | 支持富文本卡片 |
| **微信** | 见下方「关于微信的诚实说明」 | — | ⚠️ 有合规门槛 |
| **邮件** | SMTP | `SMTP_HOST` / `USER` / `PASS` | 适合日报周报归档 |
| **stdout** | 打印到终端 | 无 | **默认渠道，永远可用** |

**配置驱动**（`11情报Agent/config/notify.json`，不入库）：

```json
{
  "routes": [
    {"role": "社区运营", "channels": ["wecom"],     "trigger": "event"},
    {"role": "内容增长", "channels": ["feishu"],    "trigger": "daily"},
    {"role": "产品发行", "channels": ["email"],     "trigger": "weekly"}
  ],
  "default": "stdout"
}
```

**关键设计点**：

1. **`stdout` 是默认且永远可用的兜底** —— 没配任何渠道时链路照样跑通、可验证，
   只是输出到终端。**这让"推送层"在没有任何凭据的情况下也能开发与测试。**
2. **一处渲染，多渠道分发** —— 三种角色只是同一份 facts 的**三次渲染**（§2.3），
   渲染结果再交给各渠道适配器。不是每个渠道各写一套内容。
3. **新增渠道 = 加一个类 + 加一行配置**，不动主链。
4. **失败必须降级不抛异常** —— 企微挂了不该让整个情报链崩掉（符合项目降级纪律：
   记 `{ok: false, error}`，继续走下一个渠道或 stdout）。

### 关于微信的诚实说明（不能含糊）

微信**没有**像企微/飞书那样的开放群机器人 webhook 可以直接用：

| 路径 | 现实约束 |
|---|---|
| 个人微信 | ❌ **没有官方 API**；第三方 hook 方案违反使用条款，且封号风险高 |
| 微信公众号（服务号） | 需要**已认证主体**才能发模板消息 —— 个人项目拿不到 |
| 企业微信 | ✅ 可用（所以「微信」这条实际走企微） |

> **结论**：`wechat` 这个渠道**先只留接口位与文档说明，不实现**——
> 实现一个违反条款或用不了的通道，比诚实说"这个做不了"更糟。
> **准确表述是**：「支持企微 / 飞书 / 邮件三类可达渠道；微信因个人主体无官方 API，提供接口位但不实现。」

### 3.2 推送门槛：不是所有热点都值得推


这是接入层最容易被忽略、但最影响体验的一条。

**推得太少** → 员工不信，回去自己刷热榜
**推得太多** → 员工开始无视，系统等于不存在

| 状态 | 是否推送 | 理由 |
|---|---|---|
| 沉寂 / 退潮 | ❌ 不推 | 没人需要知道一个话题凉了 |
| 冒头 | ❌ 不推 | 首日全是冒头（需 ≥2 次采样才判趋势），推了等于推噪声 |
| **升温** | ⚠️ 条件推 | 仅当同时满足「可发酵度 ≥ threshold」才推 |
| **爆发** | ✅ 必推 | 这是「现在接还来得及」的窗口 |

> ⚠️ **阈值全部未校准**。`RISING_SLOPE_RATIO=1.5` / `BURST_SLOPE_RATIO=3.0` /
> `ferment_judge` 的 `act≥60` 都是拍的。**未校准前不得当可信参数使用**，
> 也不得写进任何对外的承诺里。

### 3.3 去重：同一个热点不要推 7 天

需要一张「已推送」表（可复用 `topic_state` 的同库）：

- 记录：`topic_key` + `pushed_at` + `pushed_state` + `channel`
- 规则：**同一话题在同一状态下只推一次**；状态升级（升温→爆发）可再推
- 冷却：退潮后再升温，允许再推（但标记「二次抬头」）

> 这条不做，第一周就会失去所有使用者。

## 4. 协作层设计（缺 ②）

### 4.1 「我要跟进」这个动作存在哪里

员工看到一个热点，想说「这条我来处理」。这个动作必须被记录，否则：

- 同一条会被别人重复处理
- 系统不知道哪条真的有用 → 无法校准阈值

**最小实现**：推送卡片上加两个按钮 → 回调写入 SQLite 表 `action_log`

| 字段 | 说明 |
|---|---|
| `topic_key` | 关联话题 |
| `action` | `follow` / `ignore` / `done` |
| `actor` | 谁操作的（角色，非个人标识） |
| `acted_at` | 时间 |
| `suggested_action` | 系统当时建议的动作（用于对比） |

### 4.2 这一层的边界

⚠️ **注意 PII 边界**（见架构设计 §4.5）：`actor` 只记**角色**
（运营/内容/产品），不记个人标识。否则会重蹈 `reviews.csv` 的覆辙。

## 5. 闭环层设计（缺 ③）

### 5.1 为什么这层最重要，却排在最后

因为**它决定系统能不能变准**，但它依赖 ①② 先跑起来才有数据。

没有闭环的后果是具体的：`topic_tracker` 的阈值（1.5×/3.0×/0.6×）
会永远是拍的，`ferment_judge` 的 `act≥60` 也永远是拍的。
**系统永远不会知道自己是推多了还是推少了。**

### 5.2 闭环怎么转

```
推给员工 → 员工点「跟进/忽略」 → 写入 action_log
    ↓
对比：系统建议 vs 员工实际动作
    ↓
得到两条校准信号：
  · 系统说 act、员工点 ignore → 阈值可能太松（推多了）
  · 系统说 skip、员工没看到 → 漏推（无法直接观测，需人工抽查）
    ↓
定期（如每周）用 action_log 重新标定阈值
```

### 5.3 诚实的边界

**「建议被采纳后效果如何」这一环，本项目做不了。**

原因：个人项目拿不到真实的社区运营数据回流
（发了话题后社区活跃涨了多少，只有 TapTap 内部知道）。
所以闭环**只能转到「动作是否被采纳」这一层**，
**不能转到「采纳后是否有效」**。

> 这条必须写清楚。否则会被人问「你怎么证明你的创意真的带来了增长」——
> 答不上来，整个系统的价值主张就崩了。
> 正确的说法是：**我做的是「把热点变成可执行的建议」，
> 建议是否有效需要 A/B，那需要平台方配合，不在本项目范围内。**

## 6. 框架选型：从前五节推导，不独立选

> ⚠️ **本节已于 2026-09-30 修订**。初版结论是「LangGraph 现在上还早」，
> 判据只有「必要性」一条，忽略了本项目是**作品集项目**这一前提。
> 用户的纠正见 [Agent框架落地设计 §0](./Agent框架落地设计.md)，
> 完整用法与用量见该文档（4 图 / 32 节点 / 7 条件边 / 2 环 / 3 中断点）。

### 6.1 三个选项不在同一层

| 选项 | 实际是什么 | 判定 |
|---|---|---|
| **LangChain** | LLM 应用**零件箱**（链 / prompt / retriever / LLM 客户端） | 🟡 **部分用** —— 用掉样板代码的三件，拒绝与图冲突的四件（清单见落地设计 §5） |
| **harness** | **不是框架名**，是概念：模型外面那圈控制代码（循环、工具调用、重试、上下文） | ✅ **必须自己写一部分** —— 其中「业务纪律」那半是项目的技术主张，不能外包（分工见落地设计 §6） |
| **LangGraph** | **编排框架**：状态图，节点=函数，边=条件路由，带 checkpoint 与 interrupt | ✅ **成体系上**，按 P1→P2→P3 分期 |

### 6.2 判据修正：从一条变三条

初版只用「必要性」判断（不用它今天能不能跑通），这是**产品视角**。
但本项目的验收标准不是「能跑」，是「**能证明工程能力**」+「**能支撑下一步迭代**」。

| 判据 | 问的问题 |
|---|---|
| **必要性** | 不用它，今天能不能跑通？ |
| **展示性** | 用它之后，能力是否**可被观察**？ |
| **可扩展性** | 下一步迭代时，它是否省事？ |

三条并行后，LangGraph 的结论从「等」变成「上，但分期上」。

### 6.3 分期：不是一次性铺满

| 阶段 | 做什么 | 用上哪些特性 | 前置 |
|---|---|---|---|
| **P1** | G2 情报图（`daily_agent` 迁进图）+ 换 `ChatOpenAI`/结构化输出 + 接 `SqliteSaver` | StateGraph · checkpointer | 装 `langgraph-checkpoint-sqlite` |
| **P2** | G1 巡检图 —— 第一次用上**环 + interrupt** | 条件边 · 环 · interrupt · retry_policy | P1 |
| **P3** | G3 追踪图 + G4 创意图（**服务目标缺口②③**） | supervisor · RAG · 自评环 | 「素材」定义 |

**为什么 P1 先做**：风险最低（现有逻辑不变，只换壳），但一次性验证环境 + checkpointer + 测试怎么改。
**为什么 P2 紧接着**：环与 interrupt 是「框架真的在干活」的证据；做完 P1+P2，「这是个 LangGraph 项目」就是结构事实而非声明。

### 6.4 面试口径（会被问「为什么用 LangGraph」）

❌ 差的回答：「因为它是主流 Agent 框架。」
✅ 好的回答：

> 「我的控制流有四种不同形态——按需批处理带重试环（巡检）、每天一次的直线（情报）、
> 30 分钟心跳的事件驱动（追踪）、带自评改稿环的迭代生成（创意）。
> 这四种的触发方式与失败处理都不一样，但共用同一套跨天状态，
> 所以用 LangGraph 的 checkpointer 统一管，比我手写四套调度省事。
> 另外我有两个真实的人工中断点（标注要花钱、员工要挑选题），
> 这两个中断都得跨进程存活，用 interrupt + SQLite saver 是现成的。
> **在此之前我的控制流是一条直线，我确实没上框架。**」

**这个回答证明的是「你想过控制流形态」，不是「你学过框架」。**

## 7. 未决问题（需要用户拍板）

| # | 问题 | 选项 |
|---|---|---|
| 1 | 三类角色**先服务哪一类** | A 社区运营（时效最强，但推送最复杂）/ B 内容增长（最贴「素材+创意」目标）/ C 产品发行（最简单，已有周报基建） |
| 2 | ~~推送渠道**选哪个**~~ → **已解（2026-09-30）**：**不选，做成可插拔**（企微/飞书/邮件 + stdout 兜底，配置决定启用哪个，让使用者自己配）。微信因个人主体无官方 API，只留接口位不实现。见 §3.1 |
| 3 | ~~素材层的**「素材」具体指什么**~~ → **已解（2026-09-30）**：四类全要，但**分两级** —— 原帖引用 / 热评金句 / 梗是**素材本体**（抽取），二创角度是**加工建议**（生成，使用者视角）。见 [素材层设计](./素材层设计.md) |
| 4 | 闭环的**周期** | 每周重标定 / 累积 N 条后重标定 / 暂不做 |
| 5 | 是否**先做一个角色的端到端**（而非三个都做一半） | 我的建议：✅ 是。先做一类角色跑通「推 → 看 → 点 → 回写」全环 |
| 6 | 框架迁移**是否按 P1→P2→P3 动工** | 见 [Agent框架落地设计 §7](./Agent框架落地设计.md) |

### 我的推荐

**先做 ② 内容增长 的端到端**，理由：

1. 它最贴项目目标原文（「**情报与素材**系统」+「**产出创意**」）——
   缺口 ②③ 都在这条线上
2. 它不要求事件驱动的实时性（可以先做每日定时），
   工程量比 ① 运营小一个量级
3. 它的产出（素材 + 创意）是**最能证明 LLM 价值**的部分，
   也最能在面试里讲清楚「这个 Agent 算不算真 Agent」

而 ① 运营的事件驱动推送，等 ② 跑通、G3/G4 落地之后再做。
