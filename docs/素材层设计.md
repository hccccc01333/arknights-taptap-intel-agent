## 1. 定义（用户 2026-09-30 拍板）

四类都要，但**它们不是平级的** —— 用户明确指出：

> 「原帖肯定是要引用的，因为**原帖引用首先要确保人工会找到素材是怎么来的**。
> 其次热评金句确实，然后梗也对，然后二创角度——
> **二创角度其实是对于我们这个项目使用者来说的**。
> 前三个是『是什么』，然后最后一个角度应该是**使用者二创的角度有哪些**。」

这个区分是本节最重要的设计输入：

| # | 类型 | 性质 | 从哪来 | 谁的视角 |
|---|---|---|---|---|
| 1 | **原帖引用** | 素材本体 | 数据里**抽取** | 客观（帖子里本来就有） |
| 2 | **热评金句** | 素材本体 | 数据里**抽取** | 客观（评论里本来就有） |
| 3 | **梗** | 素材本体 | 数据里**发现 + 解释** | 客观（社区共识，但需要识别） |
| 4 | **二创角度** | **加工建议** | 从前 3 类**派生生成** | **使用者视角**（我能拿它做什么内容） |

> **一句话**：前三类回答「**有什么可用的**」，第四类回答「**能用它做什么**」。

### 1.0 最终定案：段子并入梗（用户 2026-09-30 二次拍板）

用户先提出「段子 / 金句 / 梗 是三种概念」，随后**自己收回了这个细分**：

> 「段子和梗其实是两个东西吧，我觉得就是其实是一个东西。
> 因为我们这里**如果无限细分的话，那确实很难，而且很杂，因为他们都相互有重合**。
> 本质来说可能没有什么差异——**段子可能是对使用者而言它称为段子，
> 如果你大家都在用这个段子，他就变成了梗。就这么个道理。
> 所以说我觉得还是维持原判，我们就原先的 4 种类型。**」

**定案**：

| | 判定 |
|---|---|
| 类型数量 | **维持 4 类**：原帖引用 / 热评金句 / 梗 / 二创角度 |
| 段子 | **并入梗**，不单列 |
| 段子与梗的关系 | **同一事物的不同扩散度**，是一条连续谱 |
| 金句与梗的关系 | **同一批文本的两种视图**，不是互斥分类 |

```
        扩散度低 ──────────────────────────→ 扩散度高
          段子           →            梗
     （少数人用、单帖高赞）      （大家都在用、跨帖/跨社区）

        热评金句 = 采集口径（单帖高赞，宽）
        梗       = 提炼口径（跨帖重复 + 语义确认，窄）
        └─ 两者作用于同一批文本，是视图不是分类
```

### ★ 这个定案大幅简化了架构（重要的正面后果）

如果段子单列，就必须回答「这条高赞评论**是金句还是段子**」——
而 §4.0 已实测：**这个判断在结构指标上根本区分不开**（都是单帖高赞）。

**段子并入梗之后，这个无解的判断消失了**：

| 原来（三概念） | 现在（两口径） |
|---|---|
| 要判「金句 vs 段子 vs 梗」= 需要一个专门仲裁 | 金句 = **点赞排序**（结构可判）；梗 = **跨帖重复 + LLM 确认** |
| 需要为「金句 vs 段子」设计样例库 | 样例库只服务「**这是不是梗**」一个判断 |

> 用户的「不要无限细分，他们有重合」这个判断，
> 直接把 §4.0 里那个最难的判定问题**消掉了** —— 这是设计上的净收益。

⚠️ **但 §4.0 的仲裁层仍然需要**，只是职责收窄为：
**判「这条跨帖重复的短语是不是真梗」**（排除标签/专名/口头禅），
而不是判三个互斥类别。

### 1.1 这个区分在设计上的后果（重要）

前三类是**抽取**，所以判据可以是**确定性规则**（排名、频次、去重）——
符合项目的 facts 锁数纪律：数字与选取依据都能核对。

第四类是**生成**，必须 LLM。它是**唯一没有确定性判据**的一类，
所以也是唯一必须标注「这是建议、不是事实」的一类。

**由此得到分批实现策略**（见 §6）：**原帖引用 + 热评金句/段子这两类不需要 LLM，现在就能做**。

⚠️ **但第三类（梗）比预想难**——我上一版设计写「发现可以纯统计」，**实测被推翻**：
n-gram 跨帖频次的产出全是 `<br/>`、游戏名、评价模板标签这类垃圾，
**统计发现不了梗，判定必须 LLM**。详见 §4.3 的实测翻案。

## 2. 溯源设计（用户的第一要求）

> 「原帖引用**首先要确保**人工会找到素材是怎么来的。」

这不是可选项，是**素材的准入条件**：**没有溯源的素材一律丢弃。**

### 2.1 溯源链（已实测验证真实可用）

```
评论素材  comment_id ─┐
                      ├─→ moment_id ─→ https://www.taptap.cn/moment/{moment_id}
帖子素材  moment_id ──┘                        ↓
                                        实测 HTTP 200 ✅
                                        （2026-09-30 用真实 id 验证）
```

**实测记录**：

```
$ curl -sI "https://www.taptap.cn/moment/853956790541355163"
HTTP 200   final=https://www.taptap.cn/moment/853956790541355163
```

用的是 `data/raw/taptap/discovery_posts.csv` 里第 1 条真实记录（光·遇「说陪我都是假的」，149 条数据中的一条）。
**链接真能打开** —— 这是「人工能找到来源」的硬前提，不是假设。

### 2.2 溯源的三个层次（都由 provenance 块承载）

| 层次 | 回答的问题 | 字段 |
|---|---|---|
| **定位** | 到底是哪一条？ | `moment_id` / `comment_id` / `url` |
| **来历** | 从哪个通道抓的、什么时候？ | `source_channel` / `source_type` / `captured_at` |
| **当时的样子** | 抓的时候它有多少赞、多少回复？ | `metrics`（supports / comments / pv_total） |

**第三个层次容易被忽略但很关键**：热度会变。`metrics` 是**抓取时刻的快照**，
所以它同时是「当时的证据」和「后来复核的基准」——
如果三个月后运营去看，发现点赞数变了，那是正常的，不是数据错了。

### 2.3 代码层强制

```python
def assert_traceable(material: dict) -> None:
    \"\"\"素材准入：没有溯源就不算素材。\"\"\"
    p = material.get("provenance") or {}
    if not p.get("moment_id"):
        raise ValueError(f"素材缺 moment_id，无法溯源，丢弃：{material.get('material_id')}")
    if not p.get("url", "").startswith("https://www.taptap.cn/moment/"):
        raise ValueError(f"素材 url 不是可打开的 TapTap 链接：{p.get('url')}")
```

**这一条要有测试锁死** —— 见 §7。

## 3. 素材 Schema

```jsonc
{
  "material_id": "m_20260930_0001",
  "type": "original_post | hot_comment | meme | remix_angle",

  // 归属：挂在哪个话题下（复用 topic_tracker 的 topic_key，两个系统因此可对齐）
  "topic_key": "hid:12345|page_view",
  "topic_title": "三角洲行动二周年",

  // ★ 上下文锚点（见 §3.5）：素材从哪个 Thread 派生出来的
  "thread_id": "853956790541355163",     // = moment_id，必带
  "self_contained": false,               // 段子/梗 = true；金句/原帖引用/二创角度 = false

  // 素材正文
  "text": "素材本体（原帖摘要 / 评论原文 / 梗的形态 / 二创角度描述）",

  // ★ 溯源（准入条件，见 §2）
  "provenance": {
    "moment_id": "853956790541355163",
    "comment_id": null,                                   // 仅评论类素材有
    "url": "https://www.taptap.cn/moment/853956790541355163",
    "source_channel": "S6_feed_by_hashtag",
    "source_type": "hashtag",
    "captured_at": "2026-09-30T12:37:00+08:00",
    "metrics": {"supports": 12, "comments": 3, "pv_total": 4200},
    "author_display": "⚠️ 仅本地，不入库（见 §5）"
  },

  // ★ 选取依据（必须可核对，不能是「LLM 觉得好」）
  "selection_reason": "该话题下 supports 排名第 2（12 赞）",
  "selection_kind": "rule | llm",   // 明确标出这条是算出来的还是生成的

  // 使用建议（第四类素材只有这个字段是实质内容）
  "usable_for": ["配图引用", "话题引导"],
  "confidence": "high | medium | low"
}
```

**三个强制字段**：`provenance`（可溯源）+ `thread_id`（可回上下文）+ `selection_reason`（可核对）。
缺任一个，这条素材不算数。

> `thread_id` 与 `provenance.moment_id` 当前同值（Thread 就是帖子），
> 但**分两个字段是有意的**：`provenance` 是「素材从哪来」（对外可核验的链接），
> `thread_id` 是「素材要挂回哪个上下文」（对内生成时用）。
> 若将来 Thread 的定义扩展到「帖子 + 评论区 + 转发链」，
> 两者会分叉，那时不必改 Schema。

> 注意 `selection_kind` 字段：它把「**算出来的**」和「**生成的**」分开标注。
> 这是 facts 锁数纪律在素材层的延续——**第四类素材必须标 `llm`**，
> 免得有人把生成的建议当客观事实用。

## 3.5 Thread：素材的检索单元与上下文载体（用户 2026-09-30 提出）

> 用户的洞察：
> 「关键是这个地方。其实这个项目也是可以拿来**用做 RAG** 的，只不过它**不像是用户提问**。
> 我们把 RAG 那个检索思想拿过来。因为很简单，**你把那个数据去抽取来之后，你怎么检索呢**，
> 对不对。因为无论是梗、段子、金句，还是说二创角度，
> **它都要基于原来那个帖子**，懂吗？
> **段子除外啊，段子已经成型，梗已经成型了。其他的都要基于原来那个帖子**——
> **他是什么情况，发帖人是什么样子，帖主底下。**」

### 3.5.1 实测：Thread 结构成立（100% 可关联）

```
评论 74 条 → 能关联到主帖的: 74 条 (100%)
孤儿评论（找不到主帖）: 0 条
有评论的帖子: 25 个 / 总帖子 118 个
```

`discovery_comments.moment_id` → `discovery_posts.moment_id` **完全可 join**，
所以「帖子 + 它的评论区」这个结构在数据上是**真实成立的**，不是设计假设。

⚠️ **但要看清覆盖率**：**只有 25/118 个帖子有评论**（21%）。
也就是说约八成 Thread 是「**只有主帖、评论区为空**」。
含义：
- **金句素材只能从这 25 个 Thread 里出**，池子小
- **原帖引用不受影响**（它只要主帖）
- 想让金句层真正有量，**必须先提高评论采集的覆盖率**（当前 `--comment-limit` 偏小）

### 3.5.2 实测例证：为什么「金句必须带回 Thread」

数据里正好有一条完美的例子：

```
【主帖】维什戴尔、逻各斯、锏算不算时代的眼泪了     浏览 499 · 17 条评论
  [3赞] 其实除了锏，剩下两位还碰不到时代眼泪，特别是维什戴尔，狙击现在都没有能碰瓷的……
  [2赞] 锏其实也不算时代的眼泪[表情_吃瓜]二模超长战栗不是跟你玩的[表情_斜眼笑]
```

| 素材 | 脱离主帖会怎样 |
|---|---|
| 那条 **3 赞**的 | ❌ **不知道在说什么** —— 主帖在问「算不算」，它在回答「除了锏都算」。没有主帖，这句话是悬空的 |
| 那条 **2 赞**的 | ✅ 相对自足 ——「吃瓜」「不是跟你玩的」自带调侃语境 |

**这正是用户说的区别。**

### 3.5.3 关键分类：自足素材 vs 依赖上下文素材

| 素材类型 | 是否依赖 Thread 上下文 | 为什么 |
|---|---|---|
| 原帖引用 | ✅ **就是 Thread 头部本身** | — |
| 热评金句 | ✅ **强依赖** | 「这句话是回应什么的」决定它的意思 |
| **段子** | ❌ **自足**（用户：已成型） | 幽默感自带语境，拿出来就能用 |
| **梗** | ❌ **自足**（用户：已成型） | 梗的本质就是「大家都懂、不用解释」——**自足是梗的定义性特征** |
| 二创角度 | ✅ **强依赖** | 要基于帖子的具体情境才能想到角度 |

> **一句话**：**段子和梗已经成型了**（它们是社区的成品），
> **金句和二创角度是半成品**（必须挂在 Thread 上才完整）。

**这个区分直接决定了两件事**：
1. **存储**：自足素材可以独立检索；依赖上下文的素材**必须带 `thread_id`**
2. **生成**：仲裁层判「金句 vs 段子」时，**必须把 Thread 上下文一起喂给 LLM** ——
   否则它看到的是一句悬空的话，判不准（这也解释了 §4.0 为什么结构化指标判不了）

### 3.5.4 架构：Thread 是检索与生成的基本单元

```
话题 topic_key
   └─ Thread（moment_id = 帖子 + 它的评论区）
        ├─ 主帖：title / summary / 作者 / metrics / 发布情况
        ├─ 评论列表：[{comment_id, content, supports, author}]
        └─ 元数据：话题归属 / 抓取时间 / 来源通道
             └─ 素材（material_id）
                  ├─ type
                  ├─ thread_id      ← ★ 必带：这是上下文锚点，也是溯源目标
                  └─ self_contained ← ★ 新增：是否自足（段子/梗 = true）
```

**`self_contained` 字段的意义**：
- `true`（段子 / 梗）→ 可以脱离 Thread 单独检索、单独投放
- `false`（金句 / 原帖引用 / 二创角度）→ **使用时必须回带 Thread 上下文**

### 3.5.5 两种检索必须分开（否则会误以为「处处要 RAG」）

用户问「你把数据抽取来之后，你怎么检索呢」——**检索分两类，成本和实现完全不同**：

| 检索类型 | 用于 | 实现 | 需要向量库？ |
|---|---|---|---|
| **结构化检索** | 按话题取 Thread、按 thread_id 取上下文、按 signature 去重 | 纯 SQL / dict | ❌ |
| **语义检索** | 找相似历史素材、找仲裁层样例（§4.0） | 检索器 + 索引 | ✅ |

**关键判断**：**这个项目里大部分检索是结构化的**——
「这个话题下的 Thread」「这条素材的上下文」都是精确查询，不需要语义检索。

**只有两处真的需要语义检索**：
1. 仲裁层的**样例检索**（§4.0）
2. 素材库变大后的**历史相似素材**查找

> **所以不要因为「素材要上下文」就说整个项目是 RAG** ——
> 只有那两处是。其余是普通的关联查询。

### 3.5.6 本项目的 RAG 结构（非问答式，用户说得准）

用户说「**它不像是用户提问**」——对，这正是本项目与问答式 RAG 的区别：

| | 传统问答 RAG | **本项目** |
|---|---|---|
| query | 用户自然语言问题 | **热点 / 话题 / 选题**（不是问题，是信号） |
| corpus | 文档库 | **Thread 池**（帖子 + 评论区） |
| retrieve | 找相关文档块 | 按话题取 Thread、按样例找标尺 |
| generate | 回答 | **素材 / 二创角度 / 增长创意** |
| 触发 | 用户提问 | **话题升温 / 状态迁移**（自动） |

> **一句话**：**用 RAG 的检索-生成骨架，但把「用户提问」换成了「热点信号」作为触发。**
> 这个表述在面试里比「我做了个 RAG」准确得多，也更不容易被问穿。

### 3.5.7 ★ 存什么：存 Thread，不存孤立的评论（用户 2026-09-30 追问）

> 用户的问题：
> 「**你有没有把原帖爬下来？** 因为很简单，帖主发的东西，然后底下评论，
> 这是**一个社区的基本单元**。如果我们要挖掘其中的各种素材层的话，
> 那肯定是以这个单元来进行的。那 **RAG 里面到底是怎么存？存这个单元还是存评论？**
> **存评论你就会损失这个评论所处的语境，那你损失的语境，那还能叫素材吗？** 」

**先回答事实问题：原帖爬下来了**（2026-09-30 实测）：

| 字段 | 非空率 | 说明 |
|---|---|---|
| `title` | 106/118 | 平均 12.8 字 |
| `summary` | 110/118 | **平均 90.4 字** —— 这是语境的主体 |
| `author_name` | **118/118** | 发帖人 |
| `app_title` | 114/118 | 属于哪个游戏社区 |
| `publish_time` | 118/118 | 发布情况 |
| **`ups`** | **108/118** | ⚠️ **原帖点赞在 `ups` 不在 `supports`** |

> ⚠️ **踩坑更正**：本项目里**评论的点赞字段叫 `supports`，帖子的叫 `ups`**。
> 之前实测「原帖 supports 全 0」是**看错字段**——原帖点赞实际有 108/118 非空、最高 311。
> 两者的字段命名不一致，是个真实的采集侧坑，已记入。

#### 存储设计：三层，不是两层

**用户说得对：存评论就会丢语境，丢了语境就不叫素材。** 所以设计成三层：

```
① Thread 层（基本存储单元，完整保存）
   thread 表：moment_id / topic_key / app_id / app_title
              post_title / post_summary / post_author / post_metrics
   comment 表：comment_id / moment_id / content / supports / author
        ↑ 这一层是**语境的载体**，原样保存，是所有派生的基础

② 素材层（投影，不复制原文本）
   material 表：material_id / type / thread_id ★ / comment_id（金句才有）
                text_excerpt（引用片段，非全文）
                self_contained / provenance / selection_reason

③ 检索层
   结构化：按 topic_key 取 Thread、按 thread_id 取全部评论   ← 纯 SQL
   语义：样例检索、历史相似素材                              ← 需要检索器
```

**关键设计决策**：

| 问题 | 决策 | 理由 |
|---|---|---|
| 存 Thread 还是存评论？ | **存 Thread（单元）** | 存评论会丢语境（用户的理由） |
| 素材要复制整段 Thread 吗？ | ❌ **不复制**，只存 `thread_id` 指针 + 片段 | 避免同一内容多处存储导致不一致 |
| 自足型素材（梗/段子）还要 `thread_id` 吗？ | ✅ **仍然要** | ① 溯源需要（用户第一要求）② 知道「这是哪个游戏圈的梗」有独立价值 |
| `self_contained` 影响什么？ | 只影响**生成时要不要带上下文** | **不影响存储**——所有素材都挂 Thread |

> **一句话**：**Thread 是唯一的真身，素材是挂在它上面的可检索标签。**
> 这样「素材」既能被独立检索到，又永远找得回自己的语境——
> 两个需求同时满足，代价只是多一个 `thread_id` 字段。


## 4. 四类素材的抽取判据（可核对，非主观）

### 4.0 前置问题：金句 / 段子 / 梗 三个概念，结构化指标区分不开（用户 2026-09-30 提出）

> 用户的判断：
> 「原帖引用这个没问题，主要在这里——**段子和热评金句和梗，三个之间是三种概念**。
> 但是**三种概念的话，目前的指标来看，很难区分开**。
> 所以说这一层可能要做个 RAG，用大模型来判断，
> 大模型可能我们要塞给他一个 context，然后让他**判断出输出 JSON 字段**。
> 这样才行，**还要有置信度**。」

**用户说得对，而且我实测验证了。**

#### 实测：重叠有多严重

用现有结构化指标（只有两个：`supports` 点赞 / 是否跨帖重复）看平台评论 top 6：

```
[10赞] 就是玩几个小时游戏，又不是这辈子不干别的了。这群人也真是，跟一个游戏较劲
[ 5赞] 其实宴的是肉鸽给的（刻俄柏的灰蕈迷境）只不过在这次夏活复刻了
[ 3赞] 其实除了锏，剩下两位还碰不到时代眼泪，特别是维什戴尔……
[ 2赞] 你玩个游戏还不能吐槽一下了花钱买罪受
[ 2赞] 这么强力的干员居然望记了吗
[ 2赞] 锏其实也不算时代的眼泪，二模超长战栗不是跟你玩的
```

**问题**：上面这几条，哪条是「金句」、哪条是「段子」？

**答案：结构指标完全相同**——都是单帖高赞。10 赞那条**同时是金句**（表述精彩、有观点）
**也是段子**（"跟一个游戏较劲"是调侃）。

**区别只在「表述是否有幽默/梗感」——这是语义判断，统计看不出来。**

而且梗的结构特征（跨帖重复）在当前数据上**根本不出现**：
唯一被统计到的「重复」是 `[表情_狗头]`（表情标记）和 `不`（单字）——**都不是梗**。

#### 三概念的正交分解（这决定了架构）

| 概念 | 结构化**能**判的部分 | 结构化**不能**判的部分 |
|---|---|---|
| **梗** | ✅ **跨帖重复数**（扩散范围） | ❌ 这个重复「有没有意义」（要排除标签/专名/口头禅） |
| **段子** | ❌ 无 | ❌ **有没有幽默感** |
| **金句** | ❌ 无 | ❌ **表述是否有价值** |

**两个结论**：

1. **梗有结构化强信号，但需要 LLM 确认/排除**（上一节 §4.3 已实测：纯统计输出全是标签和专名）
2. **金句 vs 段子，结构化完全帮不上忙** —— 必须语义判断

> **所以 LLM 仲裁层不是「可选优化」，是「必需组件」。** 没有它，
> 金句和段子在系统眼里是同一个东西，而它们的用途完全不同
> （金句用于引用背书，段子用于做轻内容）。

#### 架构：统计粗筛 → LLM 仲裁

```
素材候选（§4.1–4.4 的判据产出）
      ↓
┌─────────────────────────────────────────────┐
│  LLM 仲裁层                                  │
│                                             │
│  context 四块：                              │
│    ① 分类定义（三类判据，尤其金句/段子的分界） │
│    ② 结构化特征（点赞数 / 跨帖数 / 作者数 /   │
│       长度 / 所属话题）← LLM 不用瞎猜数字     │
│    ③ ★ **Thread 上下文**（主帖在说什么 + 同帖  │
│       其他评论）← 判金句/段子必需，见 §3.5   │
│    ④ **相似样例**（从样例库检索 K 条）★ RAG 在这 │
│                                             │
│  → 一次调用判三类（不是调三次，省 token 且可权衡）│
└─────────────────────────────────────────────┘
      ↓
分类结果 + 置信度 → 决定入库 / 待复核 / 上人工
```

**③ Thread 上下文为什么必需**（§3.5 已实测）：一句评论脱离主帖可能是**悬空的**——
「其实除了锏，剩下两位还碰不到时代眼泪」这条，离开主帖
「维什戴尔、逻各斯、锏算不算时代的眼泪了」就不知道在回答什么。
**给 LLM 看悬空的一句话，它判不准金句 vs 段子。**

⚠️ **但 ③ 对段子和梗是多余的**——它们自足（§3.5.3）。
所以 context 要**按 `self_contained` 条件装配**：
- `self_contained: false`（金句 / 二创角度）→ **必须带 Thread 上下文**
- `self_contained: true`（段子 / 梗）→ 可省，**省 token**

这同时是**成本优化**：带 Thread 上下文的调用贵得多，只给需要的候选带上。

#### 输出 Schema（用户要求：JSON 字段 + 置信度）

**多标签 + 各自置信度**，因为三概念**可重叠**（10 赞那条同时是金句和段子）：

```jsonc
{
  "material_id": "m_20260930_0012",
  "labels": {
    "quote": {"value": true,  "confidence": 0.88,
              "reason": "有明确观点与情绪张力，可直接引用作玩家声音"},
    "joke":  {"value": true,  "confidence": 0.71,
              "reason": "「跟一个游戏较劲」是自嘲式调侃，有段子感"},
    "meme":  {"value": false, "confidence": 0.93,
              "reason": "跨帖数 0，未扩散"}
  },
  "primary": "quote",          // 主分类：入库归属（取置信度最高且 value=true 的）
  "needs_review": false,       // 任一标签置信度 <0.85 → true
  "degraded": false,           // 无 LLM 时 true
  "model": "deepseek-flash",   // 判别式任务，thinking 关闭（决策 #16）
  "prompt_version": "v1"       // 提示词改版要能回溯，否则置信度不可比
}
```

**为什么每个标签配独立置信度**：用户说的「三种概念很难区分」意味着
**判错的风险是按类别不同的**——`meme` 判错（把专名当梗）代价最高，
`quote` 判错代价低。一个总置信度无法表达这种差异。

#### 置信度的行为（不能是摆设）

| 聚合置信度 | 行为 |
|---|---|
| 全部 ≥0.85 | ✅ 直接入库 |
| 任一 0.60–0.85 | ⚠️ 入库但标 `needs_review: true`（抽样人工看） |
| 任一 <0.60 | ❌ **不入库**，进「待人工确认」队列 |

> **这与架构设计 §3 标注三层路由是同一套思想**（p≥0.9 采用 / 0.6–0.9 采用+抽查 / <0.6 上送）。
> 同一套方法论用两次（评论情绪标注 + 素材分类），**这是架构一致性的加分项**，
> 不是重复劳动。

#### RAG 具体检索什么（关键：不是检索「相似文本」）

**检索目标 = 判定标尺**，而不是「相似的素材」。

因为「幽默」「精彩」是**标准不确定**的判断——没有参照，LLM 每次判的结果都会漂。
样例库就是**把判定标准外化成可比对的例子**。

| 检索通道 | 取什么 | 作用 |
|---|---|---|
| **① 同类已确认样例** | 每类 3–5 条**已人工确认**的样例 | 提供「像这些的才算」的标尺 |
| **② 结构邻近样例** | 结构特征接近的候选（同为高赞单帖 / 同为跨帖） | 让 LLM 看到同类候选的对照 |
| ③ 边界样例（可选） | 容易混淆的（被判 skip 的专名、模板标签） | **教它排除法**——这是最有效的负例 |

**通道 ③ 值得单独说**：上一节实测暴露的失败案例（`卫戍协议` 专名、`资源获取` 标签）
正好是**最好的负例**。把它们放进 context，比只说「不要判专名」有效得多。

> 本节是**唯一需要语义检索**的地方（§3.5.5 已把两类检索分开）。
> 其余「按话题取 Thread」「按 thread_id 取上下文」都是**结构化查询**，不需要向量库。

#### 降级（402 未解除时怎么办）

无 LLM 时，**三概念全部无法判定**吗？—— 基本是。诚实处理：

| 标签 | 无 LLM 时 | 理由 |
|---|---|---|
| `meme` | ⚠️ 输出**候选**（跨帖重复数），但标 `unconfirmed` | 结构化有信号，但分不出真梗 vs 专名 |
| `quote` / `joke` | ❌ **不判定**，标 `unavailable` | 无任何结构化依据 |
| 聚合 | `degraded: true` + `confidence: null` | — |

**降级后的产物定位**：**「高赞评论候选列表」**（按点赞排序，人能自己看），
**不是「已分类的素材库」**。系统**不声称**它知道哪条是金句、哪条是段子。

> 这是本项目一贯的降级纪律：**承认判不了，而不是用规则假装判了。**
> 假装判了的后果是——运营拿到一批「金句」，点开发现是专名和模板标签，从此不信这个系统。

#### ★ 冷启动：样例库从哪来（需要用户行动，这是硬前置）

**RAG 没有样例库就是空的。** 这是本方案唯一需要用户亲自做的事：

| 方案 | 说明 | 成本 |
|---|---|---|
| **A. 人工标种子**（推荐起步） | 从现有高赞评论里挑 **15–20 条，每类 5 条**，人工确认归类 | 用户 10–20 分钟 |
| B. LLM 先标 → 人工抽查 → 变样例库 | 需 402 解除；且首轮标的质量无标尺，容易把噪声固化成标准 | 中 |
| C. 复用已有标注 | `data/annotations` 的 154 条修辞伪装标注 | ⚠️ 那是**评论修辞标注**，不是素材分类，只能部分迁移 |

**为什么推荐 A**：样例库是**判定标尺本身**——
如果标尺是从 LLM 来的（方案 B），那就没有外部锚点，等于让 LLM 自己给自己定标准。
**先用人工锚定 15 条，比用 LLM 灌 500 条更可靠。**

#### 命名诚实性：这算不算「RAG」？

**要说清楚，因为这是会被追问的技术点**：

| 阶段 | 实际是什么 | 该怎么称呼 |
|---|---|---|
| 首版（样例库 < 100 条） | 按结构分桶取 K 条样例塞进 prompt | **「样例检索增强的判定」/ few-shot**，**不叫 RAG 系统** |
| 进阶（样例库 > 100 条） | 上向量检索器 + 索引 | 可以叫 RAG（LangChain retriever 的位置，见[框架落地设计 §5](./Agent框架落地设计.md)） |

> **不能因为是热点词就往上靠。** 若对外说「我做了 RAG」而实际是 few-shot，
> 被问「你的检索器是什么、索引怎么建的、召回率多少」就答不上来。
> 首版的准确表述是：**「用样例检索给 LLM 定判定标尺」**——这个说法既准确又不减分。

### 4.1 原帖引用 —— 纯代码 ✅

| 项 | 设计 |
|---|---|
| 数据源 | `discovery_posts.csv`（118 条）+ `data/raw/taptap_wuthering_waves` 社区帖（44 条） |
| 选取判据 | 该话题下按 `supports` 降序（点赞=社区认可度）；同分看 `comments`（讨论度） |
| 品质过滤 | 标题或摘要长度 ≥ 8 字（太短无信息量）；剔除纯表情/纯符号 |
| 去重 | 同 `moment_id` 只出一次；跨话题重复出现的帖子标「多话题命中」 |
| 需要 LLM | ❌ 不需要 |
| 分类仲裁 | ❌ 不需要（原帖引用就是原帖引用，无歧义） |

### 4.2 热评金句 —— 选取纯代码 ✅ / **分类需仲裁** ⚠️

> ⚠️ **本节已于 2026-09-30 修订**。初版写「段子 = 金句 = 同一件事的两个说法」，**这是错的**——
> 用户指出「段子和热评金句和梗，三个之间是三种概念」，见 §4.0。
> 正确表述：**选取**（哪条评论值得看）是纯代码的；**分类**（它是金句还是段子）需要 LLM 仲裁。

| 项 | 设计 |
|---|---|
| 数据源 | `discovery_comments.csv`（74 条，其中 21 条有非零点赞） |
| **选取**判据 | **帖子内**按 `supports` 降序（**不跨帖统计**——见 §4.3 实测翻案） |
| **长度窗口** | **10–120 字** —— 操作性定义：太短没信息，太长不适合引用 |
| 品质过滤 | 剔除纯表情、纯「+1」类无信息回复 |
| 溯源 | `comment_id` + `moment_id` → 可跳回原帖（§2） |
| **选取**需要 LLM | ❌ 不需要（点赞、长度、归属全部可核对） |
| **分类**需要 LLM | ✅ **需要**（金句 vs 段子 = 表述是否有幽默感，语义判断） |

**所以 §4.2 与 §4.3 的分工是**：

| | 谁做 |
|---|---|
| 哪些评论**值得进候选池** | 代码（点赞排序 + 长度窗口 + 品质过滤） |
| 它们是**金句**还是**段子** | **LLM 仲裁层（§4.0）** |
| 是否已**升级为梗** | 代码给跨帖信号 + LLM 确认 |

#### 同时标为「候选梗」纳入观察（用户补充的早发现机制）

段子**可能转化成梗**，所以除了当素材用，它还要**挂进观察名单**：

| 字段 | 值 |
|---|---|
| `promotion_watch` | `true`（标记为观察中） |
| `signature` | 归一化后的短语指纹（用于后续比对是否出现在别的帖子里） |
| `first_seen_at` | 首次见到的时间 |

**当同一个 `signature` 后来出现在 ≥2 个别的帖子时 → 触发「段子升级为梗」事件** ——
这是一个可报给运营的真实信号（「你们社区那句话开始被别处引用了」）。

> 这与 `topic_tracker` 的思路完全一致：**追踪变化过程，而不是判断绝对状态**。
> 实现上可复用同一套 SQLite 状态库（见 §6 批 1）。
>
> ⚠️ 注意：「升级为梗」这个判断**仍要 LLM 确认**——因为跨帖重复也可能是
> 专名或模板标签（§4.0 实测已证）。代码只负责**发现信号**，不负责**下结论**。

### 4.3 梗 —— 两轴分类 + 跨社区发现（用户 2026-09-30 补充两轮）

> 本节经用户**两轮补充**：第一轮给出「段子→梗」的扩散谱（下 §4.3.1），
> 第二轮给出**梗的两个分类轴**与**跨社区发现法**（§4.3.2–4.3.4）。
> 后者的信息量更大，也更难做——用户自己说「**这个地方就好好设计啊**」。

#### 4.3.1 「段子→梗」扩散谱（第一轮补充）

> 「一人说一句是段子，**其实是出现在多少个不同的帖子里面，然后还有人点赞**。
> 段子的话，一般就是在一个评论区、帖子下面评论点赞的人很多，
> 但是**可能会转化成梗**。对不对？」

**对。而且 §1.0 已定案：段子并入梗，两者是同一条扩散谱的两端。**

| | 段子态 | 梗态 |
|---|---|---|
| 范围 | **单帖内**扩散 | **跨帖 / 跨社区**扩散 |
| 信号 | 该帖下**点赞高** | **出现在多个不同帖子 / 社区** |
| 含义 | 局部高认可，有潜力 | 社区共识已形成 |
| 关系 | ——— **可能转化为** ———→ | |
| 发现时机 | **早**（刚出现就能看到） | 晚（已经扩散了才知道） |

**这是一条演化链，不是一个二元判断。** 而且它和 `topic_tracker` 的话题状态机是**同构思想**：
都在判「一个东西正在变热的过程」，而不是判「现在热不热」。

#### 4.3.2 ★ 梗的两个分类轴（第二轮补充，本节最重要的新增）

##### 轴 1：来源方向 —— 内向梗 vs 外向（破圈）梗

> 「梗的话就有点难了，因为梗的话，它每个帖子就是说，
> **可能是社区圈子的梗，有可能是破圈的梗**。
> 有一些是**你这个游戏圈子的梗**，一些是**其他地方破圈的梗，大众玩的梗，然后被运到了这个游戏里面**。」

| | **内向梗** | **外向梗（破圈梗）** |
|---|---|---|
| 来源 | 本游戏社区内产生 | **外部传入**（大众 / 其他圈层） |
| 例 | 本游玩家自造的说法 | **「V我50」**（KFC 疯狂星期四，与游戏无关） |
| 发现方式 | 本社区内**跨帖重复** | **跨社区 / 全网重复** ← 必须往外看 |
| 意义 | 社区文化资产 | **「全网热点追踪」这一目标的正面命中** |
| 在本系统的位置 | G3 追踪图覆盖 | **需要外部信号源**（架构设计 §17 的「B站/抖音/微博 为信号源」正为此存在） |

> ⚠️ **这条改变了对「全网」的理解**：之前「全网」只是**热度佐证**（决策 #17：
> 「只作外部热度佐证，不单独出结论」）。但**外向梗的发现必须依赖外部语料**——
> 光看 TapTap 内部，永远发现不了「这个梗是从外面传进来的」。
> **这是「全网」的一个新的、更硬的理由。**

##### 轴 2：可复用形态 —— 整体梗 vs 句式梗

> 「梗它那个**不一定结合游戏内容**。比如 **V我50 KFC** 是吧，那这个它就相当于
> **已经没法二次创造的梗了**，这个梗就是这个内容，他见人就用这个东西。
> 那有些比如**明朝（鸣潮）那个句式**，那就可以用这个**句式一直去套用到其他游戏**。**这是两种。**」

| | **整体梗（不可变）** | **句式梗（可套用）** |
|---|---|---|
| 例 | 「V我50」（就是这句话本身） | 「⟨X⟩都⟨Y⟩了，⟨Z⟩还远吗」这类句式 |
| 用法 | **直接用**，不能改 | **替换槽位后套用到新对象** |
| 可二次创造 | ❌ 不能 | ✅ **能** |
| 二创价值 | 低（只能引用） | **★ 高（可生成新内容）** |
| 对 G4 的意义 | 作为素材引用 | **直接是二创角度的生成模板** |

**两轴正交，组合出四种情况**：

| | 内向 | 外向 |
|---|---|---|
| **整体** | 本游专有说法（社区知识） | 破圈热梗（可直接蹭） |
| **句式** | ★ **本游句式（最能二创）** | 大众句式（可套用到本游） |

> **两个 ★ 是二创的高价值区**：内向句式梗（本游自己的句式，最贴社区）
> 和外向句式梗（大众句式套到本游，最易传播）。
> **G4 生成二创角度时应该优先从这两格取材。**

#### 4.3.3 发现方法：跨社区模板重合度（用户设计的路线，含实测）

> 「第一，就是发现**不同类型的游戏，它里面的一些帖子下面的评论出现了**，
> 就是用这个结构吧，**语句的结构是类似的，只不过是换成了游戏内容**，
> 这个的话就需要用某种方法，这个地方就要**设计怎么判断**了。
> 首先你怎么发现，**你得从整一个社区不同的游戏圈子里面的帖子的评论去，看有没有重合度**，
> 那**怎么判断重合度**？」

**用户设计的路线是对的**：把「游戏内容」抽象掉，看**句式结构**是否跨社区重复。
技术上叫 **slot abstraction / 模板挖掘**：

```
步骤 1  抽象：把游戏专名替换成占位符
        「明日方舟的限定池太毒了」 → 「⟨G⟩的⟨TERM⟩太⟨ADJ⟩了」
        「鸣潮的武器池太毒了」     → 「⟨G⟩的⟨TERM⟩太⟨ADJ⟩了」   ← 模板重合！

步骤 2  跨社区统计：同一模板出现在几个**不同的 app_id / group_id**
        注意：是「不同社区数」，不是「不同帖子数」—— 社区维度才是扩散的证明

步骤 3  粗筛入围：模板出现在 ≥N 个不同社区 → 候选

步骤 4  LLM 判定 + 两轴分类：是内向还是外向？是整体还是句式？
```

**依赖**：一份**专名词典**（游戏名、角色名、模式名、活动名）用于抽象。
这正是 `games/*.json` 别名库的用处——**但实测发现它当前取不到词**（见下）。

##### ★ 实测（2026-09-30）：方向对，但当前数据量不够，且有新噪声源

**实验**：118 帖（title+summary）+ 74 评论 → 抽象游戏名后统计跨社区重合。
有效文档 **125 条，来自 18 个社区**。

**结果：候选 76 个，排名靠前的全是噪声**：

| 候选 | 社区数 | 这是什么 |
|---|---|---|
| `⟨G⟩⟨` / `G⟩⟨G` | 5 | 占位符边界产生的垃圾（抽象实现有 bug） |
| **`游戏日常`** | **4** | **话题标签**（`#游戏日常#`）← **新发现** |
| `⟨G⟩攻略` | 3 | **话题标签**（`#明日方舟攻略#`） |
| `联动宇树` | 2 | **活动名**（星布谷地的联动），不是梗 |

**两个新结论**：

1. **发现了一个之前没考虑到的噪声源：话题标签**（`#游戏日常#`、`#XX攻略#`）。
   它们是**跨社区高频重复的成分**，和梗的信号混在一起。
   → **粗筛的屏蔽词表必须包含 `#...#` 格式**，这是对 §4.3.4 的具体补充。

2. **数据量级不够**：18 个社区摊到 125 条文档，**平均每社区仅 7 条**。
   跨社区重合检测在这个量级上**不可避免是噪声**——
   要真做，**每个社区至少需要 100+ 条评论，且覆盖 5–10 个社区**。

> **诚实结论**：用户设计的路线（跨社区模板重合）**方向正确、方向性判据合理**，
> 但**当前数据完全不支持**。它属于「机制先设计好、等语料扩充后再启用」的部分。
> **不能现在承诺「系统能发现跨社区梗」。**

#### 4.3.4 ★ 实测翻案：纯 n-gram 统计**发现不了梗**（2026-09-30 实测）

上一版设计写的是「发现可以纯统计」。**我用真实数据测了，结论是错的。**

**实验**：对 `reviews_clean.csv` 3000 条评价做 n-gram（n=4..7）滑窗，
统计每个短语出现在多少个**不同文档**、多少个**不同作者**（作者用 `user_id_hash` 去重，不涉明文）。

**第一轮（裸统计）** —— 完全失败：

| 候选 | 出现 | 这是什么 |
|---|---|---|
| `<br/>` | 705 帖 / 705 作者 | HTML 标签 |
| `明日方舟` | 357 帖 / 357 作者 | 游戏名 |
| `这个游戏` | 133 帖 / 133 作者 | 功能词 |
| `[表情_` | 149 帖 / 149 作者 | 表情标记 |

**第二轮（加专名/模板屏蔽 + 通用词过滤）** —— 仍然不达标：

| 候选 | 出现 | 问题 |
|---|---|---|
| `卫戍协议` | 123 帖 | **专有名词**（游戏模式名），不是梗 |
| `资源获取` | 84 帖 | **评价模板标签** |
| `立绘建模` | 70 帖 | 评价模板标签 |
| `什么时候` | 58 帖 | 功能短语 |
| `💃🏻立绘` | 66 帖 | emoji 碎片 |

**根因（这是本节最有价值的一句）**：

> **梗的语言特征是「罕见而独特」，而频次统计天然把「常见」排在前面——两者方向相反。**
> 统计能告诉你「什么短语常见」，但「常见」的成因有四种：
> **格式标签 · 专有名词 · 功能词 · 真梗**。
> 前三者在数量上碾压第四种，所以纯统计的输出永远是垃圾。

**所以修正为**：

| 步骤 | 方法 | 需要 LLM |
|---|---|---|
| **粗筛** | 跨帖重复 + 作者去重 + 屏蔽标签/专名/通用词 → **候选池** | ❌ 统计 |
| **判定** | **这是不是梗**（区分真梗 vs 专名 vs 口头禅） | ✅ **必须 LLM** |
| **解释** | 什么意思、什么语境用 | ✅ LLM |

⚠️ **粗筛产出不得命名为「梗」** —— 只能叫「**高频重复短语（未经语义确认）**」，
且必须标 `confidence: low` + `degraded: true`。
**把粗筛结果当梗用，就是拿垃圾当资产。**

#### 4.3.5 「高赞评论」维度：纯统计可做（但**不等于**能判定「段子」）

**代码能做的是「选出值得看的评论」**（单帖内按点赞排序），不涉及跨帖统计，
所以不受上面的失败影响。

**实测（平台评论 74 条，21 条有非零点赞）**：

```
[10赞] 就是玩几个小时游戏，又不是这辈子不干别的了。[表情_笑哭了]这群人也真是，跟一个游戏较劲
[ 5赞] 其实宴的是肉鸽给的（刻俄柏的灰蕈迷境[表情_流口水]只不过在这次夏活复刻了
[ 3赞] 其实除了锏，剩下两位还碰不到时代眼泪，特别是维什戴尔……
[ 2赞] 你玩个游戏还不能吐槽一下了花钱买罪受[表情_斜眼笑]
```

这些**确实是值得看的候选**，判据完全可核对（点赞数、帖子归属），不需要 LLM。

⚠️ **但要说清楚边界**（§4.0 的实测已证）：
**「这是高赞评论」≠「这是段子」**。因为**金句和段子的结构指标完全相同**——
上面 10 赞那条既可以是金句（有观点、可引用）也可以是段子（"跟一个游戏较劲"是调侃）。

| 问题 | 谁回答 |
|---|---|
| 哪些评论值得看？ | ✅ **代码**（点赞排序 + 长度窗口） |
| 它是**金句**还是**段子**？ | ⚠️ **只能 LLM 仲裁**（§4.0） |

所以这一维度的正确称呼是「**高赞评论候选池**」，**不是「段子库」**。

#### 4.3.6 数据量级的诚实说明

| 数据源 | 数量 | 可用性 |
|---|---|---|
| 平台帖子 `discovery_posts.csv` | 118 | ✅ 有 title + summary |
| 平台评论 `discovery_comments.csv` | 74 | ✅ 有 content；21 条有赞 |
| 鸣潮社区帖子 | 44 | ✅ 有 title + summary（但 `supports` 全 0） |
| 鸣潮社区评论 | 345 | ❌ **`content` 345/345 全空，不可用** |
| 方舟主链评价 `reviews_clean.csv` | 3000 | ✅ 最大的语言池（但 `support_count` 全 0，拿不到赞） |

⚠️ **两处必须说清**：
1. **鸣潮 345 条评论内容全空** —— 之前 memory 记的「44 帖 + 345 评论」数量对，
   但**内容实际没抓到**。这是本次实测新发现的数据质量问题，需单独跟进。
2. **方舟 3000 条评价拿不到点赞**（`support_count` 全切片为 0，已知问题），
   所以「段子」维度**只能在 74 条平台评论上跑**，量很小。

⚠️ **诚实的量级问题**：不要对外宣称「系统能发现全网梗」——
**当前量级只能做机制验证**。真要用，需先解决「评价/评论的点赞数采集」与
「鸣潮评论内容采集」两件事，把语料扩到千级。

### 4.4 二创角度 —— 必须 LLM ✅

| 项 | 设计 |
|---|---|
| 输入 | **前 3 类素材 + 话题状态 + 可发酵度（`ferment_judge`）** |
| 输出 | 「使用者可以从哪些角度二创」的列表，每条附**依据**（基于哪条素材） |
| 模型 | Flash + **thinking 开** + `reasoning_effort=high`（决策 #16 定的创意生成档） |
| 免责 | **必须标注这是建议**，见 §4.5 |

### 4.5 第四类的特殊纪律

因为二创角度是**唯一由 LLM 生成、无确定性判据**的一类，它需要专门的标注：

```jsonc
{
  "type": "remix_angle",
  "selection_kind": "llm",              // ← 明确标注是生成的
  "based_on": ["m_20260930_0001", "m_20260930_0007"],   // ← 依据哪几条素材
  "text": "从玩家「说陪我都是假的」这句引发共情，可做「你在光遇遇到的人」征集",
  "confidence": "medium"
}
```

**硬规则**：`based_on` 必须引到真实存在的 `material_id`。
如果 LLM 给的角度找不到对应的素材依据 → **丢弃**。
这条防止「创意是凭空想的」——每个建议都能追到某条真实素材。

## 5. PII 边界：素材带作者名，但绝不入库

### 5.1 冲突在哪

素材要溯源，就需要 "谁说的"；但项目的 PII 三域模型说**产出域只出聚合**。

**冲突是真实的**：`discovery_posts.csv` 与 `discovery_comments.csv` 都含 `author_name` 明文。

### 5.2 解法：素材库属原始域边界，与 `reviews.csv` 同策略

| 产物 | 位置 | 含作者名 | 入库 |
|---|---|---|---|
| **运行时素材库** | `data/raw/taptap/materials/materials.jsonl` | ✅ 含（内部溯源需要） | ❌ **不入库** |
| **素材简报**（给员工看） | 同上，或 `data/outputs/agent/` | ✅ 含（对内） | ❌ **不入库**（含明文） |
| **仓库里的样例** | `docs/` 或 `tests/fixtures/` | ❌ **脱敏**（合成或抹名） | ✅ |
| **抽取代码 + schema** | `11情报Agent/` | — | ✅ |

### 5.3 已实测确认忽略规则生效

```
$ git check-ignore -v data/raw/taptap/discovery_posts.csv
.gitignore:91:data/raw/taptap_*/   data/raw/taptap/discovery_posts.csv
$ git ls-files data/raw/taptap/
（空 —— 未追踪）✅
```

⚠️ **但这里有个教训要用上**：2026-09-29 的 PII 泄漏事故，根因就是
`.gitignore` 里写的 `data/raw/taptap_*/`（带下划线）**不匹配**实际目录 `data/raw/taptap/`（无下划线），
规则静默落空两个月无人察觉。

所以素材库落盘后**必须立刻用 `git check-ignore -v` 验证命中**，
并且 CI 的 PII guard 要覆盖到素材产物。**不能因为是新目录就默认规则会生效。**

### 5.4 素材简报的渲染要加守卫

复用 `user_flow.assert_aggregate_only()` 的思路，素材简报写文件前扫描：
- 不得出现 `author_name` 的字段名
- 作者名统一渲染为「某玩家」或省略（内部溯源靠 `moment_id` 跳链接即可，不必显示名字）

> **设计取向**：**溯源靠链接，不靠名字。** 点链接就能看到是谁，不必在文件里存明文。

## 6. 分批实现

DeepSeek 余额 402 阻塞了 LLM 路。但**素材层有部分现在就能落地**：

| 批次 | 内容 | 需要 LLM | 现在可做 |
|---|---|---|---|
| **批 1** | 原帖引用 + **高赞评论候选池**（含「候选梗」观察名单） | ❌ | ✅ **可以立刻做** |
| **批 0（前置）** | **样例库种子标注**（15–20 条人工确认） | ❌（人工） | ✅ **需要用户花 10–20 分钟** |
| **批 1.5** | 梗粗筛（跨帖重复候选池，**只叫「高频重复短语」**） | ❌ | ⚠️ 技术可做但产出质量差，**建议延后** |
| **批 2** | **LLM 仲裁层**（判「是不是真梗」+ 解释 + 两轴分类）→ 二创角度 | ✅ | ❌ 等充值 |
| **批 3** | **跨社区梗发现**（模板重合度，外向梗） | ✅ + 语料 | ❌ 需先扩语料（每社区 ≥100 条 × 5–10 社区） |

> **批 1.5 的降级理由（诚实版）**：实测表明纯统计的输出是标签/专名/功能词，
> 直接给运营看会损害系统可信度。所以它的定位是**给批 2 的 LLM 减少输入量**，
> 而不是一个独立交付物。**若在 402 未解除前做，只能内部用，不进任何简报。**

> **批 3 为什么单独列**：跨社区模板重合是**外向梗唯一的发现路径**（§4.3.2），
> 但它对语料量的要求在数量级上高于批 2 —— 实测已证当前 18 社区摊 125 条文档
> 产出全是话题标签。**机制先写进设计，等语料到位再启用。**

⚠️ **批 0 是批 2 的硬前置，且不依赖 LLM** —— 现在就可以做。
样例库是判定标尺，没有它 LLM 仲裁层就没有锚点（§4.0 冷启动一节）。
且批 0 的种子**同时服务判断与生成两处用途**（见[创意生成与闭环设计 §5.3](./创意生成与闭环设计.md)），
冷启动只需做一次。

**批 1 的完整交付**：
1. 抽取器（读 CSV → 按判据选 → 产出带溯源的素材）
2. Schema + 准入校验（`assert_traceable`）
3. 素材库落盘 + gitignore 验证
4. 素材简报渲染（带链接、不带作者名）
5. 「候选梗」观察名单（高赞评论入观察池，复用 SQLite 状态库思路）
6. 测试锁死（准入、判据、脱敏守卫）

**批 1 的产物定位（重要，别夸大）**：
产出的是「**原帖引用（已分类）+ 高赞评论候选池（未分类）**」。
**不是「已分类的金句/段子库」** —— 后者要等批 2 的 LLM 仲裁。
简报里必须写明这个区分，否则运营会以为系统分好了类。

**批 1 做完的意义**：
- 「素材」这个缺口从**空白**变成**有产物**
- 它不需要 LLM，所以**不被 402 阻塞**
- 批 2 接上时，schema / 存储 / 追溯已验证过，只需插入一个仲裁节点

| `test_arbitration_includes_negative_examples` | context 必须含边界负例（专名/模板标签） |
| `test_arbitration_context_includes_thread_for_dependent` | `self_contained=false` 的候选，context 必须带 Thread 上下文 |
| `test_arbitration_skips_thread_for_self_contained` | 段子/梗不带 Thread 上下文（省 token） |
| `test_prompt_version_recorded` | 记录 `prompt_version`（否则置信度不可比） |
| `test_remix_angle_requires_based_on` | 二创角度必须引到真实存在的素材 id |
