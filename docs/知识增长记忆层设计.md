# 第五层：Knowledge & Growth Memory Layer  
**知识与增长记忆层**

前四层已经完成：

```text
① Signal Acquisition
哪里出现了新信号？

② Semantic Processing
单条内容是什么意思？

③ Trend Intelligence
什么事件正在爆？

④ AI Intelligence
这个热点对 TapTap 有什么意义？
应该抓什么增长机会？
```

第五层解决的是：

> **TapTap 过去知道什么、做过什么、什么有效、什么无效，以及这些经验如何被第四层 Agent 重新利用。**

它不是一个普通 RAG，也不是简单的 Vector DB。

更准确地说，第五层应该是整个系统的：

# Intelligence Memory System

---

## 一、第五层真正解决的问题

如果没有第五层，每一次热点分析本质上都是：

```text
Trend
  ↓
LLM
  ↓
从零开始分析
```

比如今天出现：

```text
游戏角色捏脸热点
```

Agent 每次都会重新想：

> 可以搞个 UGC 挑战。

但如果系统有历史记忆：

```text
2025 某角色换装热点
→ UGC活动
→ 投稿 +62%
→ 分享 +31%
→ 但拉新效果弱

2026 某游戏截图热点
→ 排行榜玩法
→ CTR +18%
→ Game Follow +27%
```

那么下一次 Agent 可以推理：

```text
这次也属于：
展示型用户动机
+
UGC传播
+
游戏社区场景

历史上排行榜 + 分享卡效果较好，
但纯UGC活动拉新有限。
```

这才是真正的：

> **组织级 AI Intelligence。**

---

# 二、第五层职责边界

第五层负责：

| 能力 | 作用 |
|---|---|
| Business Knowledge | 保存 TapTap 稳定业务知识 |
| Entity Knowledge | 游戏、厂商、IP、用户等实体知识 |
| Trend Memory | 保存历史热点及传播规律 |
| Creative Memory | 保存历史创意方案 |
| Experiment Memory | 保存真实实验与业务结果 |
| Decision Memory | 保存人工采用、拒绝、修改记录 |
| Retrieval | 为第四层检索历史经验 |
| Memory Writing | 把新结果沉淀回来 |
| Knowledge Versioning | 管理知识变化 |
| Feedback Learning | 用实验结果优化推荐 |
| Evaluation | 评估记忆是否真正有用 |
| Governance | 权限、生命周期、可信度 |

第五层不负责：

```text
热点发现
实时趋势计算
Agent Workflow 编排
Dashboard 展示
Campaign执行
```

# 四、第五层不要只做一个 Vector Database

最常见错误：

```text
所有历史文档
    ↓
切 chunk
    ↓
embedding
    ↓
pgvector
```

然后认为：

> “我们有企业记忆了。”

其实远远不够。

你的 Memory 至少应该分成：

```text
结构化事实
+
半结构化业务知识
+
历史案例
+
实验结果
+
语义向量
+
时序数据
```

所以应该是：

```text
Relational DB
+
Vector Retrieval
+
Analytics Store
+
Object Storage
```

而不是 Vector DB 一把梭。

# 十、Memory 4：Opportunity / Creative Memory

# 十二、Memory 5：Experiment Memory

这是第五层价值最高的一部分。

必须明确：

> **Creative ≠ Experiment**

创意只是假设。

Experiment 才是：

> 真实世界反馈。

结构：

```text
Trend
 ↓
Opportunity
 ↓
Creative
 ↓
Experiment
 ↓
Metrics
 ↓
Outcome
```

# 十三、Experiment 数据模型

建议至少：

```sql
CREATE TABLE growth_experiment (

    experiment_id UUID PRIMARY KEY,

    creative_id UUID,

    event_id UUID,

    experiment_name TEXT,

    experiment_type VARCHAR(50),

    audience_segment VARCHAR(100),

    treatment TEXT,

    control_definition TEXT,

    started_at TIMESTAMP,

    ended_at TIMESTAMP,

    primary_metric VARCHAR(100),

    status VARCHAR(30),

    result_summary TEXT,

    statistical_significance FLOAT,

    created_at TIMESTAMP
);
```

Metrics：

```sql
CREATE TABLE experiment_metric (

    experiment_id UUID,

    metric_name VARCHAR(100),

    baseline_value FLOAT,

    experiment_value FLOAT,

    absolute_lift FLOAT,

    relative_lift FLOAT,

    p_value FLOAT,

    sample_size BIGINT,

    PRIMARY KEY (
        experiment_id,
        metric_name
    )
);
```

# 十四、保存相对 Lift，而不仅是绝对数

例如：

```text
CTR = 7.2%
```

本身意义有限。

更重要：

```text
Control CTR = 5.3%

Treatment CTR = 7.2%

Relative Lift = +35.8%
```

Agent 以后才能学习：

> 什么方案在什么情况下有效。

# 十五、Experiment 还必须保存上下文

例如：

```text
渠道
用户群
游戏
生命周期
曝光位置
活动持续时间
资源位
预算
版本
季节
```

否则你可能错误地认为：

> 排行榜玩法历史上 +40%。

实际上那次：

```text
刚好是春节
+
首页核心资源位
+
头部游戏
```

所以要保存：

# Experiment Context

# 十六、Memory 6：Decision Memory

这个非常容易被忽略。

第四层 AI 推荐：

```text
Idea A
Idea B
Idea C
```

运营最终：

```text
A Reject
B Edit
C Approve
```

这些决策全部应该保存。

例如：

```sql
CREATE TABLE human_decision (

    decision_id UUID PRIMARY KEY,

    object_type VARCHAR(50),

    object_id UUID,

    decision VARCHAR(30),

    reason_code VARCHAR(50),

    reason_text TEXT,

    editor_diff JSONB,

    reviewer_role VARCHAR(100),

    created_at TIMESTAMP
);
```

这会告诉系统：

> 什么类型的 AI 建议业务团队真正愿意采用。

# 十七、Reject Reason 建议结构化

不要只存：

```text
“这个不好。”
```

建议固定 reason taxonomy：

```text
LOW_RELEVANCE

TOO_LATE

TOO_EXPENSIVE

BRAND_RISK

RESOURCE_UNAVAILABLE

LOW_NOVELTY

WEAK_USER_INSIGHT

NO_GROWTH_MECHANISM

DUPLICATE_IDEA

LEGAL_RISK

OTHER
```

这样以后可以分析：

```text
过去半年 AI Idea 被拒绝的主要原因是什么？
```

---

# 十八、Memory 写入不是“所有东西永久保存”

需要区分：

```text
Working Memory
Short-term Memory
Long-term Memory
```

建议：

```text
Working Memory

当前 LangGraph State
生命周期：分钟/小时
```

↓

```text
Short-term Memory

最近热点
最近上下文
生命周期：天/周
```

↓

```text
Long-term Memory

确认后的知识
实验结果
历史案例
生命周期：长期
```

不是所有 Agent 中间推理都值得长期保存。

---

# 十九、什么东西应该进入 Long-term Memory

建议至少满足之一：

```text
人工确认

真实实验发生

事件生命周期结束

业务知识正式更新

高置信度事实

重复出现的行为模式
```

而不是：

```text
LLM随便生成一句分析
```

就永久写进去。

---

# 二十、需要 Memory Write Policy

例如：

```python
if object.type == "experiment_result":
    save_long_term()

elif object.type == "human_approved_creative":
    save_long_term()

elif object.type == "llm_inference":
    save_short_term()
```

让 Memory 是受控的。

---

# 二十一、Knowledge Source 必须有 Provenance

每一条知识都需要：

```text
source
source_type
created_at
valid_from
valid_to
confidence
verified_by
version
```

例如：

```json
{
  "fact": "某功能支持分享卡",

  "source": "internal_product_doc",

  "confidence": 1.0,

  "valid_from": "2026-08-01",

  "valid_to": null,

  "version": 3
}
```

否则 Agent 未来会拿已经下线的产品能力做创意。

---

# 二十二、知识必须有时效性

尤其是：

```text
产品能力
运营资源
品牌规范
组织流程
用户画像
```

不能永远有效。

建议：

```text
valid_from
valid_to
```

而不是直接：

```text
active = true
```

因为你需要历史复现。

---

# 二十三、Knowledge Versioning

例如：

```text
社区话题页能力 v1

↓ 产品升级

社区话题页能力 v2
```

Agent 在分析 2025 年案例时：

```text
应该读取当时能力
```

分析当前创意时：

```text
应该读取最新能力
```

这属于：

# Temporal Knowledge

非常重要。

# 二十四、第五层最核心组件：Retrieval Engine

第四层每个 Agent 不应该：

```text
直接 query pgvector
```

应该统一经过：

```text
Memory Retrieval Service
```

接口例如：

```python
retrieve(
    query,
    memory_type,
    filters,
    top_k,
    ranking_strategy
)
```

这样以后可以独立升级检索算法。

---

# 二十五、不要只做 Semantic Retrieval

建议至少：

\[
RetrievalScore =
w_1 Semantic
+
w_2 Entity
+
w_3 Metadata
+
w_4 Recency
+
w_5 Performance
+
w_6 Trust
\]

例如 Creative Agent 查询：

> 类似角色捏脸热点以前做过什么？

系统可以：

```text
Semantic similarity        .89

Same game genre            .92

Same user motivation       1.00

Growth goal = UGC          1.00

Experiment performance     .85

Recency                    .71
```

最终排序。

---

# 二十六、Retrieval 类型建议分 5 种

### 1. Semantic Retrieval

```text
找“意思相似”的案例
```

### 2. Entity Retrieval

```text
找同一个游戏/IP/厂商
```

### 3. Metadata Retrieval

```text
creative_type = UGC
growth_goal = Share
```

### 4. Temporal Retrieval

```text
最近90天
同生命周期
```

### 5. Performance Retrieval

```text
只找表现高于中位数的实验
```

最终是：

# Hybrid Retrieval

# 二十七、一个真实 Retrieval 示例

当前事件：

```text
某二次元 RPG
角色外观编辑功能爆火
```

Opportunity Agent 请求：

```json
{
  "memory_type": "experiment",

  "semantic_query":
    "角色展示 UGC 社交分享",

  "filters": {
    "genre": "anime_rpg",
    "growth_goal": "ugc"
  },

  "performance_filter": {
    "relative_lift": ">0"
  },

  "top_k": 10
}
```

返回：

```text
Case 1
角色截图排行榜
UGC +62%

Case 2
角色分享卡
Share +38%

Case 3
AI角色标签
CTR +17%
但 retention 无提升
```

然后第四层才做推理。

# 二十八、RAG 的返回值不要直接是一堆 chunks

传统：

```text
chunk1
chunk2
chunk3
```

不够。

应该返回：

```text
Case Package
```

例如：

```json
{
  "case_id": "case_123",

  "context": {
    "game_type": "anime_rpg",
    "trend_type": "ugc_showcase"
  },

  "strategy": "UGC排行榜",

  "result": {
    "ugc_lift": 0.62,
    "share_lift": 0.31
  },

  "lessons": [
    "排行榜促进投稿",
    "分享卡促进站外扩散"
  ],

  "confidence": 0.88
}
```

这对 Agent 更容易消费。

# 二十九、第五层可以建立 Case Memory

这是我非常推荐的一层抽象。

将：

```text
Trend
Opportunity
Creative
Experiment
Outcome
```

压缩成一个：

# Growth Case

例如：

```json
{
  "case_id": "growth_case_001",

  "trend_pattern":
    "游戏角色创作热点",

  "user_motivation":
    "身份表达 + 社交展示",

  "strategy":
    "UGC + 排行榜 + 分享",

    "角色展示挑战",

  },

  "lesson":
    "适合社区激活，但直接拉新较弱"
}
```

这是以后最有价值的 Memory 单元。

# 三十四、Memory Quality

知识库最危险的问题：

> **垃圾经验积累。**

所以每个 Memory 最好有：

```text
confidence

quality_score

evidence_strength

human_verified

sample_size

freshness
```

比如：

```text
某创意 CTR +80%
```

如果：

```text
sample_size = 40
```

不能和：

```text
sample_size = 5,000,000
```

一样进入 Recommendation。

---

# 三十五、Experiment Reliability Score

可以做：

\[
Reliability =
f(
SampleSize,
StatisticalSignificance,
ExperimentDesign,
DataQuality
)
\]

例如：

```json
{
  "relative_lift": 0.40,
  "reliability": 0.21
}
```

第四层要知道：

> 看起来效果不错，但证据弱。

---

# 三十六、Historical Performance 不应该直接复制

例如：

```text
Case A：
UGC +60%
```

不能因此预测：

> 新活动一定 +60%。

Agent 应该读取：

```text
historical effect
+
context similarity
+
confidence
```

输出：

> 历史类似案例曾出现较高 UGC lift，但本次需通过实验验证。

而不是把历史结果当预测。

---

# 三十七、Memory Decay

不是所有历史案例永远同样重要。

例如：

```text
3年前的Push玩法
```

可能已经不适用于当前产品。

因此可以有：

\[
MemoryWeight =
BaseQuality
\times
RecencyDecay
\times
ContextSimilarity
\]

例如 exponential decay：

\[
R=e^{-\lambda t}
\]

但某些知识：

```text
长期游戏实体关系
```

不应该快速衰减。

所以 decay 要按 Memory Type。

# 三十八、Conflict Resolution

例如：


不能让 RAG 两条都直接塞给 Agent。

需要：

```text

version
```

优先：

```text
最新
+
权威
+
仍有效
```

的知识。

非常重要。



非常有价值。

# 五十、Memory Evaluation

第五层也必须有自己的评估。

最重要的不是：

```text
Vector Search Recall
```

而是：

### Retrieval Relevance

Agent 拿到的案例是否相关？

### Knowledge Freshness

是不是最新有效知识？

### Grounding Rate

Agent 结论有多少来自有效 Memory？

### Memory Utilization

Agent 实际用了多少检索结果？

### Case Reuse Rate

历史经验有多少真正被重新使用？

### Improvement Lift

有 Memory 与没有 Memory 相比：

```text
Creative Adoption
Opportunity Quality
Experiment Success
```

是否提升？

# 五十三、知识污染防护

Agent 输出不要自动进入高权威知识库。

应该分：

```text

candidate_knowledge

agent_generated_memory
```

路径：

```text

    ↓

    ↓

    ↓
Verified Knowledge
```

避免：

> Agent 幻觉 → 写入 Knowledge → 下次 Agent 检索 → 幻觉变“事实”。

这是长期 Agent 系统很危险的 feedback loop。

## 到第五层以后，系统发生了本质变化

前四层还是：

> **AI 帮 TapTap 做一次热点分析。**

加入第五层以后变成：

> **TapTap 自己的增长经验，被不断结构化、实验化、沉淀，再由 AI 在下一次热点中复用。**

因此这个系统真正的长期壁垒不是 LangGraph，也不是某个大模型，而是：

> **Trend × Opportunity × Creative × Experiment × Outcome 的历史闭环数据。**

模型可以换，Agent 框架可以换，但这套 **Growth Memory** 一旦积累起来，就是最难复制的部分。
