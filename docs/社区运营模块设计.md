## 1. 先回答：社区运营到底能运营哪些东西

用户 2026-09-30 的质疑：

> 「社区运营这个地方能运营哪些东西呢？都要好好想一下啦，**你只是一个爆发话题提醒吗？** 对不对？」

**问得对。** 我之前列的 4 个功能（爆发提醒 / 争议点 / 高投入负向 / 我要跟进）
**全在防守，没有进攻** —— 而项目目标原文是「产出实际**增长**创意」，增长是进攻性的。

### 1.1 社区里能被运营的对象（六类）

| 对象 | 运营动作 | Agent 能提供什么 | 第一版 |
|---|---|---|---|
| **话题** | 建 / 推 / 救 | 哪些值得做：状态 + 可发酵度 + 建议动作 | ✅ 功能 ① |
| **社区氛围** | 引导 / 降温 | 哪里在吵：争议聚集 + 高投入负向 + 干预建议 | ✅ 功能 ② |
| **帖子 · 评论** | 加精 / 推荐 / 精选 | 哪些值得推：高赞内容 + 可点回原帖 | ✅ 功能 ③ |
| **运营动作本身** | 跟进 / 忽略 / 复盘 | 我做了没有 + 不重复推 + 供校准 | ✅ 功能 ④ |
| **用户** | 激励 / 维护 | ⚠️ 只能出**聚合分布**（PII 边界：不得出个体、不得出轨迹） | ❌ 不入第一版 |
| **活动** | 策划 / 执行 | 活动创意 + 具体示例 | ❌ 需 LLM（402 阻塞） |

### 1.2 第一版 4 个功能（攻守平衡）

| # | 功能 | 性质 | 运营动作 | 依赖 LLM |
|---|---|---|---|---|
| ① | **话题机会** | 🔥 进攻 | 建话题 / 加运营位 | ❌ |
| ② | **风险预警** | 🛡 防守 | 介入引导 / 准备口径 | ❌ |
| ③ | **内容候选** | 🔥 进攻 | 加精 / 推荐 / 做内容 | ❌ |
| ④ | **动作闭环** | ⚙️ 机制 | 记录跟进，供阈值校准 | ❌ |

**四个都不依赖 LLM**，所以不被 402 阻塞 —— 这是刻意的选择：
**先把「运营能拿到东西」这条链打通，再谈智能。**

## 2. 四个功能的具体定义

### ① 话题机会：哪些话题现在值得做

| | |
|---|---|
| 输入 | `outputs/topic_state.json`（状态机）+ `outputs/ferment_judge.json`（可发酵度） |
| 门控 | **只有「升温/爆发」进行动项** —— 冒头首日全是（迁移需 ≥2 次采样），推了等于推噪声 |
| 分级 | 另设**观察位**：冒头 + 可发酵度明确为 `act`/`watch` 的话题（不声称可行动） |
| 输出 | 话题 + 状态 + 当前/峰值 + 可发酵度 + **建议动作**（来自 `ferment_judge.suggested_action`） |
| 排序 | **先按紧急度（爆发 > 升温），再按可发酵度** |

> 为什么排序要加状态优先级：可发酵度在 LLM 未跑时**全为 None**，
> 只按它排会退化成插入顺序，可能把「爆发」排在「升温」后面。**紧急的先做。**

### ② 风险预警：哪里在吵、要不要介入

| | |
|---|---|
| 输入 | `outputs/risk_insight.json` 的 `topic_risk_table` + `intervention_map` |
| **闸门** | 负向率 ≥ 阈值（默认 50%） |
| **优先级标记** | 高投入负向占比 ≥ 阈值（默认 60%）→ 标 `high_stakes`，**加粗显示** |
| 输出 | 主题 + 负向率 + 高投入占比 + **干预建议**（如「数值调整公开说明与补偿预告」） |

> **为什么高投入是标记不是闸门**：「高负向但高投入少」仍可能是真问题，**筛掉会漏**；
> 而「高投入玩家也在骂」是最该先处理的信号 —— 所以**标出来，不筛掉**。

### ③ 内容候选：哪些帖子/评论值得推

| | |
|---|---|
| 输入 | `02数据_platform/discovery_posts.csv` + `discovery_comments.csv` |
| 判据 | **点赞排序**（社区认可度），≥1 赞才入候选 |
| 输出 | 内容 + 点赞 + **可点回原帖的链接**；评论额外带**所属帖子标题** |

**两条硬纪律**：

1. ⚠️ **不声称这是「已分类的素材」** —— 「哪些值得看」（点赞排序，代码可判）
   和「是金句还是段子」（需 LLM 仲裁）是两件事。**报告里必须写明这个区分。**
2. ⚠️ **作者名一律不出** —— 溯源靠可点链接，不靠名字（PII 三域纪律）。

> **踩过的坑**：帖子点赞在 `ups`，评论点赞在 `supports` —— **字段名不一致**。
> 早期实测「原帖 supports 全 0」是看错字段，实际 `ups` 有 108/118 非空、最高 311。

### ④ 动作闭环：我做了没有 + 不重复推

| | |
|---|---|
| 存储 | `state/community_ops.sqlite3`（已在 `.gitignore`，运行时状态不入库） |
| 表 1 | `ops_action`：topic_key / title / action(follow\|ignore\|done) / **state** / actor_role / note / acted_at |
| 表 2 | `ops_push`：topic_key + state **唯一约束** → 同话题同状态只推一次 |
| 规则 | 状态**升级**（升温→爆发）允许再推；退潮后再升温也允许 |

**为什么 `ops_action` 要记 `state` 字段**：它是**闭环的原料** ——
系统当时判「爆发」、运营点了 ignore，就说明**阈值太松**。
**这是本项目阈值校准的唯一数据来源**（个人项目没有真实运营反馈，只能靠自己的记录）。

**实测**（已跑通）：

```
$ python 11情报Agent/community_ops.py --act follow --key "hid:2530899|page_view" \
      --title "白银之城技术测试招募开启" --note "已建话题页，观察24h"
{"ok": true, "topic_key": "hid:2530899|page_view", "action": "follow"}
```

## 3. 刻意不做的两件事

| 不做 | 为什么 |
|---|---|
| **用户维度运营** | PII 边界：只能出聚合分布，不能出「谁是活跃用户」清单。**做不了个体级运营动作**，硬做就违反三域模型 |
| **活动策划** | 需 LLM 生成创意（二创角度），当前 402 阻塞；且属「内容增长」角色的主场，不是社区运营 |

## 5. 与验收项的关系（诚实说）

| 验收项 | 本模块的作用 |
|---|---|
| A1 服务（员工能收到） | ⚠️ **仍未达成** —— 本模块产出的是**本地 .md 文件**，没有推送渠道 |
| B2 情报 | ✅ 已达成（本模块消费它） |
| B3 素材 | ⚠️ 部分覆盖（功能③ 提供高赞候选，但不是 4 类素材） |
| C3 可采纳 | 🔵 机制已就位（`ops_action` 表），但**没有入口让员工点** |

> **所以本模块的准确定位是**：**把「运营要收到的内容」准备好**，
> 但「送出去」那一步（推送层）还没做。
> **下一步应该是推送层** —— 否则这个日报和现有 11 份 `.md` 一样，还是没人看。
